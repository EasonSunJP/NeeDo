# NeeDo 未来六个月真实运营数据与排班预约去 Mock 设计

日期：2026-08-28  
状态：已确认设计，等待用户审阅  
适用仓库：`/Users/eason/Documents/New project`

## 1. 背景

NeeDo 本机正式开发数据库 `needo_dev` 已存在一套由 Prisma/MySQL 持久化的运营测试数据：

- 10 个商户负责人账号；
- 100 个技师账号；
- 100 个顾客账号；
- 10 家店铺；
- 30 个服务；
- 2,600 个排班时段；
- 1,957 条预约。

现有排班和预约数据只覆盖 2026-06-01 至 2026-08-29。与此同时，部分高级排班、调度和预约页面仍通过前端 store、localStorage 或固定日期生成展示数据。正式上线版本不能继续把这些浏览器数据当成业务事实。

本设计先完成一个可独立验收的微步骤：复用现有测试账号与实体关系，在真实 MySQL 中生成未来六个月的排班及预约数据，并将直接依赖这些数据的第一批页面切换为正式 API。其他模块的旧 mock 后续继续按页面和领域分批退役，不在同一个改动中爆发式重构。

## 2. 已确认时间范围

使用东京时区的六个完整自然月：

- 起点：2026-09-01 00:00:00 JST，包含；
- 终点：2027-03-01 00:00:00 JST，不包含；
- 页面显示范围：2026-09-01 至 2027-02-28；
- 数据库存储：统一转换为 UTC `DateTime`；
- 日本不实行夏令时，本数据窗口固定使用 UTC+09:00。

## 3. 目标与非目标

### 3.1 目标

1. 只复用数据库中已经存在的测试账号、店铺、技师档案、服务和身份关系。
2. 在真实 Prisma/MySQL 表中持久化 Availability、ScheduleSlot、BookingOrder 及必要的状态历史和通知。
3. 生成结果确定、可重复计算、可 dry-run、可对账、可安全重试。
4. 未来预约的状态和时间关系符合业务逻辑。
5. 第一批用户端、技师端和商户端排班/预约页面只读取正式 API。
6. 删除第一批页面中生成班次、预约或临时技师的 localStorage/mock 路径。
7. 重启前后端或刷新浏览器后，仍能读取同一批数据库记录。

### 3.2 非目标

1. 不创建新的用户、技师、商户负责人、店铺或公开号。
2. 不修改现有 `u/s/b/o/needo` 公开号规则或账号凭证。
3. 不删除 2026-06 至 2026-08 的历史运营数据。
4. 不把未来预约伪造成已完成服务，不触发未来结算或工资发放。
5. 不在本微步骤内一次性替换 IM、Social、餐饮、营销、财务等所有旧 mock。
6. 不在页面打开时临时生成业务数据。

## 4. 采用方案

采用独立的“未来六个月运营数据扩展”工作流，不修改旧三个月种子的破坏性重建范围。

旧 `seed-three-month-simulation.ts` 会重建服务、技师服务、旧预约、财务和其他关联记录。直接把它扩展为九个月会扩大删除范围，并可能影响已经验收的联系人、聊天、工资与财务数据。因此，新工作流只读取并验证已有实体，再增量写入新的日期窗口。

## 5. 真实账号与实体引用

生成器必须先从数据库解析以下既有记录：

- 100 个既有测试技师 User 与 TechnicianProfile；
- 100 个既有测试顾客 User 与 CustomerProfile；
- 10 家既有 Shop；
- 每位技师当前有效的 TechnicianService；
- 每项技师服务对应的正式 Service；
- 店铺与技师的当前有效归属关系。

解析只允许使用已经存在且可验证的稳定测试数据标识。不得：

- 创建补位账号；
- 猜测 userId、profileId、shopId 或 public identifier；
- 使用前端数组下标代替数据库关联；
- 在缺失实体时静默跳过并继续；
- 把 `customers[0]` 或静态展示用户作为预约人。

任何必需实体缺失、重复、已软删除或关系不一致时，dry-run 和 apply 都必须失败，并给出稳定、可定位的错误信息。

## 6. 排班生成规则

### 6.1 工作模式

- 正职技师：每周 5 个工作日，每个工作日约 4 个可预约时段；
- 临时技师：每周 3 个工作日，每个工作日约 3 个可预约时段；
- 使用确定性轮班规则分散休息日，避免所有技师使用完全相同的班表；
- 周末保留较高的可服务覆盖率；
- 加入少量确定性的休假、店铺维护或不可预约时段；
- 时段长度必须使用该技师当前有效服务的 `durationMinutes`；
- 同一技师的 Availability 和 ScheduleSlot 不得发生时间重叠；
- 所有时段必须位于所属店铺和技师关系的有效范围内。

### 6.2 状态

未来时段允许：

- `AVAILABLE`：尚未预约；
- `BOOKED`：存在有效的待处理或已确认预约；
- `BLOCKED`：休假、维护或人工封锁，不允许产生预约。

`BOOKED` 时 `bookedCount=1`；`AVAILABLE` 和 `BLOCKED` 时 `bookedCount=0`。每个时段容量保持为 1。

## 7. 预约生成规则

### 7.1 预约密度

预约率按距离当前日期递减，同时保留周末和热门时段更高的占用率：

- 2026-09：约 65%；
- 2026-10：约 55%；
- 2026-11：约 45%；
- 2026-12：约 50%；
- 2027-01：约 35%；
- 2027-02：约 25%。

实际精确数量由确定性生成器输出，并以 dry-run 结果作为 apply 后对账基线。不得使用运行时随机数导致每次结果不同。

### 7.2 预约人分配

- 只从现有 100 个顾客测试账号中分配；
- 每个顾客跨月份、店铺和技师获得不同预约分布；
- 同一个顾客在时间重叠的时段不得拥有多条有效预约；
- 顾客、店铺、技师、服务、技师服务和时段必须属于同一条可验证业务链。

### 7.3 未来状态约束

未来预约只允许：

- `PENDING`；
- `CONFIRMED`；
- `CANCELLED`。

禁止生成未来的 `IN_SERVICE` 或 `COMPLETED`。取消预约必须有取消原因，并把对应时段恢复为可预约状态；待处理或已确认预约必须占用时段。

未来预约不得生成已结算 OrderFinancial、工资行、已完成评价或收入账本。只有在真实业务状态机未来推进到服务完成后，才允许正式服务创建这些记录。

## 8. 幂等、命名空间与事务

新数据使用独立命名空间和独立订单号前缀，与 2026-06 至 2026-08 历史数据区分。命名空间必须保存在可审计的数据字段中，订单号必须唯一。

执行分两阶段：

1. `dry-run`：只读数据库，生成完整计划并输出统计，不写任何记录；
2. `apply`：重新验证同一输入和计划摘要后，在数据库事务中分批写入。

apply 要求：

- 使用 `createMany` 分批写入，避免逐行 N+1；
- 在事务开始后重新验证目标窗口不存在非本命名空间的冲突数据；
- 同一命名空间重复执行时，结果保持一致，不产生重复记录；
- 任一外键、重叠、唯一性或数量校验失败时整体回滚；
- 不删除或软删除目标窗口外的数据；
- 不触碰旧聊天、联系人、Social、工资、财务与会员数据。

## 9. Dry-run 与对账输出

dry-run 和 apply 后检查器至少输出：

- 数据库名称与安全环境判定；
- 已解析的顾客、技师、店铺、服务数量；
- 六个月各月 Availability、ScheduleSlot、BookingOrder 数量；
- 各状态预约数量；
- 每家店铺、每位技师的时段数量范围；
- 预约率；
- 时间范围最小值和最大值；
- 重叠冲突数；
- 重复订单号数；
- 无效外键或跨店铺关系数；
- 未来 `IN_SERVICE/COMPLETED` 数量；
- dry-run 计划摘要与 apply 后数据库摘要是否一致。

验收要求所有冲突、重复、无效关联和未来完成状态均为 0。

## 10. 第一批前端去 Mock 范围

真实数据写入并完成数据库对账后，再逐条切换直接消费排班与预约的页面：

1. 用户端预约列表、预约详情和技师日程；
2. 技师端排班、排班详情和预约详情；
3. 商户端排班安排、预约列表和调度中心的排班/预约视图。

每个页面必须：

- 通过现有 `/api/v1/` 正式接口读取；
- 根据当前登录账号和当前身份执行后端 RBAC；
- 不从 localStorage 恢复业务班次或预约；
- 不在前端创建临时技师、固定日期或假预约；
- API 失败时显示正式错误状态；
- 数据为空时显示真实空状态，不回退到展示数据；
- 刷新、重新登录和重启服务后数据保持一致。

如果现有正式 API 缺少某个页面所需字段，应先补最小正式 API 契约、Zod、Swagger、权限和测试，再切换该页面；不得以新的 mock 兼容层补位。

## 11. 测试策略

实施遵循测试驱动开发：

1. 先为六个月窗口、账号复用、班次模式、状态约束和确定性写失败测试；
2. 实现纯计划生成器；
3. 为 dry-run 安全门和对账摘要写失败测试；
4. 实现只读解析与 dry-run；
5. 为事务回滚、幂等和数据库约束写集成测试；
6. 实现 apply；
7. 为正式 API 和三端页面写失败测试；
8. 逐页面删除旧 store/localStorage 生成路径；
9. 运行相关 Jest、Vitest、lint、TypeScript、生产构建和数据库检查。

- [ ] 未创建任何新用户、技师、店铺或公开号。
- [ ] 所有排班与预约都引用现有测试账号和真实数据库实体。
- [ ] dry-run 不写数据库，并输出完整预计数量。
- [ ] apply 后数量与 dry-run 完全一致。
- [ ] 无技师排班重叠、无顾客有效预约重叠。
- [ ] 无重复订单号、无无效外键、无跨店铺错误关系。
- [ ] 未来 `IN_SERVICE/COMPLETED` 预约数量为 0。
- [ ] 重复执行不会产生重复数据。
- [ ] 旧三个月历史数据及其他业务数据未被改动。
- [ ] 第一批排班/预约页面只读取正式 API。
- [ ] 第一批页面不再使用 localStorage/mock 生成班次或预约。
- [ ] 刷新、重新登录、前后端重启后仍读取相同数据。
