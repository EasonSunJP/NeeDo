# NeeDo 统一公开号、身份隔离、通讯录与 Customer Support 正式设计

- 日期：2026-08-28
- 状态：已由用户最终批准，可进入小步实施计划
- 适用范围：NeeDo 用户端、技师端、店铺端、商户端、平台后台、Auth、User Management、IM、Social、Customer Support

## 1. 目标

本设计一次性统一 NeeDo 当前并存的 `n...`、`systemId`、错误 `b/s` 映射和仅展示用联系人编号，并定义同一自然人的多身份、真实好友关系、服务号、多人客服、固定联络分类和广告群发规则。

正式实现必须满足：

1. 公开号只有一套生成、解析、登录和检索规则。
2. 所有关系以内部 UUID 为主键，公开号用于展示、输入和受控检索。
3. 同一账号共享登录和实名主体，但不同身份的资料、资产、业务及社交数据严格隔离。
4. 联系人、好友、消息、服务号、客服和动态全部使用正式 API 与真实数据库。
5. 不新增 mock、展示用假 ID、前端推测 ID 或第二套兼容 API。
6. 旧规则在迁移完成后从正式 schema、运行时代码和数据中删除。

## 2. 非目标

本期不实现：

- 靓号付费会员、靓号定向分配、停付、封号、回收或账号删除策略；
- AI 客服、自动 FAQ、客服评分、SLA、智能分流、自动分配和客服绩效；
- 服务号分类的新增、改名、排序、启用或停用；分类已经改为固定系统分类；
- 图片或视频动态缩略图聚合；
- 旧 ID 的长期别名、双规则登录或双规则检索。

## 3. 术语和对象边界

| 对象 | 含义 |
|---|---|
| UserAccount | 一个自然人或公司发放账号的登录、实名与安全主体 |
| AccountIdentity | 该账号当前拥有的 `U/NEEDO/S/B/O` 身份空间 |
| accountNo | 账号注册或发放时生成的不可变10位数字字符串 |
| PublicIdentifier | 完整公开号及其类型、目标、登录与搜索能力的统一注册记录 |
| MerchantEntity | 商户组织实体，可管理一个或多个店铺 |
| Shop | 对普通用户可发现的店铺实体 |
| CustomerSupportAccount | 店铺或 NeeDo 官方的服务号入口，不是客服人员 |
| ServiceSubscription | 某一身份主动添加某一服务号的单向关系 |
| SupportConversation | 用户围绕一个具体问题创建的客服对话根节点 |
| BroadcastCampaign | 服务号向当前订阅身份发布的一次广告群发 |

`CustomerSupportAccount`、`SupportCategory`、`SupportConversation` 和实际回复的 `b` 客服是四个不同概念，数据库和 UI 均不得合并。

## 4. 统一公开号规则

### 4.1 人员账号和身份

| 身份 | 公开号 | 数字来源 | 是否可登录 | 是否可精确检索 |
|---|---|---|---|---|
| 普通主身份 | `u` + 10位 `accountNo` | UserAccount | 是 | 是 |
| 公司主身份 | `needo` + 10位 `accountNo` | UserAccount | 是 | 是 |
| 技师身份 | `s` + 同一 `accountNo` | UserAccount | 是 | 是 |
| 店铺工作人员身份 | `b` + 同一 `accountNo` | UserAccount | 是 | 是 |
| 商户管理身份 | `o` + 同一 `accountNo` | UserAccount | 是 | 是 |

约束：

- `accountNo` 必须保存为长度10的字符串，保留前导零。
- `U` 与 `NEEDO` 是互斥的主身份，同一账号不能同时拥有 `u...` 和 `needo...`。
- 普通注册账号的主身份是 `U`。
- 平台公司发放账号的主身份是 `NEEDO`，没有对应的 `u...`。
- `NEEDO` 使用普通用户端，没有独立的 needo 身份端；它可以被用户看到、精确搜索、加好友和聊天。
- `NEEDO` 账号可以按正常审核流程申请 `S/B/O` 身份。
- 只有真实存在且有效的身份才能创建相应公开号。
- 身份被撤销后，该身份不能继续登录或操作，但账号的其他身份不受影响。

### 4.2 商户、店铺和服务号

| 对象 | 公开号 | 数字来源 | 普通用户可检索 | 是否可登录 |
|---|---|---|---|---|
| 店铺实体 | `shop` + 10位数字 | 独立 `shopNo` | 名称及完整 ID | 否 |
| 商户实体 | `owner` + 10位数字 | 独立 `ownerNo` | 否 | 否 |
| 店铺服务号 | `cs` + 10位数字 | 与 Shop 数字一致 | 完整 ID | 否 |
| NeeDo 官方服务号 | `cs0000000000` | 平台保留 | 完整 ID | 否 |

约束：

- `shopNo`、`ownerNo` 和 `cs-ID` 一经创建不可修改。
- 店铺审核通过时，在同一事务中创建 Shop 公开号和对应服务号。
- 每个店铺有且仅有一个服务号。
- `shop2948173056` 必须对应 `cs2948173056`。
- `cs0000000000` 永久保留给 NeeDo 官方服务号，不属于任何店铺。
- 人员、店铺和商户的数字命名空间相互独立；完整公开号全局唯一。
- 已经分配的号码在对象注销或软删除后也不得重新发放。

### 4.3 统一 ID 注册表

正式系统建立唯一的 `PublicIdentifier` 注册表，至少记录：

- 规范化后的完整公开号；
- 数字部分；
- identifier kind；
- 内部目标 UUID；
- 是否允许登录；
- 是否允许搜索；
- 当前状态；
- 创建、更新时间和软删除信息。

所有 Auth、搜索、联系人、名片、聊天和后台审计均通过同一解析服务访问注册表。前端不得根据首字母自行构造账号，也不得把内部自增编号转成展示 ID。

## 5. 号码生成、碰撞与靓号封印

### 5.1 普通随机生成

- 使用安全随机数生成固定10位数字字符串。
- 候选号码先通过靓号规则和手动封印名单。
- 再通过数据库唯一索引原子占用。
- 碰撞时只回滚短事务并重新生成，不扫描整张用户表。
- 必须设置有限重试次数，禁止无限循环。
- 重试耗尽时，本次账号或实体创建整体回滚。
- 用户统一看到：`当前网络繁忙，请稍后再试`。
- 内部记录稳定错误码、碰撞次数和监控指标，不向用户暴露数据库异常。
- 所有用户可见错误文案进入现有三语言 i18n。

同一账号的 `u/needo/s/b/o` 使用相同数字是产品规则，不属于碰撞。

### 5.2 靓号库

本期仅“封印”靓号：

- 任意数字连续重复6位及以上；
- 连续递增或递减6位及以上；
- 由短数字块规律重复并覆盖大部分号码；
- 运营人员手动加入的具体号码，例如 `0077007700`。

靓号库由自动识别规则与手动号码共同组成。所有普通人员、店铺和商户号码生成器必须排除这些号码；`cs` 继承 Shop 数字，因此自然同步排除。

## 6. 登录和身份切换

### 6.1 登录解析

| 输入方式 | 登录落点 |
|---|---|
| 纯10位 `accountNo` + 密码 | 该账号真实存在的主身份 `U` 或 `NEEDO` |
| `u...` + 密码 | 对应 U 身份 |
| `needo...` + 密码 | 对应 NEEDO 主身份 |
| `s...`、`b...`、`o...` + 密码 | 对应有效身份 |
| 已绑定手机号 + 密码 | 该账号主身份 |
| 邮箱 + 密码 | 该账号主身份 |
| Google 登录 | 已绑定账号的主身份；首次注册创建普通 U 账号 |

规则：

- 各身份共用账号级手机号、邮箱、密码和安全记录。
- 使用带前缀 ID 登录时默认进入该身份。
- 身份不存在、停用或撤销时明确拒绝，不能静默回退到主身份。
- Session 必须绑定内部 `userAccountId + activeIdentityId`。
- `shopNo`、`ownerNo` 和 `cs-ID` 永远不能登录。
- `NEEDO` 的后台管理员、运营、客服、财务权限通过 RBAC 角色配置，不改变其用户端公开号。

### 6.2 共享与隔离

账号级共享：

- `accountNo`；
- 手机号、邮箱、密码和登录安全记录；
- 法定实名主体；
- eKYC 结果及认证材料；
- 账号级风控和审计。

身份级独立：

- 昵称、头像、简介及公开基础资料；
- NDP 账户、余额和流水；
- 利用次数；
- 信用度和评分；
- 订单；
- 收藏；
- 地址；
- 好友、好友申请、备注、标签和黑名单；
- 群聊身份、私聊记录和消息设置；
- 动态及其他身份业务记录。

会员权益只作用于主用户身份 `U` 或 `NEEDO`。切换到 `S/B/O` 后不得显示或继承会员标识及权益。

后端所有身份级查询必须使用已验证的 `activeIdentityId`，不能只依赖前端隐藏或请求体传入的身份 ID。

## 7. 检索、好友和通讯录

### 7.1 检索

- 人员 `u/needo/s/b/o` 仅允许完整 ID 精确检索。
- 不允许使用姓名或部分号码进行全局模糊查人。
- 店铺可以通过名称和完整 `shopNo` 搜索。
- `ownerNo` 不面向普通用户检索。
- 服务号可以通过店铺页面进入或使用完整 `cs-ID` 精确检索。
- 店铺页、订单、群聊和客服记录中的合法人员名片可以点击进入身份资料页。

### 7.2 好友关系

- 好友关系建立在两个 `identityId` 之间，而不是两个 UserAccount 之间。
- 任意有效身份可以向完整检索到的 `b/o` 发送好友申请。
- 对方接受前不能建立普通私聊。
- 切换身份后只能看到当前身份的好友、申请、标签、黑名单、群聊和聊天。
- 服务号单向添加关系不使用人员好友验证设置。

### 7.3 好友添加设置

在“设置 → 个人资料与认证”增加身份级设置：

1. 拒绝所有申请；
2. 需要验证添加；
3. 同意所有申请。

默认值为“需要验证添加”。修改设置不影响现有好友关系。

- “拒绝所有申请”由服务端立即拒绝新申请，发送方看到拒绝结果，接收方不产生待处理项。
- “需要验证添加”创建待处理项并通知接收方。
- “同意所有申请”由服务端立即建立好友关系，双方看到已添加状态。

### 7.4 新的朋友和申请状态

所有好友申请显示在“通讯录 → 新的朋友”，右侧显示：

- `待处理`
- `已添加`
- `拒绝`
- `过期`

状态规则：

- 第一次申请创建一条 `PENDING` 记录并通知接收方。
- `PENDING` 自服务端 `createdAt` 起满72小时未处理后变为 `EXPIRED`。
- 3天内重复发送返回成功语义，但不新建记录、不重复通知，也不延长过期时间。
- 后端可以记录 `lastAttemptAt` 用于限流和风控。
- 过期申请不能再接受；发送方再次申请时创建新记录并产生新通知。
- 接受后状态为 `ACCEPTED` 并建立身份级好友关系。
- 拒绝后状态为 `REJECTED`；拒绝后的3天内重复发送不产生新记录或通知，3天后可重新申请。
- 旧申请记录继续保留原状态用于历史与审计。

## 8. 联系人资料页与动态入口

- 联系人头像、昵称、简介和完整公开号来自真实身份记录。
- 不显示内部自增 ID、`ID 237`、`n...` 或前端临时编号。
- 备注、标签、免打扰、置顶和黑名单按当前身份关系保存。
- “开始聊天”使用正式好友关系和真实 Conversation。
- 在联系人资料页“标签”下方增加动态区域。
- 不加载图片或视频缩略图。
- 后端只做一次权限过滤后的轻量 `exists/limit 1` 查询，判断最近30天是否存在有效动态。
- 有动态显示“前往好友的动态页”；没有显示“好友近期无动态”。
- 两种状态整块均可点击进入该身份动态页。
- 查询必须使用真实 Social 数据和索引，不扫描媒体表。

## 9. 商户、店铺与工作身份范围

- 一个 MerchantEntity 可以管理一个或多个 Shop。
- 一个商户可以有多个拥有 `O` 身份的人员。
- `B` 是店铺工作身份，`O` 是商户级管理身份。
- 同一自然人可以拥有 `B` 和 `O`，数字均来自同一 `accountNo`。
- `B/O` 的实际人员 ID 可以在聊天和合法业务场景中被用户看到。
- `ownerNo` 代表组织，不是可搜索人员账号。
- `O` 进入店铺业务时必须先选择其有权管理的 Shop。
- `B` 只能操作其被授权 Shop。
- 所有店铺数据读写、服务号处理、未读数和审计必须携带并验证当前 `shopId`。

## 10. 服务号添加与通讯录入口

### 10.1 用户主身份

`U/NEEDO` 通讯录顺序为：

1. 新的朋友
2. 群聊
3. 服务号
4. 标签

“服务号”中可以保存多个用户主动添加的店铺服务号。

添加规则：

- 所有服务号，包括 `cs0000000000`，都必须由当前身份主动添加。
- 用户单向添加后立即生效，不需要店铺审核。
- 服务号不能主动添加用户。
- 添加关系按身份隔离；主身份添加不代表 `S/B/O` 自动添加。
- 用户可以删除任何服务号，包括 NeeDo 官方服务号。
- 删除后立即停止广告群发和创建新咨询。
- 历史客服 Conversation 与消息继续保留。
- 用户可以以后再次主动添加。

### 10.2 技师身份

`S` 技师端通讯录不显示“服务号”项目。

### 10.3 店铺和商户工作身份

- `B` 在“联系人 → 服务号”中处理其获授权 Shop 的队列。
- `O` 先选择有权管理的 Shop，再进入该店铺服务号。

## 11. 固定服务号分类和界面结构

分类不允许管理员新增、改名、排序、启用或停用。

用户可选择3类：

- 投诉 `COMPLAINT`
- 询问 `INQUIRY`
- 其他 `OTHER`

店铺端固定显示4类：

- 投诉
- 询问
- 其他
- 广告 `ADVERTISING`

界面规则：

- 分类不是聊天输入框上方的常驻按钮。
- 用户进入已添加的服务号后可以查看服务号广告和历史消息。
- 发起新的联络时先从“投诉/询问/其他”中选择，再进入对应消息和 Conversation。
- 未选择分类直接发送时，不创建业务消息、不创建 Conversation、不通知客服、不增加未读数；只显示系统提示“请先选择您要联络的内容分类”。
- 已存在 Conversation 的后续消息不重复选择分类。
- 已结束 Conversation 重新打开时保留原分类。
- 创建完全不同的新问题时重新选择分类。
- 用户回复某条广告时先选择3类之一，创建 Conversation 并保存 `sourceBroadcastId`。

## 12. 分类担当权限

- 店铺固定4类均需要分配担当员工。
- 担当人员使用真实 `B` 身份。
- Category 与 `B` 为多对多关系。
- 同一 `B` 可以担当多个分类；一个分类可以分配多名 `B`。
- 每一类至少有1名有效担当后，服务号对应能力才可启用。
- 未获该 Shop 和分类权限的人员不能查看、认领、回复、创建广告或发布。
- `O` 可以在有权限的 Shop 范围内管理担当关系；如需亲自回复客服消息，必须拥有并切换到自己的 `B` 身份。

## 13. Customer Support Conversation

### 13.1 创建

用户选择投诉、询问或其他并发送第一条正式消息后，创建独立 Support Conversation：

- `csId`
- `shopId`
- `categoryCode`
- `requesterIdentityId`
- `rootMessageId`
- `status = AVAILABLE`
- `claimedBy = NULL`
- 可选 `sourceBroadcastId`

用户消息支持 NeeDo IM 已经正式支持的文字、图片、视频、文件、表情、订单卡片、店铺或工作人员名片、定位等消息类型，不得另建一套简化消息格式。

### 13.2 状态机

```text
新问题
  ↓
AVAILABLE
  ↓ 认领
CLAIMED
  ├─ 释放 → AVAILABLE
  └─ 结束 → RESOLVED
                 ↓ 用户在原 Thread 再次发言
              AVAILABLE
```

规则：

- 同一 Conversation 同一时间只能有一名 Active Agent。
- 认领由服务端原子更新，不能只依赖前端状态。
- 认领后只有当前 `claimedBy` 可以回复。
- 其他有权限员工可以查看完整 Thread 和当前处理人，但不能回复。
- 关闭页面、退出 App、断网、后台运行、锁屏均不释放会话。
- 只有当前客服主动执行“释放会话”才回到 `AVAILABLE`。
- “结束处理”进入 `RESOLVED`，清空 active claim，并记录处理人和时间。
- 用户在已结束 Thread 中再次发言时回到 `AVAILABLE`，不得自动分配给原客服。

### 13.3 临时客服私聊和发送者身份

- 认领后建立用户与实际 `B` 客服之间、受该 Conversation 限制的 Support Private Session。
- 不需要好友关系。
- 它不能自动转成普通私聊；普通聊天仍需好友申请。
- 人工回复必须显示真实 `b-ID`，不能显示成 `cs-ID`。
- 同一 Thread 可以出现多个先后接手的不同 `b-ID`。
- 每条消息保存真实内部发送身份、消息类型、内容和时间。

### 13.4 UI 和日志

- `AVAILABLE/CLAIMED` 在根消息右侧显示可点击的 `＋`。
- `RESOLVED` 显示可点击的“结束”。
- 两者均进入同一完整 Thread。
- Thread 保留用户消息、客服回复及所有交接历史。
- `CLAIM/RELEASE/RESOLVE/REOPEN/TAKEOVER` 写入独立操作日志。
- 公共待处理数只统计各分类 `AVAILABLE` Conversation。
- `CLAIMED` 下的用户新消息计入当前客服个人未读，不重复进入公共待处理数。
- 新建 `AVAILABLE` Conversation 时通知该分类全部在线担当。
- 某一客服成功认领后，其他担当的公共待处理提醒立即消除。
- `CLAIMED` 状态下用户继续回复时只通知当前 `claimedBy`。
- `RESOLVED` 状态被用户重新打开后，再次通知该分类全部在线担当。

### 13.5 删除服务号后的现有客服会话

- 删除 ServiceSubscription 后停止新咨询和广告投递。
- 已经存在的开放 Thread 仍允许当前客服完成回复，因为授权来源于用户此前主动创建的 Conversation。
- 用户仍可查看历史；若要创建新咨询，必须重新添加服务号。

## 14. 广告群发

### 14.1 权限和内容

- 广告类也必须分配担当 `B` 员工。
- 仅获授权员工可以创建、查看草稿、编辑和发布。
- 支持文字、图片、视频、优惠信息、技师名片、迁址通知及 IM 已正式支持的内容类型。

### 14.2 发布和投递

- 一次发布创建一个 `BroadcastCampaign`。
- 发布使用客户端幂等键，网络重试不得重复生成广告。
- 系统获取发布时仍处于 active 状态的 ServiceSubscription 快照。
- 为每个接收身份创建独立 `BroadcastDelivery` 状态记录。
- 用户端显示发送者为 `cs-ID`。
- 后台记录实际发布的 `B` 操作人、Shop、内容版本、时间和审计日志；`O` 对担当授权的修改另行记录其真实操作身份。
- 广告显示在接收身份与该服务号的聊天窗口中。
- 已删除服务号的身份不在投递范围内。
- 广告不创建 Support Conversation，也不进入客服认领队列。
- 用户回复广告时选择投诉、询问或其他后才创建客服 Conversation。

## 16. API 与服务层边界

正式 API 使用 `/api/v1/`，并保持 Route → Controller → Service → Repository → Prisma 分层。

建议的服务边界：

- `IdentifierService`：号码生成、靓号判断、注册、解析和唯一性；
- `LoginResolverService`：根据纯数字、前缀 ID、手机、邮箱或 Google 解析账号及身份；
- `IdentityContextService`：验证 active identity 和身份切换；
- `IdentitySearchService`：按注册表和权限进行精确检索；
- `FriendRequestService`：偏好、状态机、3天过期、重复抑制；
- `ServiceSubscriptionService`：服务号添加、删除与列表；
- `SupportConversationService`：创建、认领、释放、结束、重新打开；
- `SupportAuthorizationService`：Shop、固定分类与担当权限；
- `BroadcastService`：草稿、发布、受众快照、幂等投递和审计；
- `ContactActivityService`：最近30天动态存在性查询。

所有新增入参使用 Zod，受保护接口声明 permission，列表分页，并更新 OpenAPI。

## 17. 错误和并发语义

- 公开号格式错误或旧 ID：返回稳定业务错误，不尝试兼容或猜测。
- 登录身份不存在/撤销：拒绝登录，不回退。
- 好友申请重复：返回当前有效申请，不重复通知。
- 好友申请过期：不能接受，必须重新申请。
- 未选择服务分类：不创建业务数据，返回可本地化的选择提示。
- 未订阅服务号：禁止创建新客服 Conversation。
- 无 Shop 或分类权限：403。
- 同时认领冲突：仅一方成功，另一方收到“该对话已被其他客服接手”。
- 非当前客服回复：403。
- 群发幂等键重复：返回原 Campaign 结果，不重复投递。
- ID生成重试耗尽：整体回滚并显示“当前网络繁忙，请稍后再试”。

## 18. 旧 ID 迁移和切换

### 18.1 迁移原则

- 所有现有账号重新生成随机10位 `accountNo`，不保留 `n...` 数字。
- 不把 `n0000000237` 简单改成 `u0000000237`。
- 好友、消息、订单和其他关系通过内部 UUID 保持。
- 不提供旧公开号别名。
- 不在正式运行时长期双读或双写。

### 18.2 迁移步骤

1. 只读审计所有账号、身份、店铺、商户、好友、消息、订单及保存旧 ID 的字段。
2. 新增正式字段、约束和注册表；旧运行时暂不切换。
3. 分批生成新号码并排除靓号，避免一个超大事务。
4. 根据真实已审核资格和业务关系创建 `S/B/O` 身份。
5. 依据业务上下文把资料和记录迁移到正确 `identityId`：
   - 消费者订单、收藏、地址 → 主身份；
   - 技师服务、排班、评分 → S；
   - 店铺工作人员操作 → B；
   - 商户级管理操作 → O。
6. 无法确定归属的数据进入迁移异常报告，不允许猜测或创建假身份。
7. 完成全量一致性检查后，在短暂切换窗口暂停身份相关写入。
8. 撤销旧 Session，一次性切换 Auth、搜索、联系人、IM 和前端展示。
9. 恢复服务，只接受新 ID。
10. 验收通过后，以后续 migration 删除旧字段、索引、生成器和前端适配代码。

已应用的历史 migration 文件不得手工修改；它们可以记录过去，但正式 schema、运行时代码和当前数据不得继续使用旧规则。

## 19. 测试与验收

### 19.1 ID 和登录

- 普通注册生成随机 `u...`，Google 首次注册也生成 U。
- 公司发放账号只有 `needo...` 主身份。
- 纯数字、手机、邮箱、Google 和完整身份 ID 的登录落点正确。
- 无效/撤销身份不能登录。
- 同一账号的 `S/B/O` 数字与主身份一致。
- 靓号规则及手动号码不会被随机分配。
- 碰撞重试不产生半个账号，耗尽时显示指定文案。
- 旧 `n...` 和旧 `systemId` 登录、搜索和 API 查询全部失败。

### 19.2 身份隔离

- 昵称、头像、简介、NDP、评分、订单、收藏、地址、好友和聊天按身份隔离。
- eKYC、手机号、邮箱和安全记录共享。
- 主身份会员权益不泄漏到 `S/B/O`。
- 身份切换和重新登录后隔离仍成立。

### 19.3 好友和联系人

- 三种好友添加偏好正确。
- 新的朋友显示待处理、已添加、拒绝、过期。
- 3天内重复发送不重复通知；过期或拒绝冷却完成后可重新申请。
- `b/o` 未成为好友时不能普通私聊。
- 联系人资料显示真实公开号。
- 最近30天动态入口使用真实 Social 数据，无媒体缩略图查询。

### 19.4 服务号和客服

- U/NEEDO 可添加多个服务号；S 不显示服务号入口。
- 删除服务号停止新咨询与广告，但历史保留。
- 用户只能选择投诉、询问、其他；店铺端固定多一个广告。
- 未选分类发送不创建 Conversation。
- 分类担当权限和 Shop 范围严格生效。
- 并发认领只有一人成功。
- 人工消息显示真实 `b-ID`。
- 释放、结束、重新打开和接手完整记录。

### 19.5 广告

- 只有广告担当可以创建和发布。
- 同一幂等键不重复发布。
- 只投递给发布时仍订阅的身份。
- 用户聊天窗口显示 `cs-ID`。
- 回复广告必须选择3类之一，并记录来源广告。

### 19.6 真实数据证明

- 全部测试通过正式 `/api/v1/` 和真实数据库执行。
- 使用多组真实测试账号覆盖 `U/NEEDO/S/B/O`。
- 验证数据库写入、重新登录和重启后端后仍存在。
- 迁移前后好友、消息、订单、店铺和商户关系数量对账一致。
- 自动测试通过后仍需在目标用户端、技师端、店铺端和商户端进行实际 UI 验收。

## 20. 实施约束

本设计范围很大，后续实施计划必须拆为可运行、可测试、可回滚的微步骤。不得把 schema、Auth、所有前端、IM、Customer Support 和迁移合并为一个巨大变更。

任何微步骤完成前必须满足：

- 没有新增 mock、demo、placeholder 或 fake API；
- 新接口有 Zod、OpenAPI、permission 和测试；
- schema 变更有新 migration，不修改已应用 migration；
- 三语言 i18n 完整；
- lint、测试和正式 build 通过；
- 使用真实数据库完成对应端到端验收；
- 未经验收不得进入依赖它的下一微步骤。
