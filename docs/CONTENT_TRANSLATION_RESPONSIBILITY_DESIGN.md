# NeeDo 页面内容翻译职责分层设计文档

## 1. 结论

当前设想整体合理：

- 动态内容、用户生成内容、聊天内容：由用户在前端手动点击“翻译”触发，按需展示译文。
- 固定业务内容、可长期复用内容：由店铺、技师、运营在录入时维护多语言版本，后端保存并按语言返回。
- 系统固定 UI 文案：继续由前端 i18n 管理，后端尽量只返回状态码、枚举值、模板 key 或配置 key。

需要补充的一点是：“前端翻译”应定义为“前端触发翻译与展示译文”，不建议前端直接持有第三方翻译服务密钥。实际机器翻译请求应通过后端受控服务完成，以便做权限、限流、缓存、审计和敏感内容保护。

## 2. 基本定义

| 类型 | 定义 | 翻译责任 | 典型场景 |
|---|---|---|---|
| 系统 UI 文案 | 按钮、导航、状态名、字段名、错误提示、菜单名 | 前端 i18n | “确认预约”“联系”“时间”“取消订单” |
| 固定业务内容 | 店铺、技师、服务、分销任务等长期展示内容 | 后台多语言录入，后端存储 | 店铺名称、技师简介、服务说明、分销任务标题 |
| 动态用户内容 | 用户、技师、店铺临时发布或互动产生的内容 | 前端手动触发翻译 | 评论、动态、帖子、聊天消息、临时备注 |
| 通知模板内容 | 系统根据事件生成的通知 | 模板 key 前端翻译，变量由后端提供 | “预约已确认”“技师已接单” |
| 法务与规则内容 | 协议、隐私政策、退款规则、平台规则 | 后台或运营维护正式多语言版本 | 用户协议、取消政策、结算规则 |

## 3. 职责划分规则

### 3.1 前端 i18n 管理

适用于不会由商家、技师、用户自由编辑的系统固定文案。

后端不要直接返回这类文案的最终显示文本，应返回稳定的业务 code，例如：

```json
{
  "bookingStatus": "CONFIRMED",
  "paymentMethod": "PAYPAY",
  "serviceMode": "IN_STORE"
}
```

前端根据当前语言把 code 映射为文案：

```ts
t("booking.status.CONFIRMED")
t("serviceMode.IN_STORE")
```

这样可以保证按钮、导航、状态、菜单在全端一致，也方便继续使用现有 `zh`、`zh-Hant`、`ja`、`en`、`ko` 语言体系。

### 3.2 后台多语言录入

适用于稳定、可编辑、需要被搜索和复用的业务内容。

建议支持以下内容在录入时维护多语言：

| 模块 | 字段示例 | 推荐处理 |
|---|---|---|
| 店铺基础信息 | 店铺名、简介、地址补充、营业说明、交通说明 | 后台多语言录入 |
| 技师基础信息 | 昵称、个人简介、擅长项目、资质说明 | 后台多语言录入 |
| 服务项目 | 服务名、服务描述、适用人群、注意事项 | 后台多语言录入 |
| 套餐与商品 | 套餐名、权益说明、使用规则 | 后台多语言录入 |
| 店铺分销任务 | 任务标题、任务说明、奖励规则、素材说明 | 后台多语言录入 |
| 店铺公告 | 固定公告、营业调整、规则说明 | 后台多语言录入 |
| 平台运营内容 | banner、活动页、推荐位标题 | 运营后台多语言录入 |

录入规则：

- 必填一种源语言，默认可使用简体中文或日文，具体由业务后台配置。
- 其他语言可选填。
- 前端展示时优先当前语言，其次源语言。
- 如果当前语言缺失，不自动改写原文，可显示原文并保留语言标记。
- 商家和技师只维护自己有权限编辑的内容，平台运营可维护平台级内容。

### 3.3 前端手动翻译

适用于实时、临时、高频、不可预先维护多语言的内容。

建议支持手动翻译的内容：

| 模块 | 字段示例 | 推荐处理 |
|---|---|---|
| IM 聊天 | 文本消息、订单协商消息 | 前端显示“翻译”按钮，点击后请求翻译 |
| Social 动态 | 帖子正文、评论、回复 | 前端按条翻译 |
| 评价内容 | 用户评价、店铺回复 | 前端按条翻译 |
| 临时备注 | 用户备注、技师备注、店铺临时说明 | 根据权限按需翻译 |
| 站内私信 | 用户与店铺、用户与技师互动内容 | 前端按条翻译 |

交互规则：

- 默认显示原文，不自动翻译。
- 每条内容显示“翻译”入口，点击后展示当前语言译文。
- 译文旁提供“查看原文”或“显示原文”入口。
- 同一条内容、同一目标语言命中缓存时直接展示缓存译文。
- 内容被编辑后，以内容 hash 判断缓存是否失效。
- 已删除、无权限访问、被风控限制的内容不允许翻译。

## 4. 数据结构建议

### 4.1 稳定业务内容

建议使用统一的多语言文本结构：

```ts
type LanguageCode = "zh" | "zh-Hant" | "ja" | "en" | "ko";

type LocalizedText = {
  sourceLanguage: LanguageCode;
  values: Partial<Record<LanguageCode, string>>;
};
```

示例：

```json
{
  "name": {
    "sourceLanguage": "ja",
    "values": {
      "ja": "GINZA Calm Body Lab",
      "zh": "银座静体护理实验室",
      "en": "GINZA Calm Body Lab"
    }
  },
  "description": {
    "sourceLanguage": "ja",
    "values": {
      "ja": "静かな完全予約制サロンです。",
      "zh": "安静的完全预约制沙龙。"
    }
  }
}
```

数据库落地可分两阶段：

| 阶段 | 方案 | 适用 |
|---|---|---|
| 第一阶段 | JSON 字段保存多语言文本，例如 `name_i18n`、`description_i18n` | 店铺、技师、服务等低频编辑内容 |
| 第二阶段 | 独立翻译表，按 `resourceType`、`resourceId`、`fieldName`、`language` 存储 | 大规模内容、审批流、版本管理、搜索优化 |

第一阶段可以更快落地，但需要明确 JSON schema，并在 Service 层统一做语言选择和 fallback。

### 4.2 动态内容译文缓存

动态内容不直接改写原文，译文作为缓存结果保存。

建议缓存结构：

```ts
type TranslationCache = {
  resourceType: "message" | "social_post" | "comment" | "review";
  resourceId: string;
  sourceLanguage?: LanguageCode;
  targetLanguage: LanguageCode;
  sourceHash: string;
  translatedText: string;
  provider: string;
  createdAt: string;
  expiredAt?: string;
};
```

缓存 key 建议：

```text
resourceType + resourceId + targetLanguage + sourceHash
```

这样可以避免原文更新后继续展示旧译文。

## 5. API 设计建议

### 5.1 公开读取接口

前端请求时带当前语言：

```http
GET /api/v1/stores/:id
Accept-Language: ja
```

后端返回已按语言解析的展示字段，并附带 fallback 信息：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "id": "store_001",
    "displayName": "GINZA Calm Body Lab",
    "displayDescription": "静かな完全予約制サロンです。",
    "language": "ja",
    "fallback": {
      "displayName": false,
      "displayDescription": false
    }
  }
}
```

编辑接口返回完整多语言结构，方便后台表单编辑：

```json
{
  "name": {
    "sourceLanguage": "ja",
    "values": {
      "ja": "GINZA Calm Body Lab",
      "zh": "银座静体护理实验室",
      "en": "GINZA Calm Body Lab"
    }
  }
}
```

### 5.2 手动翻译接口

前端点击“翻译”后调用后端翻译服务：

```http
POST /api/v1/translations/translate
```

请求示例：

```json
{
  "resourceType": "message",
  "resourceId": "msg_001",
  "targetLanguage": "zh"
}
```

响应示例：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "resourceType": "message",
    "resourceId": "msg_001",
    "targetLanguage": "zh",
    "translatedText": "明天 15:00 可以到店。",
    "fromCache": true
  }
}
```

接口要求：

- 必须校验用户是否有权限读取原内容。
- 必须限流，避免恶意刷翻译成本。
- 必须记录审计日志，包括用户、资源类型、资源 id、目标语言、是否命中缓存。
- 不返回第三方翻译服务的密钥、原始错误或内部 provider 细节。
- 聊天和私密内容不得被无权限用户翻译。

## 6. 特殊场景处理

### 6.1 后端下发页面配置

如果某些页面元素确实全部由后端下发，仍建议区分两类：

| 后端下发内容 | 推荐方式 |
|---|---|
| 按钮、状态、菜单、tab、固定标签 | 下发 key/code，前端 i18n 展示 |
| banner、活动标题、店铺任务说明 | 后台维护多语言内容，后端按语言返回 |

不建议后端直接下发单语言的按钮文案给前端再由运行时翻译，因为这会导致文案不稳定、难以测试，也容易绕过术语表。

### 6.2 通知与系统消息

系统通知建议保存事件结构，而不是只保存最终文案。

```json
{
  "templateKey": "booking.confirmed",
  "variables": {
    "storeName": "GINZA Calm Body Lab",
    "time": "2026-06-27T10:00:00Z"
  }
}
```

前端或后端根据用户语言渲染模板。变量中的店铺名、服务名等使用对应语言的 `displayName`。

### 6.3 搜索与筛选

搜索逻辑需要同时考虑源语言与多语言字段：

- 店铺、技师、服务名称应索引源语言和已录入的多语言值。
- 未录入目标语言时，搜索结果仍可按源语言命中。
- 标签、分类、状态等结构化字段使用 code，不使用自由文本做筛选依据。

### 6.4 法务内容

协议、隐私政策、退款规则、平台规则必须使用正式维护的多语言版本。

这类内容不建议使用即时机器翻译作为最终展示文本。若需要辅助翻译，也应经过运营或法务确认后发布。

## 7. 前端展示规则

| 内容状态 | 展示方式 |
|---|---|
| 当前语言有正式内容 | 直接展示当前语言 |
| 当前语言缺失，源语言存在 | 展示源语言，可显示“原文”标记 |
| 动态内容未翻译 | 展示原文和“翻译”按钮 |
| 动态内容翻译成功 | 展示译文，并允许切回原文 |
| 翻译失败 | 保留原文，显示轻量错误提示 |
| 用户无权限 | 不显示翻译入口 |

前端需要提供统一工具函数：

```ts
pickLocalizedText(localizedText, currentLanguage)
```

该函数负责：

- 选择当前语言。
- 当前语言缺失时 fallback 到源语言。
- 返回是否发生 fallback。
- 避免每个页面重复写判断逻辑。

## 8. 权限与安全

- 店铺只能编辑自己店铺相关内容的多语言字段。
- 技师只能编辑自己资料中允许编辑的多语言字段。
- 平台运营可以编辑平台级内容和审核敏感内容。
- 用户生成内容的翻译必须先校验读取权限。
- 翻译接口必须限流，防止成本失控。
- 第三方翻译密钥只能存在后端环境变量中。
- 聊天、备注、订单协商等私密内容必须纳入审计。
- 原文必须保留，不得被机器译文覆盖。

## 9. 推荐落地顺序

| 阶段 | 目标 | 范围 |
|---|---|---|
| 1 | 建立翻译字段规范 | 定义 `LocalizedText`、语言 fallback、前后端 DTO 约定 |
| 2 | 固定业务内容多语言化 | 店铺、技师、服务、套餐、分销任务 |
| 3 | 前端统一展示工具 | `pickLocalizedText`、fallback 标记、编辑表单组件 |
| 4 | 动态内容手动翻译 | IM、Social、评论、评价，接入翻译缓存 |
| 5 | 通知模板多语言化 | template key、变量、多语言渲染 |
| 6 | 搜索与审核增强 | 多语言索引、敏感内容审核、翻译审计 |

当前文档仅定义设计原则和实施边界。IM、Social、Notification 的后端化应跟随正式微步骤进入对应阶段时再实现，避免提前扩大开发范围。

## 10. 开发团队执行清单

- [ ] 新增后端业务字段前，先判断字段属于系统 UI、固定业务内容、动态内容还是法务内容。
- [ ] 系统 UI 文案只传 code/key，不传自由文本。
- [ ] 固定业务内容使用 `LocalizedText` 或等价结构保存。
- [ ] 动态内容保存原文，译文作为缓存，不覆盖原文。
- [ ] 翻译请求由前端触发，但由后端代理实际翻译服务。
- [ ] 所有翻译接口必须鉴权、限流、审计。
- [ ] 编辑端需要支持源语言必填、其他语言选填。
- [ ] 读取端需要统一 fallback 规则。
- [ ] 搜索、筛选和排序优先使用结构化 code 与索引字段。
- [ ] 法务内容必须使用正式发布的多语言版本，不依赖即时翻译。
