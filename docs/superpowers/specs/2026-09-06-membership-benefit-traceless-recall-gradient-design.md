# NeeDo 会员权益本地化、无痕撤回与三色卡面设计

**日期：** 2026-09-06  
**适用阶段：** Step 12 运营后台真实数据、Step 13 IM / Social / Notification 后端化  
**状态：** 已获用户确认，待实施  
**范围：** 运营后台会员等级设置、平台会员权益目录、聊天撤回策略、详细会员卡大面积底色

## 1. 背景与目标

运营后台的会员等级编辑器目前直接展示权益字段代码，详细会员卡只允许配置单一大面积底色，并以强调色和底色的对比度阻止保存或发布。正式 IM 当前只实现普通撤回，双方都会看到不含原文的撤回占位。

本次调整建立以下正式行为：

1. 会员等级编辑器按运营后台当前语言展示正式权益名称，不显示字段代码；
2. “会员权益说明”页面按当前语言展示完整正式权益目录，并加入无痕撤回说明；
3. 新增“聊天无痕撤回”权益，免费会员默认关闭，白银、黄金、黑钻默认开启；
4. 用户执行同一个撤回操作时，由后端根据撤回当时的有效权益选择普通撤回或无痕撤回；
5. 详细会员卡的大面积底色由左上、中段、底部三个颜色形成渐变；
6. 颜色仍需满足格式校验，但任何颜色对比度都不得阻止草稿保存或版本发布。

本设计不新增 mock，不让前端会员文案或会员等级名称成为聊天授权依据，也不改变店铺自行发行的会员卡体系。

## 2. 已确认的产品规则

### 2.1 权益显示语言

- 运营后台会员等级设置从正式会员权益目录读取名称和说明。
- 运营后台“会员权益说明”页面使用同一正式权益目录，并展示新增无痕撤回权益的名称和完整说明。
- 页面使用运营后台当前语言选择 `zh`、`zh-Hant`、`ja`、`en` 或 `ko` 对应翻译。
- 接口字段代码只用于稳定标识、提交和审计，不作为正常界面的显示文案。
- 单项翻译缺失时按现有平台 i18n 回退规则选择可用翻译；只有正式数据异常且所有翻译均为空时，才允许显示稳定代码作为诊断性回退。

### 2.2 聊天无痕撤回权益

正式权益代码新增 `traceless_recall`，显示名称为“聊天无痕撤回”。五语言名称和说明存放在正式权益目录中。

权益说明需要明确表达：开启后，会员在有效撤回时限内撤回自己发送的消息，发送者和接收者的聊天窗口均不保留“消息已撤回”提示；发送者权限、撤回时限和安全审计仍然适用。五语言文本表达相同业务含义，不把会员等级名单写入说明文案。

首版正式文案：

| 语言 | 权益名称 | 权益说明 |
| --- | --- | --- |
| 简体中文 | 聊天无痕撤回 | 在有效撤回时限内撤回自己发送的消息时，双方聊天窗口均不保留“消息已撤回”提示。发送者权限、撤回时限和安全审计仍然适用。 |
| 繁体中文 | 聊天無痕撤回 | 在有效撤回時限內撤回自己傳送的訊息時，雙方聊天視窗均不保留「訊息已撤回」提示。傳送者權限、撤回時限和安全稽核仍然適用。 |
| 日本語 | 痕跡を残さない送信取消 | 有効な取消期限内に自分が送信したメッセージを取り消すと、双方のチャット画面に「メッセージを取り消しました」という表示が残りません。送信者の権限、取消期限、セキュリティ監査は引き続き適用されます。 |
| English | Traceless message recall | When you recall your own message within the valid recall window, no “message recalled” notice remains in either participant's chat. Sender authorization, the recall deadline, and security auditing still apply. |
| 한국어 | 흔적 없는 메시지 회수 | 유효한 회수 시간 안에 자신이 보낸 메시지를 회수하면 양쪽 채팅 화면에 “메시지가 회수되었습니다” 안내가 남지 않습니다. 발신자 권한, 회수 시간 제한 및 보안 감사는 계속 적용됩니다. |

默认值：

| 会员等级 | 默认状态 |
| --- | --- |
| 免费会员 `free` | 关闭 |
| 白银会员 `silver` | 开启 |
| 黄金会员 `gold` | 开启 |
| 黑钻会员 `black_diamond` | 开启 |

运营发布会员等级新版本后，新版本的权益状态成为当前资格判断依据。正式权益目录的全局停用仍具有最高优先级；全局停用后，即使某会员版本中该权益为开启，也按关闭处理。

### 2.3 撤回行为

- 客户端仍只提供一个“撤回”操作，不展示普通/无痕模式选择器。
- 仅消息发送者可以撤回，且继续受后端的正式撤回时限约束。
- 后端在撤回事务开始时解析当前用户的有效平台会员版本及 `traceless_recall` 权益。
- 权益关闭时执行普通撤回：双方保留“消息已撤回”占位，行为与当前正式实现一致。
- 权益开启时执行无痕撤回：发送者和所有接收者的聊天窗口均不显示消息，也不显示撤回占位。
- 本次撤回采用的模式写入消息生命周期状态。用户之后升级、降级或权益版本变化，不重新解释历史撤回结果。
- 重复撤回请求保持幂等，不能恢复内容、改变已确定的撤回模式或重复生成可见事件。

### 2.4 三色大面积底色

详细会员卡的大面积底色配置调整为：

1. 详细卡左上底色；
2. 详细卡中段底色；
3. 详细卡底部底色。

用户端实际详细卡和运营后台预览必须复用同一个渐变生成逻辑。渐变从左上方向经过中段延伸到底部，三个色值均为正式会员版本主题的一部分。

### 2.5 颜色发布规则

- 所有主题颜色继续校验为合法十六进制颜色，非法格式不得保存。
- 删除前端和后端所有“颜色对比不足则不能保存或发布”的门禁。
- 自动文字颜色可以继续用于提高预览可读性，但计算结果仅影响展示，不构成发布资格。

## 3. 采用的架构

采用“正式会员权益驱动、服务端决定撤回模式、渐变字段增量扩展”的方案。

不继续使用 IM 内部的会员等级名单作为本功能的正式判断来源。该名单会与会员等级版本和全局权益开关形成第二套配置，产生发布后不一致风险。现有 `ImPolicy.tracelessRecallMembershipLevels` 在本微步骤中保留以避免破坏历史 schema，但不再作为新无痕撤回资格的来源；后续如要删除，应另开迁移步骤。

不在会员等级表增加独立的 `tracelessRecallEnabled` 布尔字段。无痕撤回属于会员权益目录，与其他权益共用版本、全局开关、翻译和审计能力。

## 4. 正式数据模型与迁移

### 4.1 权益枚举与目录

在正式会员权益枚举中追加 `traceless_recall`，并在权益目录写入五语言名称、说明和确定的排序值。

迁移为每个现有会员等级版本补齐该权益关系：

- `free` 写入关闭；
- `silver`、`gold`、`black_diamond` 写入开启。

迁移必须可在已有正式数据上安全执行，不覆盖其他七项权益的既有状态，不生成重复目录或重复等级权益关系，并同步扩展与权益数量或排序范围有关的数据库约束。

### 4.2 主题字段

保留现有 `detailSurfaceColor`，将其正式解释为详细卡左上底色；新增：

- `detailSurfaceMiddleColor`：详细卡中段底色；
- `detailSurfaceBottomColor`：详细卡底部底色。

迁移时把每个既有版本的 `detailSurfaceColor` 复制到两个新字段。迁移后旧卡面仍呈现原来的纯色效果，只有运营修改并发布新版本后才出现新的三色渐变。

前端类型、API 解码、Zod、OpenAPI、Service、Repository 和 Prisma 映射必须同步要求完整的三个色值，不允许只在前端临时拼接未持久化颜色。

## 5. 后端业务流

### 5.1 权益解析边界

Realtime Service 通过一个窄的会员权益解析端口读取用户在当前时刻的有效权益。该端口由正式平台会员服务实现，返回是否具有 `traceless_recall`，不把会员数据库查询散落到 IM Repository。

解析必须遵守：

1. 当前有效会员资格；
2. 当前发布的会员等级版本；
3. 该版本中的权益开关；
4. 权益目录的全局启停状态。

任何无有效资格、无发布版本、权益缺失或全局关闭情况均按无痕权益关闭处理，不得由客户端声明升级为无痕撤回。

### 5.2 原子撤回

后端在同一事务边界内完成资格解析结果的应用和消息生命周期变更：

- 普通撤回写入 `STANDARD`，清空用户内容，保留无内容占位行，写入 `STANDARD_RECALL` 同步指令；
- 无痕撤回写入或保留 `TRACELESS` 生命周期审计事实，从参与者可见历史中移除消息，清理文字、翻译、反应、媒体及可识别原内容，写入 `TRACELESS_RECALL` 同步指令。

无痕撤回的审计和同步记录只能包含消息 ID、会话 ID、操作人 ID、时间和模式，不得包含原文、翻译、媒体 URL、存储键、文件名或缩略图。

### 5.3 会话派生状态

无痕撤回完成后，后端重新计算受影响会话的派生状态：

- 最后一条可见消息和预览；
- 未读计数；
- 已读位置或与被撤回消息有关的可见标记。

如果不存在更早的可见消息，预览回到空状态。不得继续显示已无痕撤回消息的内容、类型或“已撤回”摘要。

### 5.4 实时与离线同步

- 在线参与者收到不含原内容的无痕撤回事件，前端按消息 ID 删除对应行。
- 普通撤回事件继续把消息替换为双方可见占位。
- 离线设备通过正式删除同步游标收到 `TRACELESS_RECALL`，删除本地内存、IndexedDB、媒体缓存和活动对象 URL 中对应内容。
- 历史列表查询过滤无痕撤回消息；普通撤回消息仍返回内容为空的占位模型。

## 6. 前端交互与视觉

### 6.1 会员等级编辑器

- 页面同时读取固定四档会员等级和正式权益目录。
- 每项开关以当前语言的正式权益名称显示，说明仍可通过已有说明区域或信息入口读取当前语言内容。
- 提交继续使用稳定权益代码，切换语言不会改变草稿值。
- 新权益按正式排序进入现有两列权益布局，不为其创建单独的临时表单字段。

### 6.2 会员权益说明

- “会员权益说明”页面读取与等级编辑器相同的正式权益目录，不维护第二套静态说明。
- 新增“聊天无痕撤回”的五语言名称和说明，页面按当前后台语言展示。
- 全局启停、编辑和审计继续复用现有权益目录能力；修改说明不会直接改变等级开关，修改等级开关也不会覆盖说明文本。

### 6.3 会员卡颜色编辑

原“详细卡大面积底色”改为三个独立色值输入：左上、中段、底部。其余强调色、项目底色、边框、头像边框和简易卡上下颜色保持不变。

详细卡使用统一的线性渐变，例如从左上到右下的约 `155deg` 方向：

```text
左上色 0% -> 中段色 52% -> 底部色 100%
```

准确角度和中段位置由共享主题函数固定，运营预览与用户端不能各自维护不同 CSS。

低对比组合可以正常保存草稿和发布。界面不再显示阻止性对比度错误，也不因对比度禁用按钮。

### 6.4 聊天窗口

聊天菜单仍显示统一的“撤回”。成功响应和实时事件中的服务端撤回模式决定本地更新：

- `standard`：将消息变为现有撤回占位；
- `traceless`：从消息列表直接移除，双方不显示额外系统提示。

前端不得根据自己的会员展示标签预测或覆盖服务端结果。

## 7. API、权限与审计

- 现有撤回接口路径、发送者校验、会话参与者校验和撤回时限保持不变。
- 请求不新增可由客户端选择的无痕模式。为兼容现有客户端，可暂时接受当前 `mode: "standard"` 请求字段，但它只表示执行撤回操作，不决定最终服务端模式。
- 响应和 SSE 模型返回实际 `recallMode`，只允许 `standard` 或 `traceless`。
- 会员等级草稿和发布继续使用既有 RBAC、版本控制和审计链路。
- 发布会员版本时删除对比度断言，但保留主题字段完整性和颜色格式校验。
- 无痕撤回生成内容为空的安全审计动作；普通撤回保留现有审计语义。

## 8. 错误处理

- 正式权益目录加载失败时，会员等级编辑器显示已有错误态，不能用硬编码权益名称伪装正式数据成功。
- 权益解析基础设施异常时，撤回请求失败并保持消息不变，不得静默降级后造成双方状态分叉。
- 合法但低对比度的颜色不得产生业务错误。
- 非法颜色格式、版本冲突、无权限、超过撤回时限等继续返回稳定错误键。
- 实时事件重复或乱序时，普通和无痕更新均按消息 ID 幂等；无痕删除优先级高于普通占位，不能被旧事件恢复。

## 9. 测试与验收

### 9.1 数据与后端

- migration 在已有七项权益和既有主题数据上成功升级；重复目录和关系受约束保护；
- 免费等级默认关闭，三档付费等级默认开启；
- 当前发布版本、全局权益开关和会员有效期共同决定资格；
- 普通撤回继续产生双方占位；无痕撤回双方都无占位；
- 权益变化不改变历史撤回模式；重复请求保持幂等；
- 无痕审计、SSE 和删除同步不包含原内容；
- 历史查询、会话预览和未读状态不泄漏无痕消息；
- 任意合法颜色组合均可保存和发布，非法十六进制颜色仍被拒绝。

### 9.2 前端

- 五种后台语言分别显示正式权益名称，不显示 `ndp_experience` 等原始代码；
- “会员权益说明”页面在五种语言下均包含无痕撤回的正式名称和说明；
- 新权益的开关值可读取、修改、保存草稿并发布；
- 三个底色输入实时生成与用户端一致的渐变；
- 旧主题解码升级后保持视觉兼容；
- 低对比色不显示阻止性错误，保存和发布按钮可用；
- 普通撤回显示现有占位，无痕撤回直接删除，重复 SSE 不恢复消息。

### 9.3 正式验收边界

代码测试和构建通过后，仍需在真实运营后台和两个正式聊天账号之间进行浏览器验收：

1. 切换后台语言，确认等级设置的权益名称及“会员权益说明”中的无痕撤回说明随语言变化；
2. 检查免费与三档付费会员默认开关；
3. 配置并发布三色渐变，确认预览与用户详细卡一致；
4. 发布低对比主题，确认没有前后端阻止；
5. 分别使用无权益和有权益账号撤回消息，确认双方窗口、刷新后历史和会话预览一致；
6. 检查浏览器控制台、网络错误和移动端横向溢出。

数据库 migration 应用、正式环境部署和 staging 跨账号验收是独立发布步骤，未经明确授权不得把本地测试结果表述为已部署。

## 10. 非目标

- 不新增每次撤回时的模式选择器；
- 不改变 180 秒撤回窗口或发送者权限规则；
- 不删除历史 `ImPolicy.tracelessRecallMembershipLevels` 字段；
- 不重做整个会员等级页面或会员卡视觉系统；
- 不修改店铺发行的会员卡权益；
- 不把卡面低对比度改成另一种隐藏发布限制；
- 不在本微步骤执行 staging 部署或正式数据库迁移。

## 11. 回滚策略

- 业务代码可回滚到只执行普通撤回；已经记录为无痕撤回的消息不得恢复原内容。
- 新增主题字段在回滚代码后可留存，旧代码继续读取 `detailSurfaceColor`，不需要破坏性删列。
- 新权益目录和等级关系可以保留为未被旧代码消费的数据；不得通过回滚迁移恢复已清理的聊天内容。
- 发布前必须分别备份和验证数据库迁移回滚边界，尤其确认枚举扩展在 MySQL 中不依赖危险的自动回退。
