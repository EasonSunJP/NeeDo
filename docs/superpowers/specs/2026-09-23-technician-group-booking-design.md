# Technician service group booking design

## Scope and acceptance

This design applies only to shop visits with selected technicians and supports the shop's existing shop-service or technician-service pricing mode. Restaurant reservations, shop services without a selected technician, home visits, Intelligence campaigns and affiliate checkout keep their current paths. A free, silver or gold customer can submit one guest. An active black diamond customer can submit between one and the smaller of ten and the number of distinct eligible technicians who can complete the selected work at the common start time. The server checks the current tier inside the booking transaction; UI limits are advisory.

A guest is a named participant in the purchaser's booking, not another login identity. Each guest receives at least one technician assignment. Each assignment has one or more ordered services from the shop's active pricing mode. A technician can serve only one guest in the group. A guest may have multiple technicians, whose work starts at the group start time unless the guest explicitly orders successive services from the same technician. All selected technicians belong to the same shop. A group with one guest and one technician remains compatible with today's checkout, including the existing service bundle. Shop and technician pricing rules continue to choose the eligible catalog before booking.

Every assignment creates a real `BookingOrder` with its own slot reservations, snapshots, payment state, history, and refund path. A group record ties orders to guest ordinals and makes a stable idempotent response possible. All group rows, orders, service items, slot reservations, and audit rows are created in one database transaction. Any invalid tier, service, price, availability, slot capacity, conflicting order, or failed write rolls the whole transaction back. On retry, the same idempotency key and fingerprint return the original group; a changed payload conflicts.

After creation, a customer or authorized provider cancels an individual order using the existing order cancellation endpoint. Its slots, payment/refund, audit, and notifications are handled by that order's existing state machine. The group retains the other orders, including other assignments for the same guest. The group projection derives guest and assignment states from orders; it does not keep a competing status field. A group-wide cancel command, if added later, must call the same per-order transition in one transaction.

## User flow

The existing `AvailabilityCalendar` displays a bounded numeric guest selector only for technician-backed bookings in either pricing mode, based on current membership and distinct technicians available at the selected common start. Other store types retain their current people selector. `FormalCheckout` displays one guest card per guest, with technician and service selectors drawn from the existing public pricing navigation and schedule availability. It shows the per-assignment breakdown and exact total before submission. A stale slot or tier change produces an actionable refresh error, never a partial success. After creation, the order page links to the related guest orders and exposes each order's existing cancellation action.

## Server contract and data

Add `POST /bookings/groups` under the existing booking auth/RBAC path and `GET /bookings/groups/:id` scoped to the purchaser or authorized shop/technician/operations identities. Request: `shopId`, `startsAt`, `guests[{label, assignments[{technicianProfileId, serviceIds or technicianServiceIds, scheduleSlotIds, expectedPriceAmountJpy}]}]`, `paymentMethod`, and optional note, plus a required `Idempotency-Key`. `scheduleSlotIds` are ordered for sequential services assigned to one technician. The server rejects duplicate technician assignments, repeated slots, noncontiguous service slots for an assignment, differing first start times, wrong shop, unsupported fulfillment, and mismatched catalog ownership. Price is calculated per assignment from current service price plus the existing nomination fee rule; totals are integer JPY. The response includes group public id and individual order ids, guest ordinals, service snapshots, and totals.

Create `BookingGroup` (`id`, `publicId`, `customerUserId`, `shopId`, `startsAt`, `idempotencyKey`, `requestFingerprint`, timestamps) and `BookingGroupGuest` (`groupId`, `position`, `label`) with unique group/position. Each `BookingOrder` has nullable `bookingGroupGuestId`; one assignment is one order. A group guest can have multiple orders. Migration is additive and leaves existing orders unchanged. The order relation is retained when cancelled or refunded.

## Transaction and conflicts

Lock the purchaser, resolve the authoritative membership entitlement and any active adjustment, then lock shop and technician owners in stable id order. Resolve dynamic selectors inside the same transaction. Re-read the current service, affiliation, location, schedule source, full duration plus buffers, booked count, existing hard locks and exchange participation. Validate selected technicians are distinct and count is at least the number of guests. Do not use the current non-black pending-order replacement behavior for a group: replacement would silently cancel unrelated bookings. Reserve each selected slot with a conditional update. Persist group, guests, orders, service items, status history, location and existing compensation snapshots. The first failed check aborts. Existing independent bookings continue to see each group order as an ordinary technician/customer conflict.

## Impact map

Customer checkout and order detail, technician schedule, merchant orders, and operations order detail are affected by the added group link and per-order visibility. Existing booking auth/RBAC, service/slot validation, payment and refund state machines, status history, ledger and financial reporting remain authoritative per order. Slot occupancy, booking projections, real-time notifications and cache invalidation must run for every created or cancelled order. Dining and home-service paths are confirmed outside scope. Installed PWA and device behavior require separate acceptance evidence.

## Verification

Start with failing validator and transaction tests for membership limits, ten-person cap, duplicate technicians, same-start and full-duration checks, stale price, two concurrent buyers, rollback after a late reservation failure, idempotent replay, and independent cancellation. Then add focused API authorization and frontend interaction tests. Validate the migration against a local database, run focused backend and frontend suites, builds, and real local browser checkout against isolated local data. No staging writes are part of this task.
