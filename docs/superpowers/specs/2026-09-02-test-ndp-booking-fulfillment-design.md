# Test NDP 预约履约闭环设计

## 目标

让 NeeDo 测试账号只使用 `TEST_NDP` 完成一条正式、可审计、可重复验证的预约履约链路：

`客户下单 → 商户/技师接单 → 技师输入服务码开始服务 → 双方处理追加项目 → 结束服务 → 客户使用 Test NDP 结算 → 双向评价`

本微步骤不接第三方支付，不把现金、银行卡或银行转账作为验收条件，也不改变正式账号使用 `NDP` 的生产结算规则。

## 正式数据边界

- 测试账号的活动货币必须由服务端账号分类解析为 `TEST_NDP`，客户端不得自行选择或伪造货币。
- 下单、状态变化、服务会话、追加项目、结算、账本、评价与审计全部写入现有正式 API、Service、Repository 和 MySQL 表。
- Test NDP 扣款只能发生在 `TEST_NDP` 钱包；不得创建或修改正式 `NDP` 钱包余额。
- Test NDP 结算写入测试钱包、交易、流水与审计证据，但不生成生产财务对账记录，也不进入正式财务导出或生产结算。
- 所有测试数据使用唯一标记，并在事务回滚或精确清理后验证零残留。

## 主流程

1. 客户读取已发布服务与可预约排班。
2. 客户选择时段并创建 `PENDING` 预约。
3. 当前店铺作用域的商户或被指派技师确认预约，状态进入 `CONFIRMED`。
4. 系统向客户侧展示服务码；技师必须输入正确服务码才能开始服务。
5. 正确服务码使订单进入 `IN_SERVICE`；错误服务码返回稳定错误且不得产生部分写入。
6. 服务中任一允许方可提出追加项目，另一方接受或拒绝；只有已接受项目计入结算。
7. 存在未处理追加项目时禁止结束服务；全部处理后订单进入 `AWAITING_CHECKOUT`。
8. 客户选择 NDP 支付入口，服务端自动以 `TEST_NDP` 结算并把订单推进到 `COMPLETED`。
9. 客户评价技师、技师评价客户；方向、唯一性、标签规范化和汇总必须正确。

## 异常与并发验收

- 余额不足：返回 `error.wallet.insufficient_available`，订单、钱包、账本、对账和审计无部分写入。
- 重复提交：相同幂等键和相同请求返回原结果；同键不同请求返回 `error.idempotency.key_reused`。
- 错误服务码：不能开始服务，订单与服务会话保持不变。
- 未处理追加项目：不能结束服务，订单和追加项目状态保持不变。
- 排班冲突与容量：重叠排班拒绝；容量 1 只接受一个并发预约，容量 2 接受两个不同客户。
- 接单暂停：暂停期间仍可创建待确认预约，但确认必须被阻止；解除全部有效暂停后才能确认。
- 并发与事务：结算、重复请求和竞争写入必须使用现有锁与事务；失败时恢复完整数据库基线。

## 实现策略

- 复用现有 Booking、Schedule、Order Fulfillment、Ledger、Review API 与状态机，不新增平行 mock 或简化流程。
- 把正式履约检查器的测试客户设为测试账号，并使用合法 NeeDoID；检查器必须断言解析货币为 `TEST_NDP`。
- 修复检查器与当前账号基础表、身份作用域和新增 Repository 接口的兼容问题，但不改变与本目标无关的业务行为。
- 先写或调整会失败的回归测试，确认失败原因后再做最小生产代码或检查器修复。

## 验收证据

- 预约、排班、履约、Test NDP 账本、评价相关单元与 API 测试全部通过。
- 本地 `needo_dev` 的 Test NDP 正式流程检查器退出码为 0，并证明测试前后数据基线一致。
- 前端客户下单/订单详情、商户或技师接单、技师服务码、追加项目、结算和双向评价页面测试通过。
- 当前 main 的 5180/3000 运行时健康；在真实窄屏浏览器中验证三端关键页面、按钮、状态和控制台。
- 验收后不得遗留唯一标记测试账号、店铺、服务、预约、钱包或账本记录。

## 非目标

- 第三方支付、银行卡、银行转账或外部支付回调。
- 生产 NDP 规则重构。
- 预约以外的 Exchange、Affiliate、工资、会员或运营后台扩展。
- 全仓库重构、迁移重写或新增 mock 数据源。
