# Exchange 匹配后双方取消：逐单设计

日期：2026-09-05。

状态：用户已确认推荐的逐单方案；持久化、正式取消 API 与三端页面接入已在独立分支实现并通过隔离验收。两份取消 migration 已应用到本地 `needo_dev`，尚未远程推送或部署。

基线：本地 main `288cf0ec`。联盟营销及其退款、奖励政策继续暂停。

## 已确认的规则与代码事实

1. 匹配成功后必须双方同意才能取消。已入选 claim 不能通过原来的抢单撤回接口撤回。
2. 既有匹配设计规定，双方同意取消时发布费全额转平台收入，不退还发布费；NDP/TEST_NDP 不得混用。
3. 一个匹配结果目前由发布者一次确认，为每位 Participant 原子创建一张独立 `REQUEST/PENDING` 订单。报价、服务、技师和时段快照来自 Participant。
4. 已关联 Exchange Participant 的订单，被普通取消接口保护，返回 `error.exchange.match_cancellation_required`；不能移除该保护后直接复用普通取消按钮。
5. 发布费以 Demand 为单位，`ExchangeRequestFinancial` 和对应 `WalletHold` 目前仍为 `HELD`。`LedgerService.captureExchangeRequestPublication` 已能在传入事务中完成全额扣费、同币种平台入账和重复调用幂等。
6. 订单的 Request 派单费与 Demand 发布费是不同费用。现有 `BookingService.createLedgerSettlementOptions` 对已确认的 Request 取消调用 `releaseBookingHold`；普通 Booking 的商家取消则可能触发顾客补偿。不能把这两类费用和责任含义混为一谈。
7. 当前不存在持久化的“取消申请/对方同意”模型，也没有对应 Exchange API。其他模块的审批表不属于本业务权威。

## 已确认的多人取消范围

### 采用：逐张订单取消

一次取消申请绑定一张订单及其 Participant，由该订单顾客与服务承接方完成同意。其他入选服务者的订单、时段和履约继续保持原状。

例如三位技师中的一位无法服务，经双方同意仅取消这一单。此方案与目前“一位服务者一张订单”的接单、履约和评价边界一致。

### 不采用：整批取消

一次申请绑定整个 Matching，必须记录发布者及全部服务承接方的决定。只有所有要求的同意均满足后，才原子取消整批订单；任一方拒绝则不能完成整批取消。

此方案适合多人必须共同完成的服务，但需要定义部分订单已开始或已完成时的处理方式，不能套用逐单批准模型。

用户在推荐逐单取消的确认问题后回复“ok”。因此活动申请按订单唯一，批准来自该订单另一方，不等待其他 Participant。

## 逐单方案的具体建议

以下内容按已确认的逐单推荐方案实施。

### 第一功能版本的范围（由多个独立微步骤交付）

- 仅处理已创建正式订单、尚未开始服务、尚未确认收款的 Exchange `PENDING/CONFIRMED` 订单。
- 匹配后尚未创建订单的取消、服务中止、完单后退款、支付退款和责任处罚另行处理。
- 发起、拒绝、撤回申请均不改变订单状态、时段容量或钱包。
- 对方同意时，在一个事务中执行批准、订单取消、释放对应时段、处理适用的已冻结费用、状态历史、通知和审计；任一环节失败全部回滚。

### 申请和权限

- 一张订单同时最多一个待答复申请；发起人可以撤回，另一方可以同意或拒绝。
- 服务端根据登录身份、订单顾客、Participant、当前技师和有效店铺管理作用域确定双方。客户端不能提交任意操作人或批准人 ID。
- 店铺代理技师操作继续遵守现有店铺管理权限和有效归属关系；同一服务方的另一个操作员不构成“另一方”。
- 每次命令使用幂等键和预期版本。同键同载荷返回同一结果，同键异载荷、过期版本和已经失效的申请均不执行重复副作用。
- 不把未回复或超时当成同意；不同意时订单继续有效。
- 同意前重新检查订单状态和付款状态。订单已开始、已完成或收款状态不符合范围时，不得通过旧申请取消。

### 费用边界

- Demand 发布费只扣一次，不能每取消一位服务者就重复扣整笔费用。
- 在该 Demand 第一次双方同意取消时，按既有“同意取消时全额收取”规则结算发布费。其他订单仍继续履约；后续取消或完单复用已结算事实。
- 第一实施微步骤不自创商户责任赔偿或奖励追回规则；已确认 Request 的派单费冻结按现有正式 Request 取消逻辑处理。
- 不等待同一 Demand 的全部订单结束，也不改变其他订单的接单、履约和费用规则。

### 数据和事务设计

- 取消申请保存订单/Participant、发起身份及一方类型、原因、待答复/同意/拒绝/撤回状态、版本及时间。
- 保留申请历史和追加事件，不删除原始入选事实、订单关系或原报价。
- 活动申请唯一约束、外键、索引、状态约束使用前向 migration；不改历史 migration。
- 接单、开始服务、确认收款与同意取消必须使用兼容的订单行锁及条件更新，确保竞争时最多一个有效状态转换。
- 重复批准不重复释放 `bookedCount`、不重复结算发布费或派单费、不重复发送业务通知。
- 公开列表不扩大地址及身份隐私；只有订单双方能读取取消原因和决定记录。

### 前端与验收

- 沿用现有 Exchange 详情和正式订单详情；显示“申请取消/等待对方答复/同意/拒绝/撤回申请”的实际服务器状态。
- 同意前明确展示影响范围及费用；用户输入的原因保持原文，系统文案补齐五种语言。
- 单元及 API 测试覆盖双方权限、越权、自我批准、重复提交、过期版本、拒绝和撤回零财务写入。
- 真实本地数据库检查覆盖容量守恒、费用守恒、同意/接单/开始服务/收款竞争、故障回滚与幂等。
- 真实顾客与服务方浏览器覆盖刷新持久化、错误重试和 320/440 像素布局。

## 当前交付与实施门禁

1. 规则层已完成：无副作用的领域状态判定与严格命令校验，独立提交 `5582c619`。
2. 持久化基础已完成：取消申请/事件 Prisma 模型、前向 migration、数据库 CHECK/FK/唯一键约束，以及独立 MySQL 8.0.46 实例的 34 项约束检查。两份取消 migration 已应用到本地 `needo_dev`；没有应用到线上。
3. API 微步骤已实现：五个受 JWT/RBAC 保护的读写端点、严格请求校验、服务端身份/店铺/技师作用域判定、事件幂等重放、行锁内批准，以及订单/时段/发布费/已确认 Request hold/历史/通知/审计的同事务处理。
4. 前端接入微步骤已实现：共享面板读取实际服务器状态，以 `expectedVersion` 和稳定幂等键执行申请、同意、拒绝、撤回；已复用到双方 Exchange 卡片以及顾客、技师、店铺正式订单详情。普通订单只有在取消端点返回精确 404 后继续显示既有普通取消操作；已识别的 Exchange 订单不会再触发通用取消接口。系统文案提供五种语言，用户原因保持原文。
5. 隔离 MySQL 门禁已完成：一次性数据库从零应用 130 个前向 migration；8 个真实 MySQL 场景覆盖双订单并发取消与发布费守恒、取消同确认/开工/收款竞争、活动申请唯一、事务故障回滚、拒绝/撤回财务中性，以及已确认 Request hold 释放并保留已结算发布费。测试后删除专用数据库和账号并验证 `existingDatabaseModified=false`；该 checker 未修改 `needo_dev`。
6. 浏览器门禁已完成：从本地正式数据克隆隔离验收库，并在副本中补全当前 main 所需的所有 migration。真实顾客依次申请→撤回、再申请→技师拒绝、再申请→技师同意；顾客、技师和商户端刷新后均读到最终接受状态。验收覆盖 320/440 像素、普通订单回退、无横向溢出及无未豁免应用错误。隔离库最终证据为 `orderStatus=cancelled`、`cancellation.status=accepted`、时段容量释放、六条追加事件、审计/通知持久化；验收后隔离库及专用授权已清理。
7. `needo_dev` 边界：两份取消 migration 已应用，但浏览器验收未修改其订单、时段、权限或钱包数据。合并进入的 travel fare 代码还有一份无关 migration 未在 `needo_dev` 应用，所以本轮不把该库上的当前 main 标准端口运行视为通过。
8. 待部署门禁：远程推送、获准环境 migration、发布及发布后 smoke/登录验收。本地实现与隔离验证不代表已部署。

前端源码已经开放由正式 API 状态控制的取消操作。本地 `needo_dev` 只应用了本功能的两份前向 migration，未写入验收业务数据；可写浏览器证据发生在可清理的隔离副本。因此可以宣称本地功能实现和隔离验收完成，但在获准环境完成远程推送、migration、发布与 smoke 之前，不得宣称线上功能已正式可用。
