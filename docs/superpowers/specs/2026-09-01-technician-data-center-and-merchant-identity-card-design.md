# 技师数据中心、预约详情与商户独立信息卡设计

日期：2026-09-01
状态：用户已确认

## 1. 目标

本次工作以正式 API、正式数据库、身份隔离、RBAC 与审计为前提，完成四个连续微步骤：

1. 修复技师信息卡在合法空字段状态下无法保存的问题。
2. 将服务完成分成、加钟分成与指名费建模为可独立配置、可版本化并可结算的正式薪酬字段。
3. 完成技师数据中心、双曲线趋势、最近三条正式订单、既有预约详情补全和期限联动排班入口。
4. 为商户身份新增独立个人信息卡，并统一技师端、商户端个人中心头部结构。

禁止新增 mock、静态统计、浏览器业务存储或 fake-success；旧数据缺少可证明的财务拆分时必须显示明确状态，不进行推测。

## 2. 身份与数据归属

三种信息卡可以复用纯展示组件，但不得共享数据记录、编辑状态或写接口：

- 用户端继续使用 `CustomerProfile` 与用户自资料 API。
- 技师端继续使用 `TechnicianProfile` 与技师自资料 API。
- 商户端新增 `MerchantIdentityProfile`，一对一关联当前 `UserIdentity`，通过商户自资料 API 读写。

`MerchantIdentityProfile` 保存商户身份个人头像、显示名称、性别、年龄、身高、语言、自我介绍和隐私范围。店铺名称、门店图片、地址、服务、菜单及经营设置继续归 `Shop`，只由“服务展示”及现有店铺设置入口维护。

身份切换后必须按新的 `currentIdentityId` 重新加载资料。通讯录、IM、Social、日程、订单、技师服务和店铺经营等现有身份内关联不改变。

## 3. 技师信息卡保存修复

当前正式数据库允许技师资料的语言、服务区域或支付方式为空，但 PATCH 校验对这些数组使用了最少一项限制。前端保存未修改的合法空数组时因此收到 `error.validation`。

正式契约统一允许这些可选集合为空；仍对数组长度上限、单项长度、枚举值和预算上下限进行严格校验。错误响应由前端映射为具体、可读的字段提示。更新继续通过当前技师身份 scope，并记录 `technician_profile.self_update` 审计日志。

## 4. 薪酬模型与历史版本

保留现有 `commissionRateBps` 作为“服务完成分成比例”的正式语义，新增：

- `extensionCommissionRateBps`：加钟金额分成比例。
- `nominationFeeJpy`：每笔明确指名该技师的固定指名费。

字段同时存在于店铺默认 `ShopFinanceRuleSet` 和技师覆盖 `TechnicianCompensationProfile`。既有记录迁移时将 `extensionCommissionRateBps` 回填为当前服务分成比例，以保持升级前结算结果；`nominationFeeJpy` 回填为 0，不凭空创建指名费用。

订单财务快照需要区分：

- 基础服务金额。
- 加钟金额。
- 指名状态及适用指名费。

补偿引擎按基础服务金额计算服务分成、按加钟金额计算加钟分成，并在订单具有正式指名快照时加入指名费。薪酬预览、订单财务时间线、工资单和导出使用订单当时的版本快照，修改当前方案不得倒改历史订单。

若旧订单只有合计服务金额且没有可证明的拆分，继续使用旧版本结果并标记为旧口径，不拆分出虚构加钟或指名数据。

## 5. 技师数据中心

新增当前技师身份限定的正式数据中心接口。请求接受 `period`，可选值：

- `last7days`：最近 7 个东京自然日，每日一个节点。
- `last30days`：最近 30 个东京自然日，每 5 日一个节点。
- `week`：东京时区本周，每日一个节点。
- `month`：东京时区本月，按被月边界裁切的自然周分桶。
- `year`：东京时区本年，每月一个节点。

接口一次返回同一时间桶中的收入与工作时长，避免前端分别请求造成横轴错位。收入只来自可审计的正式订单财务/薪酬结果；工作时长来自正式服务时间。响应还包含当前有效收入模型、汇总数据、下一条安排和最近三条正式订单。

前端呈现一张双曲线图：

- 收入趋势使用左侧日元刻度。
- 工作趋势使用右侧小时刻度。
- 两条曲线共用时间轴。
- 图表下方的两个图例按钮可独立隐藏或恢复对应曲线。

页面顶部不显示基础工资标签，只显示“收入模型详情”小按钮。详情面板显示：店铺关系、入社日期、版本更新时间、基础工资、服务完成分成、加钟分成、指名费和奖金状态。无店铺或无有效版本时显示正式空状态。

## 6. 最近订单、预约详情与排班期限

数据中心仅显示最近三条正式订单。整张订单卡跳转到既有 `/technician/orders/:orderId`，不新增平行详情路由。

现有预约详情需要复用正式订单资源并补全为批准的详情结构：

- 统一个人端详情头部。
- 动态状态步骤。
- 服务卡。
- 金额、支付方式与来源。
- 店铺与服务方信息。
- 当前状态允许的确认、开始、完成或取消操作。

缺失展示字段必须扩展正式订单详情 DTO；无法证明的数据隐藏或显示“未提供”，不得使用静态卡片。

数据中心跳转订单详情时携带当前 `period`、已解析 `from`/`to`、返回地址和图例可见状态。返回数据中心后恢复期间、图例和滚动位置。

数据中心底部固定“确认详细排班记录”按钮，位于底部导航区域。跳转 `/technician/schedule` 时携带 `period`、`from`、`to` 和锚点日期。排班页面读取这些参数并展示相同日期边界，不静默重置到今天；从订单详情进入排班时沿用相同参数。

## 7. 技师与商户个人中心头部

技师端与商户端个人中心均使用共享 `MobileFullscreenHeader` 视觉网格：

- 左侧返回按钮。
- 中间标题“个人中心”。
- 右侧设置按钮。
- 同一头部容器下方保留插页切换。

技师端插页为“信息卡／服务信息／数据中心”。商户端插页为“信息卡／服务展示／数据中心”。

商户“信息卡”使用用户端相同的卡片布局、头像裁剪、编辑模式、隐私选择和固定保存体验，但通过独立商户资料 API 持久化。“服务展示”继续维护 `Shop`；“数据中心”继续承载店铺经营能力。商户底部导航、店铺切换、设置路径和其他身份内功能保持不变。

## 8. API、权限与审计

新增或扩展的正式接口全部使用 `/api/v1/`、Zod、OpenAPI、认证与权限声明：

- `GET/PATCH /api/v1/merchant-profile/me`
- `GET /api/v1/technician/data-center`
- 既有技师自资料 PATCH 合法空集合契约
- 既有薪酬方案读写与预览字段
- 既有订单详情必要的正式投影字段

商户资料只允许 `currentIdentityType=merchant` 且当前 identity scope 匹配的主体读写。技师数据中心只允许当前技师身份读取。资料更新、薪酬变更和财务拆分均记录 changed-fields 与主体 ID，不把密码、令牌或敏感内容写入审计元数据。

列表仍分页；数据中心最近订单在服务端固定限制为 3，同时返回完整订单入口所需公开 ID。

## 9. 状态、错误与可访问性

- 加载、无数据、无关联店铺、无薪酬版本、无权限和服务错误分别展示。
- 期间切换取消或忽略旧请求，防止旧响应覆盖新状态。
- 图例按钮使用可访问的按下状态并可键盘操作。
- 所有新增用户可见文字补齐现有多语言。
- 不把原生异常、Zod 结构或内部 ID 直接展示给用户。
