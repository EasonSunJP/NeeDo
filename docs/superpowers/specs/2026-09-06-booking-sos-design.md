# 预约 SOS 与后台统一工具栏设计

日期：2026-09-06。状态：用户已确认方案；同日按用户追加要求取消服务时间限制。本地代码与数据库已实施，验收记录见 `docs/qa/2026-09-06-booking-sos.md`。

## 用户需求

用户端、技师端预约详情始终显示 SOS，不判断是否开始服务或结束多久。点击后点亮商户端和运营后台的求救通知入口，入口打开求救列表。两端后台右上角功能按钮统一位置和设计。截图仅作为按钮位置、颜色和视觉参考；业务规则以用户文字要求及追加修改为准。

## 实施前基线

- 技术栈为 React / TSX / Vite，正式 API 为 Express / Prisma / MySQL。
- 用户预约详情在 `src/pages/user/UserOrderDetailPage.tsx`；技师正式预约详情在 `src/features/technician-schedule/route-pages.tsx`。
- 运营 `AdminLayout.tsx` 的求救入口目前是固定红色链接，指向 `/admin/reviews?module=sos`。尚无正式 SOS 表和 API。
- 商户 `MerchantAdminLayout.tsx` 的通知按钮尚未绑定点击行为；工具栏顺序与运营端不同。
- 现有 SSE 网关支持按 `recipientIdentityId` 分发，可复用，并以数据库作为列表和计数的事实来源。
- 工作区已有大量其他任务的未提交修改，含运营布局、预约 repository、Prisma schema、路由和翻译。后续实施必须隔离或逐块保护这些修改，不能覆盖、回退或一并提交。

## 方案比较

1. 推荐：独立、持久化的求救记录，复用现有 SSE 和后台布局能力。能独立表示待处理状态、做订单权限隔离和审计，改动限于 SOS 闭环。
2. 复用普通 Notification：表面改动少，但个人已读与求救已处理语义不同，多人接收易发生计数和状态混淆，仍需新增业务记录。
3. 扩展完整客服工单：可覆盖后续分派、升级和 SLA，但超出本次按钮、列表与状态提醒的范围。

按 Step 13 的单一 SOS 闭环微步骤实施，不修改预约或财务状态机；顶部工具栏统一是该入口接入的一部分。

## 显示与发送行为

- 预约详情加载成功且当前用户/技师具备正式发送权限时，SOS 始终可见。未开始、已取消、已完成、没有实际服务会话或结束已超过 10 分钟，均不限制发送。
- 状态请求只同步当前待处理求救，不决定按钮可见性。请求失败仍保留 SOS，发送由正式接口再次校验权限与归属。
- availability 保留响应结构：授权与归属校验成功后 `canSend:true`、`expiresAt:null`，`serverNow` 为服务端时间。
- SOS 位于现有详情头部右侧、关闭按钮左侧，保持现有头部高度与对齐。两类身份复用相同组件。
- 用户补充的 `codex-clipboard-ca50c629-40e0-4f3b-b243-5138fc90af42.png` 是用户/技师 SOS 按钮的明确视觉依据：横向胶囊形，约 80 × 48 的视觉比例，顶部深红至底部亮红渐变、白色粗体圆润 `SOS` 字样，不带警告图标。按共享头部实际尺寸适配并保持足够点击面积；不把参考图背景裁进按钮，不改变头部主题。后台“求救通知”仍采用前一张参考图的警告图标加文字设计。
- 单击立即发送，不增加二次弹窗或长按步骤。发送中避免重复点击，提交成功显示“求救已发送”；失败提供明确错误与重试。
- 客户只能为自己的预约发送；技师只能为当前正式分配给自己的预约发送，服务端同时核对当前身份和权限。
- 每个预约、每个发起身份最多一条当前待处理求救；并发点击合并。网络不确定失败重试复用幂等键，不能重复落库。已处理后允许再次求救并生成新记录。
- 不自动启动定位、联系紧急联系人、打电话或宣称接收方已经阅读。

## 接收、列表和点亮规则

- 订单所属商户范围内、有 SOS 读取权限的有效商户身份接收；有 SOS 读取权限且作用域覆盖该订单的运营身份接收。
- 所有查询、计数、处理 API 都在服务端校验身份、RBAC 和店铺范围；不向其他店铺广播订单或发起人资料。
- 持久化成功后发送轻量 SSE 失效提示，两端重新读取求救计数与列表。初次加载、重连、返回前台和定期补偿刷新均查询正式 API，以覆盖事件遗漏。
- 有待处理求救时，入口红底白字并显示待处理数量；没有待处理求救时，入口保持普通工具按钮样式，仍可查看历史。
- 点击入口打开共用的求救列表抽屉：新记录优先，支持待处理/已处理筛选和服务端分页；显示求救时间、发起人及用户/技师身份、预约号、服务、店铺和处理状态。
- 打开列表不改变求救状态；有处理权限的人员可显式标记“已处理”，记录处理者、身份、时间及审计。商户与运营共用该业务状态并实时刷新。多次处理请求幂等，只有最后一条待处理记录处理完成后入口熄灭。
- 查询失败显示重试和连接异常，不能显示假“0 条”；切换身份时清除旧范围数据并重新加载。

## 后台工具栏

- 抽取共享 `BackofficeHeaderActions`，固定右上方顺序：求救通知 → 语言 → UI 主题 → 消息 → 客服。
- SOS 常态与其他按钮共用高度、圆角、边框、间距和焦点样式；激活态沿用截图红色警告图标与文字。
- 语言、主题继续复用现有控件；消息、客服指向各端已有的真实功能，实施时核实商户路由与身份守卫，不新增无效按钮。
- 商户现有设置入口仍可从设置导航进入；运营独有的数据大屏保留原有导航职责。
- 窄屏缩减文字、保留可访问标签及按钮顺序，SOS 入口不得因现有 `xl` 断点而消失。
- 深浅主题都保持可读；新增业务文案补齐现有五语言支持。

## 正式数据与 API 边界

- 独立 SOS 模块保持 Route → Controller → Service → Repository 分层。
- 新增求救记录及幂等存储，包含预约、店铺、发起用户/身份、状态、处理用户/身份/时间，标准创建/更新/软删除字段与关联索引。数据库约束和事务保证并发重复提交、待处理记录唯一性与审计原子性。
- 新增 migration 包含数据结构和部署所需权限更新；不能只改 seed，也不修改已经应用的 migration。
- 拟定 API：`GET /api/v1/bookings/:orderId/sos-availability`、`POST /api/v1/bookings/:orderId/sos`、`GET /api/v1/sos-alerts`、`GET /api/v1/sos-alerts/count`、`POST /api/v1/sos-alerts/:alertId/resolve`。
- 参数与请求体使用 Zod，响应保持现有 envelope，列表有分页上限，OpenAPI 与角色权限同时补齐。
- SSE 只作为刷新提示，数据库保存记录及待处理状态。若推送失败但事务已经成功，响应仍准确说明求救已提交；重连及补偿刷新恢复提示。

## 验收与实施顺序

1. 先写失败测试：未开始、取消、已完成、缺失服务会话及结束很久仍可发送；按钮不因旧截止时间或状态接口失败消失。
2. 实现最小数据库/权限/API；测试本人/指派技师权限、跨商户 403/404、并发重复发送、失败回滚、处理审计和幂等重试。
3. 接入用户/技师按钮和共用后台工具栏、列表；验证发送错误、列表错误、处理中、断线重连、切换身份与多端同步。
4. 本地隔离 MySQL 事务验收写入和清理；验证真实登录的用户及技师各发起一次、正确商户和运营接收、其他商户不可见。
5. 在真实浏览器验证手机详情与桌面两端工具栏，检查深浅主题、窄屏、固定头部、列表分页和已处理后熄灭。
6. 运行相关测试、lint、build，更新正式 API/实时能力文档；报告本地验证结果。远程推送、部署、线上 migration 和 staging 验收作为独立动作记录，不以本地结果代替。

## 最终产品语义

“点亮”表示存在待处理求救，只有显式“已处理”解除提醒；打开列表不会消除提醒。用户在实施中明确取消原定服务起止加 10 分钟限制，最终代码、数据库验收与界面测试均使用始终可发送规则。
