# NeeDo 正式版前后端数据打通设计规格

## 1. 文件状态

- 日期：2026-08-24
- 状态：实施基线
- 目标：在保留现有 React / TypeScript / Vite 多端前端与 Express / Prisma 后端的前提下，逐步移除生产路径中的 mock、localStorage 业务状态与静态兼容接口，形成可部署、可审计、可测试、可回滚的正式业务系统。
- 用户授权：按核心交易闭环优先的纵向路径持续推进，不再逐段暂停确认。
- 首期支付：不接外部支付 API；支持到店／线下支付、银行转账及运营人工确认。NDP 使用真实账本，充值、提现先由运营人工审核。
- 首期认证：邮箱＋密码；用户可注册，技师需店铺或运营审核，店铺账号由运营创建，运营账号由超级管理员创建。短信 OTP 暂不开放。
- 模拟数据：前后端打通后，仅在本地／测试环境生成 10 个店铺、100 个技师、100 个用户与连续 3 个月业务数据，并导出 CSV 与 XLSX 账号清单。

## 2. 设计原则

1. 一次只完成一个可运行、可测试、可回滚的微步骤。
2. 不推倒现有前端，不删除现有路由、主题、三端入口或已实现的正式 API。
3. 正式页面只通过 `/api/v1/` 读取和修改业务数据；MySQL 是唯一事实源。
4. Redis 只承担会话、Token 撤销、限流、缓存和实时事件辅助职责，不作为永久业务事实源。
5. 生产构建不得包含 demo seed、测试账号、静态登录、前端业务 mock 或假成功响应。
6. 外部付费能力没有正式凭证时必须返回明确的“未配置”状态，不能伪造调用成功。
7. 所有写操作都必须经过 Zod、鉴权、RBAC、Service、Repository、事务与必要的审计日志。
8. 所有列表接口分页，所有删除软删除，所有时间以 UTC 存储并以 ISO 8601 输出。
9. 每个纵向闭环先补契约与失败测试，再实现后端，再接前端，最后做真实运行验证。

## 3. 范围

### 3.1 首期核心交易正式版

- 用户、身份、角色、权限、会话与邮箱密码注册／登录。
- 店铺入驻、店铺账号、技师申请／审核、技师与店铺归属。
- 服务项目、技师服务、定价模式、可预约时间与排班。
- 预约创建、确认、开始服务、完成、取消与状态历史。
- 线下支付／银行转账的收款确认、退款标记、NDP 冻结／解冻／结算。
- 运营后台和店铺后台的真实仪表盘、列表、详情与操作。
- 用户端和技师端核心预约、订单、排班页面的数据打通。

### 3.2 第二批实时能力

- IM 会话、成员、消息、联系人、好友申请。
- Social 动态、关注、互动和通知。
- SSE 事件订阅、断线重连和基于游标的遗漏数据补取。

### 3.3 生产化与测试数据

- 环境隔离、生产构建保护、数据库迁移、备份恢复、日志、指标、限流与健康检查。
- 本地／测试环境的三个月一致性模拟数据。
- 模拟账号 CSV 与 XLSX 清单。
- 预发布端到端验收、生产部署清单和回滚演练。

### 3.4 暂缓范围

- 地图、路线导航、eKYC、短信 OTP 与外部在线支付。
- 暂缓能力保留正式 adapter 契约、配置检查与可观测错误，不实现 fake provider。

## 4. 总体架构

```text
用户端 / 技师端 / 店铺后台 / 运营后台
                  ↓
      统一 httpClient + Auth/RBAC Guard
                  ↓
       Nginx /api/v1 与 SSE 反向代理
                  ↓
       Express Route + Zod Validator
                  ↓
 Controller → Service → Repository
                  ↓
         Prisma / MySQL + Redis
                  ↓
       审计日志 / 指标 / 结构化日志
```

### 4.1 前端边界

- `src/api/httpClient.ts` 继续作为唯一 HTTP 基础设施，负责 JSON、Token、刷新、超时、取消、统一错误与请求标识。
- 每个业务域提供 typed API adapter；页面不得直接拼接 URL 或直接读取 mock 模块。
- React 组件只负责展示、输入与交互；数据加载、缓存失效、状态转换集中在域 adapter/hook/store。
- localStorage 仅允许保存语言、主题及非敏感 UI 偏好。Token 和任何涉及安全的长期存储策略必须单独审查；业务实体不得以 localStorage 为主数据源。
- 生产构建通过显式环境守卫阻止静态 demo 与 legacy fake auth 被打包到正式入口。

### 4.2 后端边界

- Route 只注册 path、validator、authenticate、authorize 和 controller。
- Controller 只做 req/res 映射。
- Service 处理业务规则、事务、状态机、幂等与审计。
- Repository 只通过 Prisma 做数据访问。
- 对外统一返回 `{ code, message, data }`；Node/Prisma 原生异常不得泄露。
- 所有状态变更带 actor、目标、前后状态、requestId 与必要 metadata。

## 5. 环境隔离与生产保护

| 环境 | 数据 | 模拟种子 | 调试入口 | 外部服务 |
|---|---|---|---|---|
| local | 本机数据库 | 允许，需显式开关 | 允许 | disabled/test adapter |
| test | 临时数据库 | 测试 fixture | 禁止人工入口 | deterministic test adapter |
| staging | 独立数据库 | 允许受控业务种子 | 禁止 | sandbox/disabled |
| production | 全新生产数据库 | 强制拒绝 | 强制拒绝 | 仅正式配置 |

生产保护规则：

- `NODE_ENV=production` 时，任何 demo seed、测试登录、静态 demo 或 mock 安装调用立即失败并退出。
- 模拟种子还需 `ALLOW_SIMULATION_SEED=true`，并校验数据库名／连接标签不是生产。
- 生产只创建首个超级管理员；密码通过部署时安全输入或 Secret 注入，不写入仓库。
- `.env.*` 不提交密钥；启动时对必需配置做 Zod 校验。

## 6. 身份、账号与审核

### 6.1 注册和创建

- 用户：`POST /api/v1/auth/register`，邮箱唯一、密码 bcrypt rounds ≥ 12，默认 customer identity。
- 技师：注册后建立待审核 technician profile；审核通过前不能接单或发布服务。
- 店铺：运营审核资料后创建 shop、owner identity 与 merchant role；不允许公开接口直接创建已发布店铺。
- 运营：只有超级管理员可创建或授予运营角色。

### 6.2 登录和会话

- Access Token ≤ 15 分钟，Refresh Token ≤ 7 天并存 Redis。
- 刷新 Token 轮换；注销时撤销 Refresh Token 并将 Access Token 加入黑名单。
- 登录失败按 IP＋账号限流并记录 LoginLog。
- `/auth/me` 是当前身份、角色、权限和菜单的唯一来源。
- 未配置短信服务时，OTP 端点返回明确的 provider unavailable，不在生产日志输出验证码。

## 7. 核心业务数据与状态机

### 7.1 店铺、技师和服务

- Shop 保存 owner、状态、地址、定价模式和审核状态。
- TechnicianProfile 绑定真实 User，并通过 shopId 表示当前店铺归属。
- Service 表示店铺服务；TechnicianService 表示技师可提供的服务、个人价格和审核状态。
- 店铺可管理自己的技师、服务、排班和订单；运营可跨店查看并执行受审计的管理动作。

### 7.2 排班

- Availability 表示周期或日期可用规则，ScheduleSlot 表示可预约的具体时段。
- 排班写入必须检测同一技师时间重叠。
- 预约确认时使用数据库事务锁定 slot；成功后从 AVAILABLE 变为 BOOKED。
- 取消或拒绝后按规则恢复 AVAILABLE；人工封锁使用 BLOCKED。
- 前端日历只读写真实排班 API，不再由浏览器本地数组计算最终状态。

### 7.3 预约与订单

允许状态转换：

```text
PENDING → CONFIRMED → IN_SERVICE → COMPLETED
    └──────────────→ CANCELLED
CONFIRMED ─────────→ CANCELLED
```

- 创建预约：验证用户、店铺、服务、技师、价格快照与 slot 可用性。
- 确认预约：锁定 slot，写状态历史，创建必要的钱包冻结或线下支付待确认记录。
- 开始服务：仅订单所属技师／店铺或有权限的运营可执行。
- 完成服务：幂等写入完成状态、结算、账本及通知。
- 取消：依据当前状态、操作者和取消方执行解冻、补偿或退款标记。
- 每个状态变更必须写 OrderStatusHistory 和 AuditLog。

### 7.4 支付、NDP 与结算

- 首期支付方式：`onsite` 与 `bank_transfer`。
- 外部在线支付未配置时不能创建“已支付”的第三方交易。
- 收款由店铺或运营确认，记录确认人、时间、金额、方式和备注。
- 充值、提现采用申请→运营审核→账本入账／拒绝的流程。
- NDP 只通过 LedgerService 写入；余额由不可变分录计算，不允许直接改余额。
- 预约冻结、取消解冻、完成结算使用幂等键，重试不得重复扣款或入账。

## 8. 后台与端侧数据打通

### 8.1 运营后台

- 仪表盘、店铺、技师、用户、订单、排班、财务与审核优先切换为真实 API。
- 每个列表统一支持分页、搜索、筛选、排序和加载／空／失败状态。
- 详情抽屉集中展示关联账号、身份、店铺、技师、订单、排班、账本和审计信息，减少跨页重复搜索。
- 分析、营销、库存、装修等外围模块没有正式后端前，不在生产展示假数据；按“未启用”或权限隐藏处理。

### 8.2 店铺后台

- 当前店铺由 `/auth/me` 的 identity scope 决定，不从前端硬编码 shopId。
- 店铺只能访问自身技师、服务、订单、排班、财务和设置。
- 人员、分析、设置及运营工作台逐步移除 `merchantAdminDemo` 与通用 mock 导入。

### 8.3 用户端与技师端

- 用户预约、订单历史、状态与取消操作使用真实 booking API。
- 技师排班、待处理预约、服务进行中和完成操作使用真实 API。
- 页面路由由权限守卫约束；前端隐藏按钮不能代替后端权限校验。

## 9. IM、Social 与通知

- 以现有 Step 13 数据表和 API 为基础，替换 IM 的浏览器 mock database 与 Social localStorage context。
- 列表初次加载使用 REST；新增消息、好友状态、动态和通知使用 SSE。
- SSE 使用 `Last-Event-ID` 或显式 cursor 重连；事件仅提示“哪些数据变化”，前端再按权限刷新正式资源。
- 会话成员、动态可见性和通知读取都在后端做 scope 校验。
- 图片／文件上传在未建立正式对象存储前保持不可用状态，不以 base64/localStorage 冒充正式上传。

## 10. 外部服务暂缓策略

建立统一 capability 状态：

```ts
type IntegrationStatus = "enabled" | "disabled" | "misconfigured";
```

- 地图／导航：保留经纬度与地址字段；页面可显示文本地址，不调用收费路线服务。
- eKYC：保留审核状态与 provider reference 边界；未配置时只允许人工审核。
- 短信：OTP 端点返回 `error.auth.provider_unavailable`；邮箱密码不受影响。
- 在线支付：仅线下／转账和人工确认可用；第三方支付按钮隐藏或显示未启用。

## 11. 三个月模拟数据

### 11.1 规模

- 10 个店铺，每店 10 个技师，共 100 个技师。
- 100 个用户。
- 至少 3 类服务，覆盖不同价格和时长。
- 连续 3 个自然月的 Availability、ScheduleSlot、BookingOrder、OrderStatusHistory、支付确认、Wallet、Ledger、通知数据。

### 11.2 分布与一致性

- 完成、取消、待确认、已确认、服务中等状态采用可配置且可重复的确定性分布。
- 所有完成订单具备完整状态历史、价格快照、支付／账本与排班占用。
- 所有取消订单遵守允许的状态转换，并正确恢复时段或写补偿。
- 数据生成使用固定 seed，重复运行可幂等更新或先拒绝，不能产生重复账号与重复订单。
- 生成结束运行一致性检查：用户／技师／店铺数量、重叠排班、孤儿记录、订单状态历史、钱包平衡和权限范围。

### 11.3 账号导出

- 输出 `simulation-accounts.csv` 与 `simulation-accounts.xlsx`。
- 字段：account_type、email、password、display_name、shop_name、status、notes。
- 每个模拟账号使用唯一可追踪密码；清单只写入受忽略的输出目录，不加入 Git。
- 正式生产密码和正式用户密码绝不导出。

### 11.4 2026-08-25 本地实现结果

- 独立命名空间 `needo_three_month_v1` 已实现，账号使用 `sim.*@needo.local`，订单使用 `SIM3M-`。
- 当前确定性结果：10 店铺、100 技师、100 用户、30 服务、2,600 排班、1,801 订单。
- 订单状态分布：完成 1,214、取消 487、服务中 33、待确认 50、已确认 17。
- 已写入 6,013 条状态历史、1,214 条完成订单财务记录、100 个用户钱包与种子账本、1,801 条订单通知。
- 重复执行后上述数量不翻倍，100 个钱包仍各为 5,000 NDP，账本交易与分录仍各 100 条。
- 账号 CSV/XLSX 共 210 个账号，每个密码唯一；输出目录已加入 `.gitignore`。

## 12. 错误、幂等与并发

- 统一错误分类：validation、unauthenticated、forbidden、not_found、conflict、provider_unavailable、rate_limited、internal。
- 前端根据稳定 error key 显示三语言文案，不显示堆栈或数据库错误。
- 创建预约、确认、完成、取消、充值审核、提现审核与结算使用幂等键。
- slot 预约、钱包与状态转换在 Prisma 事务内完成，并对冲突返回 409。
- 所有 API 记录 requestId；敏感字段、Token、OTP、密码和完整财务凭证不得进入日志。

## 13. 安全与可观测性

- Helmet、严格 CORS、登录和高风险写接口限流。
- RBAC 默认拒绝；店铺和技师在 Repository 查询层追加 scope 条件。
- 关键管理、订单、账本和审核操作写审计日志。
- `/health` 仅表示进程，`/ready` 检查数据库和 Redis；生产 API 根路径 404 不作为健康失败。
- 指标覆盖请求延迟／错误率、数据库池、Redis、登录失败、预约冲突、SSE 连接和账本失败。
- 日志为结构化 JSON；生产关闭 debug 日志。

### 14.1 自动化

- 后端 Service 单元测试、Repository 测试、Supertest API 集成测试。
- 前端 API adapter、权限守卫、关键页面状态和错误分支测试。
- 状态机、并发预约、幂等重试、越权访问、账本平衡与模拟数据一致性测试。
- OpenAPI 与路由契约同步测试。
- 前后端 lint、test、build 全部通过。

### 14.2 真实运行验收

1. 新用户注册并登录。
2. 运营创建店铺账号并审核技师。
3. 店铺创建服务和排班。
4. 用户预约，店铺／技师确认并开始服务。
5. 完成订单并确认线下支付，核对账本和后台统计。

7. 跨角色越权请求全部被拒绝。
8. 断开并恢复 SSE 后，无消息或通知遗漏。

10. 预发布环境完成备份、迁移、部署和回滚演练。

4. 排班真实数据闭环。
5. 预约状态机与人工支付／NDP 闭环。
6. 运营、店铺、用户和技师端核心页面去 mock。
