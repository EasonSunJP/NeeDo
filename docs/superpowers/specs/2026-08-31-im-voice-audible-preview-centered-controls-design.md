# IM 语音可听回放与居中控制设计

## 目标

修复用户端、技师端和商户端共用聊天录音浮层中“回放进度正常推进但没有声音”的问题，并把录音与预览操作按钮从画面底部移到画面中部，按钮尺寸放大为当前的 1.5 倍。

本次是 Step 13 的前端录音与试听加固微步骤。沿用现有正式语音消息上传、服务端权威时长、Conversation、Message、SSE、RBAC 和媒体存储合同，不新增接口、schema、migration、mock 或第二套语音状态。

## 已确认现象与实现缺口

- 用户确认回放时间从 `0:00` 正常向前推进，但听不到声音。
- 时间推进说明 Blob URL 已被浏览器解码，播放时间轴和 `timeupdate` 链路有效；问题集中在录音输入为静音或媒体元素输出处于静音状态。
- 当前 `useImVoiceRecording` 只以 `audio.play()` Promise 成功作为可播放依据，没有在播放前显式恢复 `muted/defaultMuted/volume`，也没有验证麦克风轨道是否在整段录制期间保持静音。
- 当前测试把 `HTMLMediaElement.play()` mock 为成功，没有验证播放前的可听输出配置，也没有覆盖持续静音的录音轨道。

## 已选方案

采用方案 A：同时加固采集端和播放端，并为持续静音的麦克风提供明确错误。

不采用只强制播放器取消静音的最小补丁，因为它不能区分录音源本身为静音的情况；不采用可见原生 `<audio controls>`，因为它会破坏用户指定的 `X / 重放 / 停止 / 发送` 简洁控制结构。

## 录音采集设计

### 兼容性约束

请求麦克风时使用非强制的理想音频约束：

```ts
{
  audio: {
    channelCount: { ideal: 1 },
    echoCancellation: { ideal: true },
    noiseSuppression: { ideal: true },
    autoGainControl: { ideal: true },
  },
}
```

所有字段都是 `ideal`，不把缺少某项能力的浏览器误判为权限失败。录音仍只请求音频，不请求摄像头、位置或其他设备权限。

### 轨道静音判断

- 获得流后读取唯一有效音频轨道；不存在活动音频轨道时立即停止流并返回现有录音失败状态。
- 记录轨道的 `mute` 与 `unmute` 事件，并维护“本次录制是否曾进入可采集状态”。
- 如果轨道从开始到停止始终为 `muted`，不生成可发送的正常预览，释放 Blob URL 与媒体轨道，并显示新的可本地化提示“没有检测到麦克风声音，请检查输入设备后重试”。
- 轨道曾解除静音但实际环境非常安静时不误判为失败；本微步骤不引入音量阈值、波形分析、AudioWorklet 或录音内容识别。

这一边界只处理浏览器明确报告的持续静音，不猜测用户是否说话，也不采集或持久化额外音频分析数据。

## 可听回放设计

每次自动试听和手动重放都通过同一个播放准备函数：

1. 确认当前 `<audio>` 仍绑定本次录音的 object URL。
2. 显式设置 `defaultMuted = false`、`muted = false`、`volume = 1` 和 `playsInline = true`。
3. 重放时先把 `currentTime` 设为 `0`，同步把显示进度归零。
4. 若媒体尚未具备当前帧数据，等待一次 `loadeddata` 或 `canplay`；加载错误、取消、换录音或组件卸载会终止本次等待。
5. 调用 `play()`；只有当前录音 generation 仍有效时才进入 `preview_playing`。

浏览器自动播放策略拒绝时，继续保留 Blob 和预览页，显示现有“点击重放”提示。系统音量、操作系统输出设备或浏览器标签页被用户手动静音时，网页不能绕过系统设置；应用只保证媒体元素自身没有静音。

## 按钮布局与尺寸

### 状态分组

- 获取权限或录音中：只显示 `取消` 与 `停止`。
- 停止后的预览、播放或发送失败：显示 `取消`、`重放` 与 `发送`。
- 发送中保持预览态的三个按钮位置，但全部禁用，纸飞机显示忙碌状态。
- 四个动作不会同时出现，保持现有状态机和用户之前确认的交互。

### 位置

- 绿色录音气泡继续位于屏幕上半部，保留居中尖角和背景模糊。
- 操作组改为绝对居中定位在视口高度约 `57%`，而不是使用 `mt-auto` 推到底部。
- 使用 `top: 57%`、水平 `50%` 与双轴 transform，使 440×956、320×956、短屏和桌面窄列都围绕画面中部稳定排列。
- 操作组与气泡保持明确间隔，不遮挡气泡，也不依赖底部安全区。

### 尺寸

- 圆形按钮从 `48×48px` 放大为 `72×72px`，严格为 1.5 倍。
- 图标从约 `20px` 放大到 `28–30px`；停止方块约 `24px`。
- 两按钮和三按钮状态使用相同圆形尺寸；按钮间距从 `20px` 调整到 `28px`。
- 保留现有深色半透明按钮、白色图标、阴影、键盘 focus ring、禁用态和 reduced-motion 行为。

## 组件边界

### `useImVoiceRecording`

- 负责理想音频约束、音频轨道生命周期与持续静音判断。
- 统一准备自动播放和重放时的可听媒体属性及加载等待。
- 保持现有 generation、计时器、Blob/object URL、取消、发送成功和卸载清理逻辑。

### `ImVoiceRecordingOverlay`

- 只负责气泡、状态文案、播放器元素、按钮布局和无障碍语义。
- 通过既有 props 接收状态和事件，不访问 Store、API、麦克风或浏览器持久化。
- 把按钮组移到视口中部并将按钮放大到 72px。

### 会话页面与正式 API

- `pages.tsx` 继续负责成功 Blob 的正式发送，不改变 `sendVoiceMessage`、文件名、时长提示或焦点恢复。
- 正式 `POST /api/v1/im/conversations/:conversationId/voice` 和服务端权威媒体时长校验不变。

## 错误与清理

- 权限拒绝、设备不支持、持续静音轨道、空 Blob、加载失败和播放策略拒绝分别使用可本地化错误，不把失败状态伪装成正常试听。
- 取消、路由离开、身份切换和组件卸载必须移除轨道事件监听、停止轨道、清理媒体等待、暂停播放器并回收 object URL。
- 发送失败继续保留同一个有效 Blob 供重放或重试；持续静音录音没有可发送价值，因此不保留为可发送预览。
- 不记录原始音频、音量样本、设备标签或其他诊断数据。

## 测试策略

### 先失败的前端测试

- `getUserMedia` 收到非强制单声道、回声消除、降噪和自动增益理想约束。
- 自动试听和重放在 `play()` 前把 `defaultMuted/muted` 设为 `false`、`volume` 设为 `1`、`playsInline` 设为 `true`。
- 媒体未就绪时等待 `loadeddata/canplay`，generation 失效后不会继续播放旧录音。
- 从开始到停止始终 muted 的轨道被拒绝，轨道和 URL 被清理且不会进入可发送预览。
- 轨道后来触发 `unmute` 时允许正常预览，避免把短暂设备切换误判为永久静音。
- 录音态按钮为 72px 的取消/停止，预览态为 72px 的取消/重放/发送。
- 按钮组使用视口中部定位，不再包含 `mt-auto` 或底部安全区布局依赖。

### 回归验证

- 聚焦运行录音 hook、录音浮层、会话页面、共享 composer 和 i18n 测试。
- 运行根目录 TypeScript lint、完整前端测试与正式 production build/bundle audit。
- 不需要后端测试或 migration，因为正式接口和存储合同不变。

### 浏览器验收

- 在当前正式 5180/3000 运行链路验证麦克风授权、手动停止、59 秒停止、自动试听与手动重放。
- 实际听到回放声音，并核对进度、`muted=false`、`volume=1`、无 console/媒体错误。
- 在 440×956 和 320×956 核对按钮组位于画面中部、按钮为 72px、无水平溢出且不遮挡气泡。
- 分别检查录音态的取消/停止与预览态的取消/重放/发送；不点击发送，避免产生额外业务消息。
- 如果浏览器或系统输出被外部静音，记录为环境阻塞并提示用户恢复输出，不把它误报为代码修复失败。

## 验收标准

- 回放进度推进时，应用内媒体元素明确为非静音、满音量，并在媒体就绪后播放。
- 浏览器明确报告整段麦克风轨道持续静音时，界面给出可操作提示，不进入虚假的正常预览。
- 录音态只显示居中的 72px 取消/停止按钮。
- 预览态只显示同一位置的 72px 取消/重放/发送按钮。
- 背景模糊、绿色气泡、59 秒上限、自动试听、失败保留、正式发送和焦点恢复行为不回退。
- 聚焦测试、完整前端测试、lint、正式构建和真实浏览器可听验收均通过后，才可声明完成。
