# IM 语音消息气泡宽度设计

## 目标

让用户端、技师端和商户端共用聊天页面中的语音消息气泡充分利用头像旁的横向空间，使浏览器原生音频播放器能够正常展示进度和音量控制，同时保持窄屏可收缩。

## 根因

`MessageBubble` 的语音内容当前使用 `min-width: 200px`，播放器同时受 `max-width: 220px` 限制；外层消息列沿用普通消息的 `max-width: 78%`。这些约束叠加后，语音播放器在移动端被压得过窄，浏览器会折叠或截断原生控制项。

## 已选方案

- 仅为 `voice` 消息提供专属宽度：优先占满头像旁可用空间，并在较宽视口封顶约 320px。
- 语音气泡内部和 `<audio>` 播放器都使用气泡的完整可用宽度，不再保留 220px 上限。
- 在 320px 等窄视口中，气泡必须随剩余空间收缩，不产生页面水平滚动。
- 文字、表情、图片、视频、文件、卡片及系统消息继续使用现有宽度规则。

## 范围与非目标

本微步骤只修改共享 `MessageBubble` 的语音宽度样式与对应前端回归测试。不修改录音、上传、发送、播放事件、正式 API、数据库、消息结构、文案或其他消息类型的视觉样式，也不新增 mock、占位实现或并行播放器。

## 测试与验收

- 先补失败测试，确认语音消息外层使用专属可用宽度，播放器占满气泡且不再包含 220px 最大宽度限制。
- 定向运行 `MessageBubble` 媒体测试，确认语音失败重试和服务端时长仍保持原行为。
- 运行相关 IM 回归、TypeScript 检查与生产构建。
- 在可用的本地正式页面上检查常用手机宽度与 320px 窄屏：播放器控制项可用，消息行不横向溢出，其他消息气泡无变化。

## 完成边界

本地自动化与浏览器验证只证明当前工作区实现；不会自动代表远程推送、部署、已安装 iPhone/Android PWA 或实体设备验收完成。
