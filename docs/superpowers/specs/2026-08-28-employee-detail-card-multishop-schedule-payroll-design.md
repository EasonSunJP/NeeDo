# NeeDo 员工详细信息卡、多店从属、日程隐私与人工结算设计

**日期：** 2026-08-28

**状态：** 已完成方案讨论，待用户复核书面规格

**适用阶段：** Step 12 商户后台真实数据；涉及 Step 10 排班/订单状态机与 Step 11 工资结算合同，但不得绕过已完成阶段的正式接口、RBAC、审计和迁移规则

## 1. 背景与当前问题

商户后台当前使用“技师正式档案”抽屉。它已经能够读取正式技师详情、部分基础资料编辑、服务、近期排班、薪酬配置、账号权限与审计事件，但仍存在以下问题：

1. 前台暴露“技师档案 #47”“账号 #86”等内部数据库编号，没有以正式 NeeDoID 统一标识员工、技师身份和登录账号。
2. 当前 `TechnicianProfile.shopId` 只能表达一个店铺，不能表达合作技师同时从属多个店铺。
3. 商户排班查询只返回本店 `ScheduleSlot`；虽然现有冲突检查按 `technicianProfileId` 检查跨店重叠，但系统没有正式多店从属关系，也没有向合法从属店铺返回脱敏的跨店占用。
4. 当前详情卡只允许编辑少量基础字段；薪酬配置、工资统计和工资单操作没有在同一员工上下文内连通。
5. 店铺没有正式的每日、每周、每月结账周期和法定节假日顺延规则；员工级覆盖也没有正式合同。
6. 当前工资模块可以记录 `PayoutRecord`，但页面仍需明确：NeeDo 只计算和登记，不在商户后台执行银行自动转账。
7. 审计时间线虽然已使用共享组件，但仍会显示内部动作代码、原始 metadata 和过大的审计卡片，不符合商户端的紧凑视觉语言。
8. 现有 `ScheduleCycleBoard` / `ScheduleGrid` 视觉与交互已经存在，但部分数据仍耦合本地调度 store，不能直接当作正式持久化结果嵌入员工卡。

## 2. 目标

本设计交付一个统一的“员工详细信息卡”，满足：

- 以 NeeDoID 为前台唯一公开标识，一个 NeeDoID 只对应一个全局技师档案。
- 正式表达专属技师与合作技师/临时工的单店或多店从属关系。
- 在员工卡内查看并按权限编辑基础资料、服务、日程、薪酬、结算、账号权限和动态记录。
- 复用现有共享日程系统，前后端打通，不新建简化版日历，不使用浏览器业务数据制造成功状态。
- 对其他店铺已确认预约只返回灰色脱敏锁定，不泄露店铺、客户、服务、订单或参与者信息。
- 支持店铺默认结账周期、员工级覆盖和日本法定节假日提前/顺延规则。
- 工资统计、工资单、调整和支付登记都关联当前店铺与当前员工；支付由财务人员在财务结算页手工确认。
- 所有写操作受店铺作用域、RBAC、Zod、OpenAPI、审计、事务和正式数据库约束。

## 3. 非目标

- 不提供银行自动转账、支付网关代付或自动扣款。
- 不允许商户读取其他店铺的名称、客户、服务、订单、备注或参与者。
- 不复制技师账号或为每家店铺创建一份独立技师档案。
- 不从 `TechnicianService`、订单或前端缓存反推从属关系。
- 不把其他店铺的完整日程先发送到浏览器再通过 CSS 隐藏。
- 不在本步骤重写完整调度中心、订单状态机或工资引擎。
- 不添加浏览器本地留言；动态记录保持只读，直到存在正式持久化评论接口。

## 4. 术语与身份权威

### 4.1 员工、技师档案与账号

- **员工详细信息卡**：商户从当前店铺视角管理一个技师从属关系的统一界面。
- **技师档案**：全局唯一的 `TechnicianProfile`，继续以内部 `id` 作为数据库外键。
- **账号**：关联的 `User` 及其技师 `UserIdentity`、角色和登录凭据。
- **NeeDoID**：技师身份对应的正式公开标识。前台显示、搜索和打开员工卡时使用该标识；内部 `User.id`、`TechnicianProfile.id` 不作为公开账号标签。

统一身份迁移完成后，员工卡必须读取技师 `UserIdentity` 关联的 canonical `PublicIdentifier.publicId`。过渡期 DTO 中即使字段仍命名为 `needoId`，也必须由正式身份公开标识解析器提供，不能重新拼接数值 ID，也不能以旧 `User.id` 或技师档案 ID 回退。

### 4.2 发布状态与在职状态分离

`TechnicianProfile.status` 继续表示技师资料的发布/审核状态，不能当作在职状态。

店铺从属关系单独提供：

- `active`：在职/合作中
- `on_leave`：休假或暂停排班
- `suspended`：店铺暂停该关系
- `ended`：关系已结束

员工卡顶部显示从属关系的在职状态，不再把“已发布”当作“在职”。资料验证状态可以作为次级徽标显示。

## 5. 技师—店铺正式从属模型

### 5.1 新增 `TechnicianShopAffiliation`

建议字段：

- `id`
- `technicianProfileId`
- `shopId`
- `relationshipType`: `exclusive | partner`
- `workStatus`: `active | on_leave | suspended | ended`
- `startsAt`
- `endsAt`
- `activeKey`：活动关系唯一键
- `createdById`
- `updatedById`
- `createdAt`
- `updatedAt`
- `deletedAt`

必要索引：

- `[technicianProfileId, workStatus, deletedAt]`
- `[shopId, workStatus, deletedAt]`
- `[shopId, technicianProfileId, deletedAt]`
- 活动关系唯一键

### 5.2 分类规则

#### 专属技师

- 一个技师最多只能有一个活动的专属从属关系。
- 存在活动专属关系时，不允许再创建任何其他活动店铺从属关系。
- 只能接受所属店铺的排班和预约。
- 所属店铺的确认班次与预约都会锁定该技师日程。

#### 合作技师／临时工

- 可以同时拥有多个活动店铺从属关系。
- 可以向所有有效从属店铺公开自己的可排班时间。
- 不同店铺的计划排班互相不可见，也允许在确认前暂时重叠。
- 任一店铺的预约进入确认状态后，对该技师形成全局硬锁。

### 5.3 旧数据迁移

- 有效 `FULL_TIME` 且有店铺的行回填为 `exclusive`。
- 有效 `TEMPORARY` 且有店铺的行回填为 `partner`。
- `INDEPENDENT` 不能无条件映射；只有能通过当前店铺服务/业务关系验证的行才能回填为 `partner`。
- `shopId = null` 的私人或非店铺技师不进入员工列表，也不创建店铺从属关系。
- 回填必须先生成可恢复备份或可逆 migration，并输出冲突报告；存在一个技师多条互相矛盾关系时不得静默选择。

`TechnicianShopAffiliation` 部署并验收后成为员工列表、详情、排班授权、薪酬和结算的关系权威。`TechnicianProfile.shopId` 仅作为兼容字段分阶段退役，正式新读路径不得同时把两者视为权威。

## 6. 员工详细信息卡

### 6.1 顶部信息

卡片标题统一为“员工详细信息卡”。顶部显示：

- 头像
- 姓名
- NeeDoID（可复制）
- 在职状态
- 技师分类：专属技师或合作技师/临时工
- 当前所属店铺
- 邮箱与手机号
- 资料验证状态

不得显示“技师档案 #n”“账号 #n”“User ID”等内部编号。

### 6.2 栏目

1. **基础信息**
2. **服务项目**
3. **员工日程**
4. **薪酬与结算**
5. **权限与账号**
6. **动态记录**

顶部同时展示当前店铺口径的关键摘要：本期完成订单、有效工时、服务收入、预估应付、已付和未付。所有指标必须由正式订单金融与工资单数据聚合，不能使用演示数字。

### 6.3 编辑模式

- 每个可编辑栏目右上角提供“编辑”。
- 原位置切换成表单，不在页面底部额外堆放重复编辑区。
- 保存前进行客户端基本校验，服务端再次通过 Zod 验证。
- 成功后重新读取正式详情；失败保留输入并展示本地化错误。
- 取消恢复最近一次服务器快照。
- 不做“先显示成功、稍后再保存”的假乐观提交。

基础资料可编辑范围包括姓名、简介、城市、服务范围、从业年限和当前店铺从属状态。技师分类变更必须走独立的关系变更操作并进行冲突校验，不能作为普通文本字段直接修改。

## 7. 员工日程：复用现有系统并正式接入

### 7.1 组件边界

卡内直接复用：

- `ScheduleCycleBoard` 作为完整日、周、月视图容器。
- `ScheduleGrid` 作为共享网格渲染器。
- 现有日期切换、图例、时间轴、拖拽创建、顶部/底部调整手柄、详情编辑和全屏入口。

不得手写第二套员工日历。现有组件中与浏览器 dispatch store 耦合的部分需要通过正式数据适配入口解耦：共享组件接收 `DispatchScheduleGridData` 或等价正式 adapter 输出，持久化由正式 API 完成。

### 7.2 默认行为

- 打开“员工日程”时默认显示当前周。
- 数据固定过滤到当前 NeeDoID 对应的技师和当前店铺从属关系。
- 支持日、周、月视图和前后日期切换。
- 卡片空间不足时提供全屏查看，仍使用相同组件和正式数据源。

### 7.3 可见性类型

正式接口只返回以下三种投影：

#### `own_detail`

- 当前店铺拥有或参与的日程。
- 返回本店权限允许的服务、订单、客户/参与者、状态和详情跳转目标。
- 有写权限时可编辑；无写权限时只读。

#### `affiliate_availability`

- 合作技师主动向有效从属店铺公开的可排班时间。
- 所有有效从属店铺可以看见时间范围并用于安排本店班次或创建本店可预约时段。
- 不携带其他店铺参与者或业务信息。

#### `busy_redacted`

- 由其他从属店铺的已确认预约形成。
- 只返回开始时间、结束时间、通用标题“其他店铺已有确认安排”、灰色锁定状态和 `isClickable=false`。
- 不返回来源店铺 ID/名称、客户、服务、订单号、价格、地址、备注、内部事件 ID或参与者。

脱敏必须在 Repository/Service 输出层完成，完整记录不得发送到前端。

### 7.4 专属技师日程规则

- 只有一个有效店铺关系。
- 本店确认班次、阻塞时间和有效预约都形成硬锁。
- 其他店铺创建排班或预约时，关系校验直接拒绝，不依赖前端隐藏。

### 7.5 合作技师日程规则

- 公开可排班时间对全部有效从属店铺可见。
- A 店与 B 店的计划排班可以同时存在；A 不读取 B 的计划排班，B 也不读取 A 的计划排班。
- `PENDING` 预约仍属于创建店铺的私有业务状态，不向其他店铺显示详情。
- 预约从 `PENDING` 转为 `CONFIRMED` 时才创建全局硬锁；`IN_SERVICE` 延续该锁。
- `CANCELLED` 立即释放未来锁；`COMPLETED` 作为历史事实保留，但不会阻止未来时段。
- 另一店铺查询相同员工时，只获得对应的 `busy_redacted` 时间块。

### 7.6 冲突和并发

确认预约与会产生硬锁的排班操作必须：

1. 在数据库事务内锁定 `TechnicianProfile` 或专用技师时间锁权威行。
2. 查询该技师所有店铺中与目标时间重叠的活动硬锁。
3. 无冲突才执行状态变化并写审计。
4. 有冲突返回稳定的 `409` 错误键，不泄露冲突来源店铺。

当前按 `technicianProfileId` 的全局 overlap 检查可以复用，但必须区分“允许重叠的跨店计划排班”和“不可重叠的确认预约/专属硬锁”。

### 7.7 正式接口建议

读取：

```text
GET /api/v1/merchant-admin/employees/{needoId}/schedule?from=...&to=...&view=week
```

返回：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "employee": {
      "needoId": "u0000000237",
      "relationshipType": "partner"
    },
    "events": [
      {
        "id": "opaque-redacted-token",
        "startsAt": "2026-08-28T13:00:00.000Z",
        "endsAt": "2026-08-28T15:00:00.000Z",
        "visibility": "busy_redacted",
        "status": "locked",
        "title": "其他店铺已有确认安排",
        "isClickable": false,
        "isEditable": false
      }
    ]
  }
}
```

日期范围继续限制在最多 93 天。公开标识必须先解析成当前活动技师身份；找不到、已结束从属或不属于当前店铺时统一返回受控的 404/403，不暴露其他店铺关系。

写入可以复用现有正式 schedule-slot API，但 Service 必须在写入前校验当前店铺从属、技师分类、可排班公开范围和全局硬锁。任何前端 adapter 都不能绕过后端规则。

## 8. 服务项目

- 专属技师只能配置所属店铺服务。
- 合作技师可以在每个从属店铺拥有不同的服务、价格、时长和可预约状态。
- 卡内只展示当前店铺的 `TechnicianService`。
- 对当前店铺服务的编辑继续使用正式服务接口、店铺作用域和审计。
- 服务关系不是店铺从属关系权威；删除服务不会自动解除从属，解除从属也必须明确处理未来排班和工资结算。

## 9. 薪酬与结算

### 9.1 薪酬归属

薪酬按“店铺 + 技师”配置。合作技师在 A、B 店可以有不同薪酬规则，互不读取、互不结算。

继续使用：

- 店铺默认 `ShopFinanceRuleSet`
- 技师级 `TechnicianCompensationProfile` override
- 版本化保存和历史工资单 `compensationProfileId` 快照

员工卡中的“薪酬与结算”包含：

- 当前规则来源：继承店铺或员工覆盖
- 月薪、时薪、日薪、单次报酬、分成、最低保障、NDP 承担和生效期间
- 当前周期订单、服务收入、工时、基础工资、分成、奖金、扣款、NDP 扣除、净应付
- 当前及历史工资单、已付、未付、申诉和支付记录

### 9.2 店铺默认结账周期

新增版本化 `ShopPayrollSchedulePolicy`：

- `cadence`: `daily | weekly | monthly`
- `weeklySettlementWeekday`: 仅每周周期必填
- `monthlySettlementDay`: 仅每月周期必填，1–31
- `holidayAdjustment`: `previous_business_day | next_business_day`
- `timezone`: 默认 `Asia/Tokyo`
- `effectiveFrom` / `effectiveTo`
- `status` / `version`
- 创建、更新、软删除与审计字段

计算口径：

- 每日：每个自然日形成一个结算期间。
- 每周：上一个周期结束后的次日至配置星期形成一个期间。
- 每月：上一个配置结算日次日至本月配置结算日形成一个期间；若配置 29–31 而当月没有该日期，先落在当月最后一个自然日。
- 得到自然结算日后，再应用法定节假日/非营业日提前或顺延规则，生成计划支付日。

### 9.3 员工级覆盖

新增版本化 `TechnicianPayrollScheduleOverride`，关联 `TechnicianShopAffiliation`：

- `inheritShopPolicy`
- 与店铺政策相同的周期和节假日字段
- `effectiveFrom` / `effectiveTo`
- `status` / `version`
- 审计字段

管理员和财务角色可以设置“继承店铺规则”或个人周期。员工覆盖仅影响当前店铺，不影响同一合作技师在其他店铺的周期。

### 9.4 日本法定节假日和营业日

支付日期计算必须在后端使用正式、可版本追踪的日本营业日日历。现有前端调度 store 中的硬编码 2026 节假日只能作为界面演示历史，不能成为工资支付日权威。

建议新增 `BusinessCalendarDate`：

- `countryCode = JP`
- `calendarDate`
- `isPublicHoliday`
- `isBusinessDay`
- `holidayName`
- `sourceVersion`
- `createdAt`
- `updatedAt`
- `deletedAt`

周六、周日和法定节假日默认非营业日；店铺后续若需要自定义营业日，必须通过独立、可审计的 override 扩展，不直接改写公共节假日事实。

### 9.5 不提供自动转账

NeeDo 商户后台只负责：

- 计算应付
- 生成和审批工资单
- 展示计划支付日
- 记录奖金、补贴、扣款和申诉
- 登记实际支付结果

系统不得调用银行自动转账。财务人员在“财务结算”页逐位员工手动记录：

- 实际支付金额
- 实际支付日期
- 支付方式
- 银行/现金/外部参考号
- 凭证 URL
- 备注

继续使用正式 `PayoutRecord`。部分支付时更新 `paidAmountJpy` 和 `unpaidAmountJpy`，不能显示为“结账完成”；只有累计有效支付金额等于工资单 `netPayJpy` 时才允许确认该员工本期结清。锁定后的工资周期不得继续新增支付记录。

### 9.6 权限

- 管理员、店铺负责人和财务可读取店铺结算周期。
- 只有具有结算规则写权限的管理员/财务可修改店铺默认或员工覆盖周期。
- 只有财务支付登记权限可创建 `PayoutRecord` 和确认结清。
- 工资单发布、审批、申诉处理、奖金扣款继续使用各自独立权限，不因进入员工卡而合并成一个“大权限”。

## 10. 权限与账号

本栏展示：

- NeeDoID
- 登录邮箱和手机号
- 账号启用状态
- 当前店铺技师身份
- 当前店铺角色与权限
- 最近登录

对账号启停、角色和关系的编辑必须调用 User Management / RBAC 正式接口。员工卡不能直接修改密码、token、内部 ID 或其他店铺角色。

## 11. 动态记录

继续复用 `ContactEventTimelinePanel`，但改成商户端紧凑样式：

- 正常事件使用蓝绿节点，失败、拒绝、冲突和异常才使用红色。
- 文案为“操作者（角色）：业务动作”。
- 内部 action code 映射为自然语言。
- 只显示有业务意义的变更字段和值。
- 不显示 `shopId`、`technicianProfileId`、权限 code、嵌套 source object 或原始 JSON。
- 资料、从属、服务、排班、薪酬规则、结账周期、工资单、调整、支付和结清都写入同一员工动态流。
- 其他店铺事件不能进入当前店铺的动态记录。
- 评论输入框保持关闭，直到存在店铺作用域的正式持久化评论 API。

## 12. API、分层与审计

所有新接口遵守：

```text
Route -> Controller -> Service -> Repository -> Prisma
```

- Route 声明 JWT、permission、Zod 和 OpenAPI。
- Controller 只处理请求响应。
- Service 处理关系不变量、隐私投影、周期计算、节假日处理、事务与审计。
- Repository 只访问 Prisma。
- 列表和日程查询分页/限制日期范围。
- 统一 `{ code, message, data }` 响应。
- 不返回原生异常、token、密码或其他店铺隐私。

必须审计：

- 创建、暂停、恢复、结束店铺从属关系
- 专属/合作分类变更
- 基础资料和服务编辑
- 排班创建、修改、取消和确认冲突
- 薪酬规则版本变化
- 店铺/员工结账周期变化
- 工资单生成、重算、发布、审批、申诉处理
- 支付登记和最终结清

纯读取审计不应污染用户可见动态流；可保留安全审计，但员工“动态记录”只呈现业务变化。

## 13. 前端状态与错误处理

- 员工卡以当前 NeeDoID、当前店铺 ID 和活动从属关系作为请求上下文。
- 切换员工或关闭抽屉时取消/失效旧请求，防止迟到响应覆盖新员工。
- 各栏目独立显示 loading/error/retry，不因日程失败清空基础资料。
- token 过期交给统一鉴权恢复/重新登录流程，不能直接显示 `error.auth.token_expired` 原始键。
- `403` 显示无权限，`409` 显示业务冲突，跨店冲突文案只说该时段已被占用。
- 写入成功后刷新相关详情、日程、工资单和动态记录。

## 14. 实施拆分

为了遵守小步开发规范，实施计划必须拆成可独立运行、测试、回滚的微步骤：

1. **从属与身份地基**：migration、回填、冲突报告、Repository/Service/API、NeeDoID 详情读取。
2. **员工卡基础结构**：改名、顶部身份、关系状态、栏目和基础资料真实编辑。
3. **正式日程投影**：多店可见性、脱敏 busy、全局硬锁、正式 schedule adapter 和共享日程组件嵌入。
4. **薪酬连接**：卡内读取/编辑/预览当前店铺薪酬版本及统计。
5. **结账周期**：店铺默认、员工覆盖、营业日日历、计划支付日计算。
6. **财务人工结清**：按员工工资单记录支付、部分支付、最终结清和财务页过滤。
7. **动态记录与完整验收**：自然语言事件、跨店隔离、桌面/窄屏视觉 QA、完整测试和文档。

每个微步骤只提交自己的 schema、API、UI、测试与文档，不得提前制造下一步的空壳入口或假成功。

## 15. 测试与验收

### 15.1 后端

- 专属技师只能有一个活动店铺关系。
- 合作技师可以同时从属 A、B 店。
- 未从属店铺无法读取、排班或结算该技师。
- A 只能看到 A 自己的完整日程。
- A 看不到 B 的计划排班。
- B 的确认预约在 A 返回灰色脱敏锁定，响应中不存在 B、客户、服务、订单和参与者字段。
- B 取消预约后 A 的灰色锁定消失。
- 两店并发确认同一时段时只有一个事务成功，另一个返回不泄密的 409。
- 店铺默认和员工覆盖结账周期按生效日期正确选择。
- 每日、每周、每月及月底 29–31 规则正确。
- 日本节假日前移/后移规则正确。
- 合作技师在 A、B 店的工资统计和工资单完全隔离。
- 部分支付不会结清；足额累计支付才结清。
- 没有支付登记权限不能创建支付记录。
- 所有写操作产生店铺作用域审计。

### 15.2 前端

- 标题显示“员工详细信息卡”。
- 顶部显示 NeeDoID，不显示内部档案/账号编号。
- 在职状态与资料发布状态分离。
- 六个栏目键盘和窄屏可访问。
- 编辑、取消、保存、失败重试都读取正式 API。
- 员工日程复用共享 `ScheduleCycleBoard / ScheduleGrid`，没有页面内手写 24 小时表格。
- `busy_redacted` 使用灰色锁定、不可点击且无详情入口。
- token 过期和权限错误显示本地化信息。
- 薪酬统计、工资单和支付状态与当前店铺/员工一致。
- 时间线不显示内部 action code 或 metadata JSON。

### 15.3 浏览器验收

- 正式本地后端、MySQL、Redis 和前端均健康。
- 以 A 店商户身份打开专属技师和合作技师员工卡。
- 以 B 店创建合作技师确认预约，再回到 A 店验证灰色脱敏锁定。
- 验证 A 不能读取 B 的业务详情或通过点击/网络响应获得信息。
- 验证公开可排班、排班编辑、取消与刷新持久化。
- 修改薪酬和结账周期后刷新仍存在。
- 在财务结算页完成部分支付和最终结清，员工卡同步显示。
- 桌面宽屏与 390px 窄屏分别检查员工卡、日程网格、薪酬表单和动态记录。

## 16. 完成标准

只有同时满足以下条件才可声明完成：

- 数据库 migration、回填和冲突处理已验证。
- 一个 NeeDoID 对应一个技师档案，多店关系由正式从属表表达。

- 店铺及员工结账周期、节假日规则、工资单和人工支付记录可持久化。
- RBAC、审计、Zod、OpenAPI、单元测试、集成测试、构建和浏览器验收通过。
- 没有新增 mock、placeholder、TODO、假保存或自动转账暗示。
