# 登录后正式排班预加载设计

## 目标

登录成功后，如果账号拥有有效技师或店铺身份及对应门户权限，客户端立即在后台请求后端加载当前 14 天排班周期。进入店铺端或技师端时优先显示最近一次正式缓存，并在画面中央显示 50% 透明度、不会拦截操作的旋转同步提示，直到最新数据返回。

## 当前问题

- 店铺端 `DispatchOverviewWorkspace` 只在页面挂载后开始读取排班，并在每次请求前清空旧结果。
- 该页面没有复用项目已有的账号级加密 IndexedDB 缓存。
- 多页排班目前逐页串行读取。
- 排班列表查询加载了地址和行政区等列表响应不需要的关联。
- 现有持久缓存关闭页面或 PWA 后继续保留；显式登出只清内存状态，没有删除 IndexedDB 账号数据。

## 方案

### 后端账号范围预加载

新增受认证保护的 `GET /api/v1/schedule/preload`。接口依据访问令牌中的 `page:merchant-app` / `page:technician-app` 门户权限决定可加载的资源，不要求先切换到对应身份；随后从已认证 `userId` 重新读取该账号的有效身份，并最多解析一个与实际门户选择规则一致的技师身份和一个店铺身份。店铺组织身份使用现有商户店铺作用域规则解析默认店铺，禁止客户端提交 shopId 或 technicianProfileId。

请求包含 `from`、`to`、`page`、`pageSize`，日期窗口受现有最大范围约束。响应分别返回技师和店铺的分页正式排班；没有对应身份时返回 `null`。该接口只读、不写数据库、不切换身份、不旋转 Token。

### 客户端预加载与缓存

新增排班预加载协调器，在认证会话提交后检测 `allowedPortals`。账号拥有技师或店铺端权限时，按当前 14 天周期异步加载所有分页并写入账号级加密持久缓存。请求失败不影响登录，进入页面后仍可正常重试。

排班缓存键以 `calendar:` 开头，并包含角色、作用域实体和日期窗口，因此继续复用现有排班变更失效规则。缓存值包含 `fetchedAt` 和正式 slot 列表：不超过 24 小时可先显示并强制后台刷新；超过 24 小时不用于可操作排班。

### 页面行为

店铺当前排班页不再在刷新开始时清空缓存数据。存在有效缓存时立即构建现有共享排班板，并将刷新状态与首次加载状态分开：

- 首次且无缓存：保持现有阻塞式“加载正式排班中”。
- 已显示缓存且正在刷新：页面中央显示 12 点环形 Loading，整体透明度 50%。
- Loading 容器使用 `pointer-events: none`，不影响查看、滚动和其他操作。
- 遵守 `prefers-reduced-motion`，降低动画而不隐藏同步状态。
- 最新响应成功后更新缓存并移除 Loading；失败时保留缓存并展示可重试错误。

技师共享日历的 slot 读取复用相同缓存读取函数，从登录预加载的当前日数据中获得快速首屏；预约和可排班窗口继续由各自正式接口加载，不合并业务概念。

### 后端查询优化

排班列表改用只覆盖响应字段的关系投影，不读取店铺地址、行政区或完整关联实体。第一页返回总数后，客户端最多四路并行读取后续分页，避免长窗口串行等待，同时限制并发以保护 API 和数据库连接池。

### 生命周期与安全

- 普通关闭标签页、浏览器或 PWA：保留加密 IndexedDB 缓存。
- 排班、可排班窗口或日程变更：按 `calendar:` 前缀删除对应账号缓存。
- 显式登出：锁定内存后物理删除该账号及其 merchant-preview 子作用域的持久缓存。
- 登录替换为另一账号：锁定并异步清除旧账号缓存。
- 系统清站点数据、卸载 PWA 或浏览器存储回收仍可能删除缓存，应用不依赖缓存保证正确性。

## 验收

- 无技师/店铺身份的账号不发送预加载请求。
- 多身份账号登录完成后只发送一条去重后的预加载链路，不切换当前身份。
- 后端只返回该账号实际拥有且门户权限已开启的技师和默认/直属店铺排班。
- 缓存存在时，店铺页立即显示排班并在中央显示 50% 非阻塞旋转 Loading。
- 刷新完成后 Loading 消失；缓存超过 24 小时不作为可操作数据展示。
- 关闭并重开页面/PWA 后缓存仍可读取；显式登出后对应 IndexedDB 数据被删除。
- 相关前后端测试、lint、typecheck、build、API 和移动端页面验证通过。
