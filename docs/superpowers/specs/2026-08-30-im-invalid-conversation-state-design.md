# IM 无法访问指定对话错误态设计

## 背景

用户通过 URL 直接进入不存在、已删除或当前账号无权访问的会话时，正式 API 会返回 `error.realtime.conversation_not_found`。当前聊天页只识别旧的 `Conversation not found` 文案，因此把这个可预期的领域 404 重新抛出为未处理 Promise rejection，最终触发全局恢复页。该现象发生在认证完成之后，不应显示为登录失败或整页运行错误。

## 目标

- 登录成功后，指定会话不可访问时不进入全局恢复页。
- 在聊天路由内显示明确的“无法进入指定对话”状态。
- 提供唯一主操作“返回首页”。
- 用户端返回 `/`，商户端返回 `/merchant`，技师端返回 `/technician`。
- 保持正常会话、认证、全局错误边界和正式 API 契约不变。

## 非目标

- 不修改登录、Token、Session 或 RBAC 实现。
- 不修改后端的安全 404 行为，也不区分“不存在”和“无权限”的具体原因。
- 不新增重试、自动跳转、会话恢复、浏览器缓存清理或新的 IM API。
- 不改造正常聊天页视觉、消息加载、发送、SSE 或分页逻辑。

## 方案比较

### 方案 A：聊天路由本地错误态（采用）

聊天页识别正式会话未找到错误，在当前路由中保存不可访问状态并渲染专用空状态。该方案保留后端防枚举语义，给用户明确反馈，并且不会吞掉其他程序错误。

### 方案 B：加入全局非致命错误名单

全局错误边界可以忽略该错误，但页面仍缺少明确状态，且容易把其他位置错误隐藏为无反馈的空白页，因此不采用。

### 方案 C：由后端返回重定向信息

后端不应决定用户端、商户端和技师端的前端路由；这也会扩大 API 契约和测试范围，因此不采用。

## 前端设计

`ImConversationRoomPage` 增加会话请求状态，至少区分初始化、可用和不可访问。三个并行请求——会话详情、消息历史、标记已读——共用同一个错误处理函数：

1. 正式错误消息精确等于 `error.realtime.conversation_not_found`，或兼容旧错误消息 `Conversation not found` 时，清除当前活动会话并进入不可访问状态。
2. 其他错误保持原有处理方式，继续抛给现有异常链路，不伪装成会话不存在。
3. 组件卸载后不再更新状态。

不可访问状态复用 `ImStandaloneShell`、`ImTopBar` 和 `ImEmptyState`，显示：

- 标题：`无法进入指定对话`
- 说明：`该对话可能不存在、已被删除，或当前账号无权访问。`
- 主按钮：`返回首页`

首页路由由当前 IM scope 决定：`config.routes.prefix || "/"`。按钮使用替换导航，避免浏览器返回键再次回到无效会话 URL。

## 国际化

新增三条中文源文案对应的日语、英语、韩语和繁体中文翻译，继续使用现有运行时 i18n 机制。不得新增只在简体中文下可读的硬编码错误态。

## 数据与安全边界

- 后端继续对不存在和无权限会话统一返回安全 404，不向前端透露会话是否真实存在。
- 前端只根据正式错误键判断错误类型，不解析数据库 ID、参与者或内部异常。
- 错误页不展示请求 ID、内部用户 ID、会话参与者或其他敏感信息。

## 测试设计

按 TDD 先增加失败测试，再实现最小修复：

1. 错误识别单元测试覆盖正式错误键、旧兼容文案和无关错误。
2. 路由页面测试验证正式会话 404 后显示指定标题、说明和按钮，且不产生未处理 rejection。
3. 路由映射测试验证用户端、商户端和技师端分别返回 `/`、`/merchant`、`/technician`。
4. 现有正式 IM adapter、聊天页和全局错误分类测试继续通过。
5. 浏览器验收直接访问一个不存在的会话 ID，确认不出现恢复页；点击“返回首页”后进入当前身份首页。

## 验收标准

- 无效或无权限会话 URL 不再显示 NeeDo 恢复模式。
- 页面明确显示“无法进入指定对话”和原因说明。
- “返回首页”只出现一个，并返回当前身份对应首页。
- 正常会话仍可加载消息、标记已读和发送消息。
- 非会话 404、网络异常和真实运行错误未被错误吞掉。
- 定向测试、前端 lint、生产构建和浏览器验收通过。
