# IM 消息多选、聊天记录转发、收藏与翻译设计

日期：2026-08-31  
状态：待用户书面复核  
适用阶段：Step 13 — IM / Social / Notification 后端化

## 1. 目标

在现有正式 IM 页面和数据链上增加以下能力：

1. 长按消息快捷菜单固定为紧凑四列两行，并增加“翻译”和“多选”。
2. 多选模式支持逐条选择、固定悬浮“选择到这里 / ここまで”、转发、复制、收藏和仅本人批量删除。
3. 单条和多条转发统一生成“聊天记录”卡片；卡片点击后打开带关闭按钮的只读全屏详情。
4. 多条收藏整体保存为一个收藏项，并从用户中心“我的收藏”进入同一全屏详情。
5. 会话自动翻译与单条手动翻译统一接入后端翻译能力；首期供应商为 DeepL API Free，但业务层不绑定供应商。

## 2. 明确边界

- 保留现有消息菜单的玻璃容器、箭头、表情区和下层无模糊/无折射遮罩。
- 不改变对方消息、不物理删除共享 `Message`，批量删除只写当前身份的永久删除墓碑。
- 不使用浏览器业务数据库、localStorage 聊天记录包或临时 mock 成功状态。
- 不把翻译密钥发送到浏览器，不在前端直接调用第三方翻译服务。
- 不实现聊天记录包编辑、记录项再次选择、记录详情内回复或消息恢复。
- 不允许系统提示、日期分隔、撤回残留、已过期消息或隐私倒计时消息进入聊天记录包。
- 单次多选、转发、收藏或批量删除最多 100 条消息。

## 3. 快捷菜单

动作区固定为四列两行：

```text
回复      转发      复制      翻译
信息置顶  撤回      删除      多选
```

- 动作按钮压缩图标容器、内边距和行高；文字仍须完整可读并保留键盘焦点样式。
- 菜单宽度继续受现有视口安全边距约束，不因桌面宽度恢复为一行。
- “翻译”仅对仍可读取的用户文本或带文字说明的媒体可用。
- 会话 `autoTranslateMessages=true` 时“翻译”置灰，不可点击。
- 当前消息的手动译文已展开时，动作名称改为“隐藏译文”。
- “多选”关闭快捷菜单、清除当前文字选区，并以长按消息作为锚点和首条选中消息。
- 既有下层遮罩继续仅使用半透明压暗，`filter`、`backdrop-filter` 与 `-webkit-backdrop-filter` 均为 `none`。

## 4. 多选模式

### 4.1 页面结构

- 顶部显示“已选择 N 条信息”和取消入口。
- 每条可选消息左侧显示圆圈；只有点击圆圈才切换该条消息的选中状态。
- 上方和下方各有一个固定悬浮的“选择到这里”按钮；日语固定为“ここまで”。
- 底部使用与消息输入框相同的玻璃容器，显示四个等宽动作：转发、复制、收藏、删除。
- 选中数为零时四个动作全部置灰。

### 4.2 固定范围按钮

- 两个按钮固定在视口左上与左下的安全区域，不随聊天列表滚动。
- 点击按钮时，以按钮中心的纵向位置为准，从已渲染消息行中选择几何中心距离最近的可选消息作为范围终点。
- 选择范围为锚点消息与终点消息之间、按会话正式顺序排列的全部可选消息，包含两端。
- 用户滚动后再次点击，终点按按钮当前覆盖位置重新计算。
- 当前已经分页加载的消息可以进入范围；按钮不为一次点击额外跨页抓取未加载历史。
- 范围超过 100 条时不改变现有选择，并显示“最多选择100条信息”。

### 4.3 点击、滚动和文字手柄判定

- 菜单、底部动作、圆圈及“选择到这里”按钮属于多选控件；点击它们不退出多选。
- 消息气泡、聊天记录卡片以及其他非控件区域属于退出区域；一次触摸未形成滚动并在这些区域抬手时退出多选。
- 指针移动超过既定触摸阈值或列表实际发生滚动后，本次手势被标记为滚动；手指抬起只结束滚动，绝不触发退出。
- `pointercancel` 不执行退出动作。
- 长按消息仍会显示快捷菜单并选中文字。
- 拖动文字选区左右手柄只调整选区，不滚动聊天列表；开始拖动手柄时关闭菜单并退出多选。
- 进入多选时主动清除文字选区，避免手柄与多选圆圈同时存在。

## 5. 聊天记录包

### 5.1 正式模型

新增以下 Prisma 模型，全部包含 `id`、`createdAt`、`updatedAt`、`deletedAt`，所有关联字段建立索引：

- `ImChatRecordBundle`
  - `publicId`：不可枚举的公开标识。
  - `createdByUserId`、`createdByIdentityId`：创建账号和正式身份。
  - `sourceConversationId`：来源会话。
  - `senderCount`、`itemCount`、`titleSnapshot`、`previewSnapshot`。
  - `contentVersion`：记录包格式版本。
- `ImChatRecordItem`
  - `bundleId`、`position`、`sourceMessageId`。
  - 发送者账号/身份可空引用以及 `senderDisplayNameSnapshot`、`senderAvatarSnapshot`。
  - `messageType`、`contentSnapshot`、`metadataSnapshot`、`sentAtSnapshot`。
  - 唯一约束为 `(bundleId, position)`。
- `ImChatRecordDelivery`
  - `bundleId`、`messageId`、`conversationId`。
  - 唯一约束为 `messageId`，用于证明记录包通过哪条正式消息投递。
- `ImChatRecordFavorite`
  - `bundleId`、`ownerUserId`、`ownerIdentityId`。
  - 每次用户主动收藏创建一个收藏关系；幂等重试不会重复创建，用户再次主动收藏可以形成新的记录包。

普通媒体复制到记录包持有的受保护文件，并复用 `MediaAsset`：

- `entityType="im_chat_record_item"`、`entityId=<itemId>`、`usageType="im_chat_record"`。
- 新文件使用不可猜测文件名，保留 MIME、大小、宽高和校验摘要。
- 聊天记录详情通过受鉴权媒体接口读取，不直接暴露内部磁盘路径。
- 只有服务端能够验证并读取的正式媒体才允许复制；外部 URL、缺失文件或已进入清理状态的媒体使整次创建失败，不降级成失效卡片。
- 任一媒体复制或数据库写入失败时补偿清理已复制文件并回滚整个记录包。

### 5.2 创建规则

- 客户端提交 `sourceConversationId` 和 1–100 个 `messageIds`；服务端重新按正式消息顺序排序，不信任客户端顺序、发送者名称、正文或标题。
- 服务端验证当前身份仍是来源会话参与者，且每条消息仍可见、未对本人删除、未撤回、未过期并符合转发/收藏政策。
- 任一消息不合法时整次失败，不创建部分记录项、投递或收藏。
- 快照创建后，来源消息被操作者仅本人删除、来源会话隐藏或来源消息后续普通清理，都不删除既有聊天记录包。
- 来源消息在记录包创建前已经撤回或进入隐私终态时必须拒绝，避免通过旧客户端复制不可用内容。

### 5.3 标题和预览

按记录项中发送者首次出现顺序去重：

- 1 名：`a的聊天记录`。
- 2 名：`a和b的聊天记录`。
- 3 名及以上：`群聊记录`。

标题必须通过五语言 i18n 生成；日语分别为 `aのチャット履歴`、`aとbのチャット履歴`、`グループチャット履歴`。卡片显示标题、最多两行安全预览、消息数量和小字“聊天记录”。

### 5.4 转发

- 单条和多条统一调用同一正式接口。
- 转发目标选择页复用现有联系人/会话能力，并允许选择联系人或已有群聊。
- 服务端在一个事务中创建记录包、记录项、目标会话中的 `chat-record` 消息及 `ImChatRecordDelivery`。
- `Message` 的正式 metadata 只保存记录包公开标识和已验证的最小卡片摘要，不内嵌最多 100 条正文。
- 成功后进入目标会话；重复幂等请求返回同一投递消息。

### 5.5 收藏

- 收藏接口在一个事务中创建记录包、记录项和 `ImChatRecordFavorite`。
- 用户中心“我的收藏”进入 `/me/favorites`，分页显示当前身份未删除的聊天记录收藏项。
- 点击收藏项复用聊天记录全屏详情。
- 移除收藏只软删除收藏关系；不删除来源消息、已发送卡片或其他用户的访问关系。

### 5.6 全屏详情和访问控制

- 详情头部左侧提供关闭按钮，标题区域显示记录包标题；正文为只读消息时间线，不显示输入框。
- 最多 100 条记录项仍使用分页或游标读取，不提供无分页全量列表接口。
- 当前身份满足以下任一条件才可读取：
  1. 是记录包创建身份；
  2. 拥有未删除的收藏关系；
  3. 仍是投递会话参与者，且对应投递消息没有被当前身份仅本人删除。
- 无权访问统一返回安全的未找到错误，不返回标题、发送者、预览或正文。

## 6. 多选动作

### 6.1 复制

- 按服务端消息顺序生成纯文本，每条格式为 `发送者显示名:内容`。
- 与现有单条复制保持一致：自动翻译已开启或当前消息手动译文已展开时复制正在显示的译文，否则复制原文；绝不把未成功的翻译当成译文。
- 正文中的换行保留；发送者前缀只出现在该消息首行。
- 媒体使用稳定文本：`[图片]`、`[视频]`、`[语音]`、`[文件] 文件名`、`[位置] 地点`、`[名片] 名称`、`[服务] 名称`、`[日程邀请] 标题`。
- 复制失败保留多选状态并显示“复制失败，请重试”。

### 6.2 批量删除

- 提交 1–100 个消息 ID；服务端先验证全部消息，再在同一事务中为当前正式身份写入 `MessageUserDeletion`。
- 接口幂等；已对本人删除的消息视为已完成。
- 写一条不含正文的批量审计，记录会话 ID、数量和消息 ID。
- 提交前显示确认：“将从你的聊天记录中删除 N 条信息，不影响对方。”
- 成功后仅从当前客户端和当前身份后续分页结果中移除，对方及其他身份不受影响。

## 7. 翻译

### 7.1 供应商边界

新增 `TranslationProvider` 接口，首期实现 `DeepLTranslationProvider`。业务服务只依赖接口，不依赖 DeepL SDK 类型。

配置全部来自后端环境：

- `IM_TRANSLATION_PROVIDER=deepl`
- `IM_TRANSLATION_API_BASE_URL`
- `IM_TRANSLATION_API_KEY`
- 请求超时、重试上限和月度保护阈值使用现有环境配置系统校验。

首期使用 DeepL API Free。根据官方文档，免费版每月最多翻译 500,000 字符，HTTP 456 表示额度耗尽；HTTP 429 使用带抖动的指数退避。以后切换收费服务时只新增或替换 provider 和配置，不改变前端接口或缓存键。

### 7.2 翻译缓存

新增 `ImMessageTranslation`：

- 包含标准 `id`、`createdAt`、`updatedAt`、`deletedAt`，并为所有关联和查询字段建立索引。
- `messageId`、`sourceContentHash`、`sourceLanguage`、`targetLanguage`。
- `translatedContent`、`providerKey`、`providerRequestId`、`translatedAt`。
- 唯一约束为 `(messageId, sourceContentHash, targetLanguage, providerKey)`。
- 只有成功译文写入缓存；撤回、内容清除或内容版本改变后旧 hash 不再命中。

### 7.3 自动与手动翻译

- 手动翻译请求当前消息和当前 App 语言；成功后在原消息下方显示译文，再次长按显示“隐藏译文”。隐藏只改变当前页面展示，不删除缓存。
- 会话自动翻译开启时，菜单“翻译”置灰；页面对当前可见且符合条件的消息进行去重、限量批量请求。
- 自动翻译不修改原消息正文，不把译文写入 `Message.metadata`。
- 同语言内容不调用供应商；服务端直接返回“不需要翻译”的明确结果。
- 系统文案、文件名、撤回残留、判断贴纸文字和运行时保护字段不进入第三方翻译。

### 7.4 失败处理

- 配额耗尽：显示“本月免费翻译额度已用完”。
- 限流：按配置进行有限次数指数退避，仍失败时显示“翻译请求较多，请稍后重试”。
- 超时或供应商不可用：显示“翻译服务暂不可用，请稍后重试”。
- 配置缺失：服务端返回配置错误并记录脱敏日志，前端显示服务暂不可用。
- 自动翻译失败保留原文，不循环重试；手动翻译失败后按钮恢复可点击。
- 绝不把原文作为成功译文返回或缓存。

参考：

- DeepL API Free 使用限制：https://developers.deepl.com/docs/resources/usage-limits
- DeepL 错误处理：https://developers.deepl.com/docs/best-practices/error-handling

## 8. API、权限与审计

正式接口统一位于 `/api/v1/`，全部使用 Bearer 鉴权、Zod、统一响应结构和 OpenAPI：

- `POST /im/conversations/:targetConversationId/chat-records`
- `GET /im/chat-records/:publicId`
- `GET /im/chat-records/:publicId/items?beforePosition=&page_size=`
- `POST /im/chat-record-favorites`
- `GET /im/chat-record-favorites?page=&page_size=`
- `DELETE /im/chat-record-favorites/:favoriteId`
- `POST /im/conversations/:conversationId/messages/delete-for-me`
- `POST /im/conversations/:conversationId/messages/translations`

转发、收藏和批量删除请求体只接受 1–100 个正整数消息 ID；翻译请求只接受 1–50 个消息 ID 和五种受支持目标语言，不接受客户端提交待翻译正文。详情列表 `page_size` 最大为 50。

新增并通过 migration 部署正式权限：

- `message:forward`
- `message:favorite`
- `message:translate`

批量删除继续使用 `message:list` 与来源会话成员资格；所有写动作记录不含消息正文的审计。控制器只负责解析请求和返回响应，业务事务在 Service，Prisma 访问仅在 Repository。

## 9. 幂等、并发与回滚

- 转发、收藏和批量删除请求携带幂等键；相同身份、路由和幂等键只能对应相同请求体。
- 消息在客户端选择后发生撤回、过期或权限变化时，以服务端事务开始时的状态为准，整批拒绝。
- 记录包数据库事务提交失败时删除本次新复制的媒体；媒体补偿失败进入结构化错误日志和清理队列，不返回成功。
- 前端提交期间锁定四个底部动作；失败保留当前选择，成功后退出多选。

## 10. i18n 与可访问性

- 所有新文案补齐 `zh`、`zh-Hant`、`ja`、`en`、`ko`。
- “选择到这里”的日语固定为“ここまで”。
- 圆圈使用真实复选语义和 `aria-checked`；顶部数量变化通过非打断式 live region 通知。
- 玻璃底栏和快捷菜单按钮保持可见焦点、44px 最小触控命中区；视觉按钮可压缩，但命中区不得缩小。
- 全屏详情关闭按钮提供明确 `aria-label`，关闭后焦点返回原聊天记录卡片。

## 11. 测试与验收

### 11.1 前端自动化

- 快捷菜单固定四列两行，八个动作顺序稳定；菜单玻璃类、箭头类和无滤镜下层规则不回退。
- 自动翻译开启时翻译置灰；手动翻译显示、隐藏和失败恢复。
- 多选初始锚点、圆圈切换、100条上限和零选择禁用。
- 上下按钮固定，滚动后按新按钮位置选择范围。
- 未滚动点击退出；实际滚动后抬手不退出；`pointercancel` 不退出。
- 文字手柄拖动不滚动列表并退出多选。
- 复制顺序、发送者前缀、多行文本和媒体占位符。
- 底部四动作 pending、成功和失败状态。
- 聊天记录卡片标题规则、预览、全屏关闭、焦点恢复和访问失败状态。
- 用户中心收藏分页、打开详情和移除收藏。

### 11.2 后端自动化

- Zod、RBAC、OpenAPI 和五语言错误键。
- 1/2/3名发送者标题、客户端伪造字段被忽略、100条上限和正式排序。
- 记录包、媒体复制、投递和收藏事务；数据库失败及文件补偿。
- 投递参与者、收藏者、创建者和未授权账号的访问边界。
- 批量删除原子性、幂等性、身份隔离、刷新后不复活且对方可见。
- DeepL 请求映射、同语言短路、缓存命中、内容 hash 失效、429退避、456配额、超时和配置缺失。

### 11.3 运行验收

- 390px 与 440px 宽度无横向溢出，菜单始终两行且占用面积明显小于当前动作区。
- 两个正式测试账号验证单条/多条转发、对方打开记录、发送者组合标题和关闭按钮。
- 验证收藏跨刷新、跨登录仍存在，用户中心入口可打开同一详情。
- 验证批量删除后操作者刷新仍不可见，对方刷新仍可见。
- 验证点击退出、滚动不退出、文字手柄退出和上下固定按钮。
- 配置真实 DeepL API Free 密钥后，验证中日英至少三组实际聊天文本；没有真实密钥时只能声明适配器测试通过，不能声明外部翻译已验收。
- 最终运行前后端定向测试、完整测试、TypeScript 检查、正式构建、产物审计和 `git diff --check`。

## 12. 实施顺序

本规格仍作为一个 Step 13 产品切片，但实施必须拆成可独立验收的小任务：

1. 聊天记录包 schema、migration、权限和 repository/service。
2. 转发创建、卡片与全屏详情。
3. 收藏关系、用户中心入口与详情复用。
4. 批量删除正式接口。
5. TranslationProvider、DeepL Free、缓存和正式翻译接口。
6. 紧凑两行菜单、多选状态、手势判定和底部玻璃动作条。
7. 五语言、完整回归与正式浏览器验收。

每个任务必须遵循测试先行，不得在前一任务未通过定向验收时进入下一任务。
