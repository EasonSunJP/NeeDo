# 店铺会员卡正式开卡设计

日期：2026-08-31  
状态：按用户“直接按最优方案执行”的既有授权进入实施  
范围：开卡微步骤，仅覆盖首次发卡，不包含充值、核销、退款或发卡后的余额/次数调整

## 1. 目标

把现有“卡方案配置”与真实会员关系连接起来，使当前店铺具备可审计、可授权、可幂等重放的正式开卡能力：

- 只能向当前店铺的有效会员发卡；
- 只能使用当前店铺已发布且仍启用的卡方案版本；
- 储值卡可录入初始本金，次数卡可录入初始次数，权益卡不录入金额或次数；
- 初始值必须落在发布版方案设定的上下限内；
- 开卡不赠送 NDP、不扣店铺钱包、不写 NDP 账本；
- 卡绑定不可变的方案版本和发布时平台费率快照；
- 开卡、审计日志和客户站内通知在一个数据库事务中完成；
- 商家端提供成熟、移动优先的开卡流程；用户端可查看真实卡状态及绑定的方案版本；
- 所有会员相关入口和新增界面继续显示 `TEST` 角标。

## 2. 方案比较与选择

### 方案 A：直接在现有会员服务中创建一张自由格式卡

优点是改动少；缺点是会绕过已发布卡方案，初始值、有效期和平台费率无法稳定追溯，也不利于未来核销与返点行为按版本执行，因此不采用。

### 方案 B：新增独立开卡服务，绑定发布版方案快照

开卡服务负责校验当前店铺、有效会员、有效方案、类型字段、上下限、有效期和幂等；仓储在同一事务写入卡、审计和通知。该方案边界清晰，并为后续充值、核销、退款及经客户同意的调整保留独立状态机，采用此方案。

### 方案 C：本步同时实现开卡、充值、核销、退款和调整确认

该方案会把多种资金与次数状态机合并，违反项目微步骤要求，也难以独立回滚和验收，因此不采用。

## 3. 数据模型

在 `ShopMembershipCard` 上新增可空字段，以兼容历史卡；本步新发卡时全部按业务规则写入：

- `planId`：绑定所属卡方案；
- `planVersionId`：绑定开卡时已发布的不可变版本；
- `issuedById`：实际操作人；
- `issuanceSource`：`OFFLINE_PAID`、`HISTORICAL_REPLACEMENT` 或 `MANUAL_GRANT`；
- `issuanceReference`：线下票据或业务参考号；
- `issuanceNote`：开卡说明；
- `initialPrincipalJpy`：储值卡开卡本金快照；
- `initialUses`：次数卡开卡次数快照；
- `platformFeeRateBpsSnapshot`：发布版平台费率快照；
- `issuanceIdempotencyKey`：客户端生成的请求幂等键，唯一；
- `issuanceFingerprint`：规范化请求的 SHA-256 指纹，用于识别同键不同请求。

卡号由后端使用密码学安全随机数生成，格式为 `NMC-` 加大写十六进制随机串；数据库唯一约束作为最终防线。卡号不会由客户端提供，公开 API 继续只返回脱敏值。

历史卡保持可读，但不会伪造方案、操作者或费率快照。

## 4. 开卡输入与规则

正式接口：

`POST /api/v1/merchant-admin/shop-memberships/:publicId/cards`

请求体：

```json
{
  "planPublicId": "uuid",
  "initialPrincipalJpy": 10000,
  "initialUses": null,
  "issuanceSource": "offline_paid",
  "issuanceReference": "receipt-20260831-001",
  "issuanceNote": "客户已在线下付款",
  "idempotencyKey": "uuid-or-client-generated-key"
}
```

校验规则：

- `stored_value`：`initialPrincipalJpy` 必填且在方案范围内，`initialUses` 必须为空；卡本金等于初始本金，奖励余额固定为 0；
- `count`：`initialUses` 必填且在方案范围内，`initialPrincipalJpy` 必须为空；剩余次数和总次数都等于初始次数；
- `benefit`：两类初始值都必须为空；
- `offline_paid`：必须提供参考号或说明中的至少一项；
- `historical_replacement` 与 `manual_grant`：必须提供说明；
- 请求中的所有文本先去除首尾空白；
- 同一幂等键与相同规范化请求重放时返回同一张卡，不新增审计或通知；同键不同请求返回 409；
- 会员或方案不属于当前店铺时统一按找不到处理，防止跨店枚举；
- 已结束会员、草稿/停用方案、非当前已发布版本或已过固定有效期均不可开卡。

## 5. 有效期

开卡时间由服务端时钟生成。有效期严格来自发布版方案，商家不能在开卡请求中绕过：

- `never`：`expiresAt = null`；
- `fixed_days`：`expiresAt = issuedAt + days × 24 小时`。日本无夏令时，语义稳定且便于测试；
- `fixed_date`：直接复制方案版本的固定到期时间；若开卡时已经到期则拒绝。

后续如需为历史补卡修改有效期，应作为独立的、需要客户同意的调整流程，不在本步暗中放宽。

## 6. 事务、审计与通知

仓储在单个 Prisma 事务中：

1. 再次读取并确认当前店铺的有效会员；
2. 再次读取并确认当前店铺有效方案及其当前已发布版本；
3. 检查幂等键；
4. 创建会员卡；
5. 写入 `merchant.shop_membership_card.issue` 审计日志；
6. 为会员所属用户写入 `SYSTEM` 站内通知。

审计 metadata 仅保存公开标识、卡类型、初始值、开卡来源、方案版本和费率快照，不记录完整卡号。通知使用 i18n key 作为 title/body，并在 payload 中携带会员、会员卡、店铺和方案公开标识，便于现有通知层实时投递与页面跳转。

事务中任何一步失败都不留部分卡、部分审计或部分通知。

## 7. RBAC 与身份范围

新增权限 `shop.member.card.issue`：

- 默认授予 `merchant_owner`；
- 不默认授予 `merchant_staff`，由店铺角色管理按需授权；
- 路由在 JWT 鉴权、权限鉴权之后执行；
- 服务仍验证当前激活身份为商家身份且具有 shop scope；
- 数据查询始终包含当前 `shopId`，不接受客户端传入店铺 ID。

## 8. API 返回

首次创建返回 201，幂等重放返回 200。返回结构包含：

- 卡公开 ID、脱敏卡号、名称、类型、状态；
- 初始值与当前值；
- 开卡来源、说明、开卡时间和有效期；
- 方案公开 ID、版本公开 ID、版本号、方案名；
- 平台费率快照；
- `replayed` 标记。

客户读取接口和商家卡列表同步扩展上述安全字段；内部数据库 ID、完整卡号和操作者内部 ID不对外返回。

## 9. 商家端交互

“已发会员卡”页顶部新增 `开卡 TEST` 主按钮。底部弹层采用三段式单页流程，避免手机端多层跳转：

1. 搜索并选择当前店铺有效会员；
2. 选择已启用的发布版卡方案，展示卡类型、版本、有效期、NDP 规则摘要及平台费说明；
3. 按卡类型录入初始金额或次数，选择来源，填写参考号/说明并确认。

前端只做即时引导，后端仍是最终规则权威。成功后关闭弹层、刷新卡列表，并显示成功卡片；错误保留输入并显示可理解反馈。无权限时不显示开卡按钮。

## 10. 用户端

个人中心会员入口保持现有店铺分组。会员卡展示补充：

- 绑定方案名与版本；
- 当前状态、余额或剩余次数；
- 开卡时间与有效期；
- 开卡来源的友好文案；
- 平台费率和返点只作为规则说明，不把开卡误写成已发生返点。

## 11. 明确不做

- 不自动增加 NDP；
- 不写钱包或 NDP 账本；
- 不做充值、核销、退款；
- 不做开卡后的金额或次数调整；
- 不做客户同意调整流程；
- 不把礼物或折扣重新引入卡方案；
- 不推送、不部署线上。

## 12. 验收

- 单元测试覆盖三种卡类型、上下限、来源要求、有效期、幂等和错误映射；
- 路由集成测试覆盖鉴权、RBAC、Zod、201/200/409 和跨店隔离；
- 仓储/真实数据库验收覆盖卡、审计、通知的一致写入及失败回滚；
- 证明开卡前后店铺钱包、客户 NDP 钱包和账本没有变化；
- 前端组件测试覆盖权限、三类字段、费率提示、提交和成功刷新；
- lint、完整测试和 build 通过；
- 本地窄屏浏览器检查登录守卫、布局、滚动、错误态与控制台。
