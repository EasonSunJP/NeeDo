# 技师个人中心、详情卡、服务信息卡与评价标签统一设计

**日期：** 2026-09-03

**适用阶段：** Step 09 前端第一批去 mock，并对其依赖的正式资料、评价与服务只读契约做最小增量

**状态：** 对话规则已确认，待用户复核本文档

**范围：** 技师端个人中心、技师公开详情页、用户最终评价、跨页面服务信息卡

## 1. 目标

本次工作把现有分散的技师资料卡、悬浮详情卡和服务信息卡收敛为正式数据驱动的统一实现：

1. 技师个人中心不显示底部导航。
2. 技师资料编辑交互与用户端一致：右上角关闭编辑，底部固定“保存并退出编辑模式”。
3. 技师个人中心和公开详情页复用同一份只读资料卡结构与展示组件。
4. 点击技师信息卡进入完整详情页，不再弹出悬浮窗口。
5. 固定四项特殊评价标签和用户自定义评价标签都从正式订单评价记录汇总，不使用硬编码次数。
6. 服务信息卡在所有实际“服务信息”场景使用同一共享组件和同一字段顺序；技师管理场景只额外增加排序与编辑操作。
7. 个人中心的服务信息区移除外层容器框，使服务卡使用完整内容宽度。

本设计不扩张 legacy mock，不以 `ServiceItem.sales`、评价数或静态数组冒充利用回数，也不把首页分类入口、纯图片导航块等非信息卡组件强行改造成服务信息卡。

## 2. 已确认的页面结构

### 2.1 技师个人中心

页面顺序固定为：

1. 全屏页头和“信息卡 / 数据中心”切换。
2. 头像、姓名、身份、公开技师 ID。
3. 第一行指标：从业年数、接单率、评价。
4. 第二行指标：完成订单数。
5. 基础信息。
6. 服务信息。

个人中心的“信息卡”和“数据中心”均不显示底部导航。

### 2.2 基础信息内部顺序

基础信息内部顺序固定为：

1. 性别、年龄、身高，同一行三列。
2. 语言能力。
3. 自我介绍。
4. 特殊标签。
5. 标签。
6. 隐私模式，作为基础信息最后一项。

用户端个人中心同步遵守“隐私模式位于标签下面、基础信息最末”的位置规则，避免两端表现不一致。

### 2.3 服务信息区

“服务信息”位于基础信息之后，是独立区块，但区块本身不使用边框、底色包裹或嵌套大卡片。区块只保留：

- 标题与添加服务操作；
- 定价模式读取状态；
- 加载、错误和空状态；
- 各张服务卡自身的边界。

技师端服务卡保留上移、下移和编辑按钮。按钮属于服务卡操作层，不改变共享服务卡的内容结构。

## 3. 编辑模式

技师端与用户端使用相同的编辑状态模式：

- 进入编辑后，右上角编辑按钮变为红色关闭按钮。
- 关闭按钮退出编辑且丢弃尚未保存的本地草稿，不发送更新请求。
- 页面底部出现固定“保存并退出编辑模式”操作。
- 保存成功后刷新正式资料并退出编辑；失败时保留草稿和错误提示。
- 保存中禁用重复提交、关闭和隐私切换。

技师可编辑的个人资料包括性别、年龄、身高、语言能力、自我介绍和隐私模式。评价产生的特殊标签、评价标签及其次数均为只读，技师不能修改或删除。

## 4. 评价标签规则

### 4.1 固定特殊标签

特殊标签始终显示以下四项，即使次数为零也不能显示空状态：

- 魅力max
- 服务max
- 情绪max
- 元气max

四项在用户对技师的最终订单评价中允许多选。每个已完成订单对同一固定标签最多贡献一次计数，因此一个订单可为零至四项分别 `+1`。

### 4.2 自定义评价标签

用户每次服务评价最多新增一个自定义标签。自定义标签规则为：

- 同一订单只保存一次同一文字；
- 下一次服务再次选择或输入同一文字时，累计到同一标签；
- 只出现一次时只显示标签文字，不显示 `×1`；
- 从第二次开始显示 `×2`、`×3` 等累计次数；
- 自定义评价标签展示在基础信息的“标签”栏；
- 该栏替换技师自编辑的普通标签展示与编辑能力。

标签文字沿用正式评价的 NFKC、首尾空白清理、不可见字符拒绝和 Unicode case-fold 去重规则。固定标签的历史旧名称通过显式别名归一到新的四项展示名称，避免已有正式评价次数丢失。

### 4.3 正式约束

约束不能只存在于前端：

- 当 `targetType=technician` 时，API 允许固定四项的任意子集，并最多允许一个非固定标签。
- 重复标签在标准化后拒绝。
- 评价仍保持每个订单、评价人、目标类型唯一且提交后不可修改。
- 当 `targetType=customer` 时保留现有客户评价标签规则，不套用技师的四项特殊标签限制。

### 4.4 计数来源

次数从未删除的 `OrderReview` 与 `OrderReviewTag` 正式记录汇总，且只统计：

- `targetType=TECHNICIAN`；
- 目标技师一致；
- 评价和标签均未软删除；
- 评价已经通过现有完成订单、结算凭证和唯一性校验。

前端不做乐观累计持久化，不读取 `serviceReviewSpecialTags` 中的静态示例次数。

## 5. 技师资料数据契约

### 5.1 性别

`TechnicianProfile` 增加与用户资料一致的性别字段及默认隐私值，并通过 additive migration、Prisma schema、repository、service、Zod、OpenAPI 和前端类型完整贯通。

允许值与用户端一致，不在前端自创不同枚举。公开详情必须遵守技师资料可见性，不能因新增字段绕过隐私模式。

### 5.2 指标

技师个人中心和公开详情共同读取：

- `yearsExperience`；
- `acceptanceRatePercent`；
- `reviewSummary.ratingAverage` 与 `reviewSummary.reviewCount`；
- `completedOrderCount`。

不以钱包余额、城市或评价次数冒充这些指标。接单率和完成订单数继续使用正式 `TechnicianPerformanceSummary`。

### 5.3 评价标签汇总

技师详情契约增加结构化评价标签汇总，而不是只返回无次数的 `highlights`。建议返回：

```ts
type TechnicianReviewTagSummary = {
  special: Array<{
    code: "appeal_max" | "service_max" | "emotion_max" | "energy_max";
    label: string;
    count: number;
  }>;
  custom: Array<{
    label: string;
    count: number;
  }>;
};
```

固定四项按产品顺序返回，包含零次项；自定义标签按次数降序、首次出现时间和稳定文字顺序做确定性排序，并设置合理上限以控制详情响应大小。

## 6. 技师公开详情页

`/profiles/technician/:id` 及商户端、技师端对应 scoped route 改为完整技师详情卡页：

- 使用全屏页头和返回/关闭动作；
- 不再把技师 route 默认转到动态主页；
- 页面主体复用个人中心的只读资料卡组件；
- 资料字段、指标、标签、服务信息的顺序和表现与个人中心一致；
- 动态主页若仍需访问，作为详情页中的明确次级入口，不作为信息卡点击的默认结果。

所有技师卡入口统一导航到 scoped detail route。移除 `SocialProfileMiniCard`、`TechnicianShowcaseCard`、店铺技师列表等入口对 `TechnicianPublicInfoCardModal` 的依赖，避免同一个实体有页面和悬浮窗两套详情体验。

## 7. 统一服务信息卡

### 7.1 字段与顺序

共享服务信息卡按下列顺序展示：

1. 服务封面。
2. 服务名称。
3. 粗体高亮价格和时长，例如 `￥1,000/60分钟`。
4. 利用回数。
5. 店铺公开 ID。
6. 店铺地址。
7. 简介。
8. 标签。

店铺 ID 使用公开标识，不显示数据库自增主键。价格统一按币种和地区格式化，不拼接重复时长或错误含税文案。

### 7.2 利用回数

利用回数来自关联服务的正式已完成 `BookingOrder` 数量：

- 普通店铺服务按 `serviceId` 统计；
- 技师自营服务按 `technicianServiceId` 统计；
- 只统计未软删除且状态为 `COMPLETED` 的订单；
- 不使用评价数量、卡片曝光或 legacy `sales` 字段代替。

查询通过关系 `_count`、条件计数或批量聚合完成，禁止为列表中的每张卡单独查询。

### 7.3 共享组件边界

建立一个正式 DTO 到共享展示模型的 mapper 和一个共享 `UnifiedServiceInfoCard`。用户首页推荐、搜索/分类结果、店铺详情、技师服务列表、个人中心及公开技师详情中的实际服务信息卡都复用它。

管理动作通过可选 action slot 注入：

- 用户端无管理动作；
- 技师端显示上移、下移、编辑；
- action slot 不复制卡片正文。

纯分类入口、宣传轮播和只承担导航作用的图片 tile 不属于服务信息卡，不在本次强制改造范围内。

## 8. 错误、空状态与隐私

- 正式资料或服务读取失败时显示可重试错误，不回退到 legacy mock。
- 技师没有服务时显示明确空状态和添加服务入口，不渲染假服务。
- 四个固定特殊标签即使均为零也照常显示。
- 没有自定义评价标签时，“标签”栏显示明确的暂无评价标签状态。
- 隐私模式开启后，公开详情 API 和列表卡遵守现有可见性策略；个人中心本人仍可查看和编辑自己的资料。
- 店铺公开 ID 或地址缺失时显示诚实的“未公开/未设置”，不能回退到数值主键或编造地址。

## 9. 实施微步骤

为符合小步、可运行、可回滚要求，实施拆为以下顺序，每一步先写失败测试：

1. 正式评价标签规则与技师标签汇总契约。
2. 技师性别和详情字段契约。
3. 服务卡正式字段：利用回数、店铺公开 ID、地址与标签。
4. 共享技师资料卡和全屏详情 route，移除悬浮入口。
5. 技师个人中心布局、编辑模式、隐私位置和服务外框移除。
6. 统一服务信息卡迁移到实际信息卡场景。
7. 用户端隐私位置同步与跨端回归。

每个微步骤只提交自身文件，不能把当前工作区的无关改动混入。

## 10. 验收

### 10.1 自动化

- Prisma schema/migration contract test。
- 技师资料 validator、repository、service、API 与 OpenAPI 测试。
- 评价标签 validator、repository、service、API 测试。
- 固定标签多选、每订单唯一、自定义标签每单最多一个、同名跨订单累计测试。
- `×1` 隐藏、`×2` 起显示的组件测试。
- 服务利用回数只统计完成订单的 repository/API 测试。
- 个人中心布局、无底部导航、固定保存按钮和服务区无外框测试。
- 所有技师卡入口不再渲染悬浮详情组件、统一导航到详情 route 的测试。
- 共享服务卡在各页面的契约测试。
- 前端 lint、targeted tests、build；后端 targeted tests、lint、build。

### 10.2 浏览器验收

在标准本地运行时先确认监听 PID、进程 cwd、分支和前端代理源，再用登录态验证：

1. 技师个人中心信息卡和数据中心均无底部导航。
2. 编辑、关闭、保存退出与用户端交互一致。
3. 基础信息顺序正确，隐私模式位于标签下面。
4. 四项特殊标签始终存在并显示真实次数。
5. 自定义标签首次无次数，重复评价后显示 `×2`。
6. 完成订单数位于第一行三个指标下方。
7. 服务信息位于基础信息之后且无外层容器框。
8. 服务卡字段和顺序正确，店铺 ID 为公开格式，利用回数来自完成订单。
9. 上移、下移、编辑仍可操作并持久化。
10. 从首页、分类、店铺详情、订单参与人等技师入口点击后进入完整详情页，不出现悬浮窗口。
11. 公开详情内容与个人中心只读卡一致，隐私模式生效。
12. 移动宽度下无横向溢出，控制台无新增错误。

## 11. 非目标

- 不在本次重做动态主页、社交关注或聊天关系。
- 不改变客户评价技师之外的商户评价中心规划。
- 不新增评价编辑或删除能力。
- 不把未完成订单计入标签或服务利用回数。
- 不重构全部前端路由、主题 token 或三端入口。
