# 商户服务卡与预约详情统一设计

## 目标

商户端不再维护独立的服务信息卡和预约详情视觉。服务卡、详情头部、预约状态、资料分区与事实信息均复用用户端已经上线的共享组件；商户端只保留业务角色差异。

## 已确认界面

- 服务信息卡只使用 `UnifiedServiceInfoCard`。商户首页“今日预约”和商户订单列表移除卡片外的第二层商户专用面板、专用状态角标、快捷联系/转发浮层及独立“预约详情”按钮；整张共享卡直接进入预约详情。
- 共享服务卡继续保留其正式公开字段契约，包含店铺公开 ID 与地址；本次不按端别隐藏或复制字段。商户入口与用户入口渲染同一个组件、同一字段顺序和同一缺失数据状态。
- 服务详情使用 `MobileFullscreenHeader` 的玻璃容器。左侧为通用返回；右侧依次为爱心收藏、转发、关闭。不再显示点赞、星标和翻译三套含义重叠的动作。
- 商户预约详情使用与用户预约详情相同的 `PageScaffold`、`AppTopBar`、`OrderDynamicStatusCard`、服务卡、资料分区、事实网格和联系时间线。
- 商户预约详情不展示服务验证码。固定底部左侧为“联系用户”，右侧为“联系技师”；未分配技师时“联系技师”不可用并给出明确的无障碍说明。
- 可取消的普通预约在头部关闭按钮左侧只显示一个红色“取消预约”按钮。Exchange 关联预约继续走既有双方取消流程，不开放不合法的普通强制取消。
- 点击红色取消按钮打开共享红色危险确认窗口，明确提示：“强制取消预约可能引起用户差评，并会降低接单率数值。是否真的要取消此预约？”确认后调用现有正式 `POST /api/v1/orders/:id/cancel`，成功后立即采用服务端返回订单；失败时保留窗口并显示正式错误。

## 组件边界

- `UnifiedServiceInfoCard`：唯一服务卡视觉和字段顺序。
- `OrderDetailSection` / `OrderDetailFactGrid`：用户端与商户端共用的预约详情分区和事实卡。
- `DangerConfirmDialog`：通用红色高风险确认窗口，负责可访问的 dialog 结构、危险视觉和确认/取消/错误状态。
- 页面组件只负责查询、角色动作、路由目标和状态更新，不复制共享视觉实现。

## 设计系统

- 颜色继续使用现有 `--client-*` token；危险操作仅使用既有红色语义色，不引入新的主题。
- 字体、圆角、阴影和玻璃质感沿用当前 NeeDo 移动端系统。
- 页面唯一强调点是红色强制取消风险窗口；其余界面保持用户端既有信息层级。
- 390–440px 移动宽度必须无横向溢出，键盘焦点清晰，按钮具备可访问名称；共享头部和危险窗口继续沿用既有移动端响应式容器。

## 数据与错误处理

- 不新增 API、数据库字段、mock 或固定业务数值。
- 卡片只展示当前正式响应已有的服务快照或公开资料；缺失图片、时长、次数、简介和标签使用共享不可用状态。
- 取消动作以服务端权限、状态机和赔付逻辑为准；409 等错误经现有商户预约错误映射显示，不做乐观伪成功。

## 测试

- 先新增失败测试，锁定共享卡字段、商户入口委托、玻璃头部动作顺序、共享危险窗口、商户预约详情结构、角色按钮、验证码隐藏和取消调用。
- 专项 Vitest 通过后运行 TypeScript lint、完整前端测试、生产构建，并验证本地监听进程、cwd、分支和登录权限边界。已登录页面结构与交互由路由级 jsdom 测试覆盖；真实浏览器登录验收单独记录结果。

## 自检

本设计没有占位项、未定义数据来源或并行视觉方案。它不改变预约状态机，只统一表现层并接通已有正式取消能力。
