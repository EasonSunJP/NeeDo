# 我的排班：可排班范围与预约占用分离设计

## 目标

在不重做现有日历视觉与基础交互的前提下，把“技师愿意接受预约的时间范围”“真实预约占用”“普通日程”“店铺排班控制权”拆成独立业务事实，并将技师出勤、Booking 自动接单、Request 自动应募和店铺调度接入同一套正式数据。

## 权威规则

- 本文以用户在 2026-09-09 当前对话中的订正为最终产品定义；附件只用于补充自动化规则背景。
- 排班决定什么时候愿意接单，预约决定什么时候已经被占用。
- 预约不得删除、缩短、拆分或关闭可排班时间。
- 只有两个及以上有效预约订单发生时间重叠时，日历才显示红色预约冲突。
- 排班、普通日程与预约重叠不属于预约冲突。
- 同一技师的同一时段只能由一个店铺拥有店铺排班控制权。
- 保留全部现有日程和测试数据；不执行清理或回填删除。

## 领域模型

### 可排班时间

继续以 `Availability` 作为技师愿意接单的正式时间范围：

- `sourceType=TECHNICIAN`：自由排班，由技师本人维护，显示“自由排班”。
- `sourceType=SHOP`：店铺排班，由 `shopId` 指定的店铺控制，显示“{店铺名称}店铺排班（可排班日程）”。

Booking 只读取 Availability，不反向修改 Availability。现有 `ScheduleSlot` 继续承担具体服务槽位与订单容量职责，不再作为任意长度排班窗口或普通日程的唯一载体。

### 预约占用

`BookingOrder` 是预约占用的唯一权威来源。有效预约冲突集合为 `PENDING`、`CONFIRMED`、`IN_SERVICE` 且未软删除的订单；`CANCELLED`、`COMPLETED` 不参与当前冲突红框。

自动动作仍在服务端检查完整 Availability 包含关系、有效预约/缓冲冲突、出勤、资格、服务、风控和设置规则。任一条件失败时回到人工流程，不自动拒绝。

### 非预约日程

新增正式 `CalendarEvent` 聚合，按拥有者身份隔离，保存标题、起止时间、全天、地点、URL、备注、提醒、重复规则、可见性、参与者和必要的媒体引用。它既不是 Availability，也不是 BookingOrder，因此与预约重叠不会触发预约冲突。

用户端只能创建普通日程。技师端新增行程提供互斥选择：

- “可排班”开启：创建自由排班 Availability。
- “手动预约”开启：通过正式 Booking 服务创建人工预约。
- 两者都关闭：创建普通 CalendarEvent。

两个开关不可同时开启。

### 店铺排班权与候选关系

复用现有 `TechnicianShopAffiliation.PARTNER` 表达候选/合作关系，不新增平行候选池。该关系只提供合作可见性和安排资格，不自动获得排班控制权。

店铺创建 `sourceType=SHOP` 的 Availability 时，在同一事务内锁定技师并检查所有店铺来源 Availability；如果任何其他店铺在目标时段有有效重叠，拒绝创建并把该时段投影为锁定。自由排班与预约可以重叠，但自由排班不能覆盖已有店铺排班控制窗口。

## 修改与取消

技师可以点击店铺排班查看、修改或取消。写操作先返回影响预览：

- 没有受影响的确定预约：提示“此次改动可能影响店铺安排”。
- 存在会落到新范围之外或因删除失去安排依据的确定预约：列出订单并提示取消及评价风险。

用户二次确认后，服务端在同一事务边界内修改/软删除排班，并通过现有 Booking 取消服务处理真正受影响的预约、状态历史、通知、审计和评价归因，禁止前端直接改订单状态。

## 日历投影与冲突显示

统一日历分别投影 Availability、BookingOrder 和 CalendarEvent，不在读取层互相相减。

预约冲突计算只比较有效 BookingOrder。若两个及以上订单存在交集，相关预约事件使用红色边框；排班范围保持原来源颜色，普通日程保持普通颜色。

技师与用户继续复用 `UnifiedUserCalendar`、`ScheduleDraftRangeBlock` 和拖动/上下手柄。技师不再使用并行店员视图；其“我的排班”与用户端保持相同单人日历结构，并额外显示排班来源和技师专属创建类型。

## 页面改动

- 技师“我的排班”移除底部“状态记录”面板，但不删除状态历史数据。
- 技师新增按钮改用首页“预约一览”相同的 `FloatingActionButton` 标准位置。
- 用户日程恢复悬浮新增按钮，并允许点击/拖动时间轴进入正式新增行程。
- 技师新增行程标题下方显示并列的“可排班｜手动预约”胶囊开关；用户端不显示。
- 在统一日程编辑器内选择“可排班”后，直接通过正式 Availability API 创建或修改时间范围并回写当前日程表；正常流程不得再跳转到 `/technician/schedule/new`，也不得再显示第二套 24 小时时间表。旧路由仅保留给历史直达链接兼容。
- 技师点击“出勤”成功后，在同步状态卡中显示“自动接单”“自动抢单”开关；两处直接读写现有自动化设置 API 与版本，和设置页面保持同步。

## API、并发与审计

- 新增身份隔离的 CalendarEvent CRUD API，Zod 校验、分页读取、软删除、RBAC 和审计齐全。
- 新增 Availability 窗口 CRUD/影响预览 API，复用当前 Booking 路由分层或在其下建立聚焦服务。
- 手动预约新增技师授权入口，但最终调用现有 Booking 状态机和事务能力；不创建平行订单表。
- 店铺排班唯一性、手动预约冲突、自动动作候选判断均在服务端事务内校验。
- 所有写操作使用幂等键或乐观版本，避免重复日程、重复预约和覆盖并发修改。

## 验证

- 领域与服务单元测试：排班不被预约裁剪、仅预约与预约标红、来源标签、互斥开关。
- API/仓库集成测试：店铺排班权同时段唯一、自由排班重叠预约、CalendarEvent 身份隔离、手动预约冲突、影响预览和确认取消。
- 前端组件测试：用户/技师创建入口、拖动范围、技师专属开关、状态记录移除、FAB 位置、出勤后自动化开关同步。
- `typecheck`、`lint`、后端 build、正式前端 build、相关完整测试。
- 如启动页面，仅使用确认空闲的 5181/5182；5180 完全不操作。
