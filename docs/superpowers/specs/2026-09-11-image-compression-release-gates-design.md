# NeeDo 图片压缩与发布门禁设计

日期：2026-09-11

修订：2026-09-12，用户上传改为上传设备本地压缩、服务器强制验证

范围：静态运行图片、用户上传图片、发布前验证

目标环境：本地开发、GitHub `origin/main`、staging；不包含 production 部署

## 1. 目标

NeeDo 在不明显降低视觉质量、不破坏现有 URL、数据库引用、透明通道、动画和审核证据的前提下，降低前端发布包与用户上传图片的存储和传输体积。

图片处理必须完全在本地开发机、用户设备、技师设备、商户设备或运营人员浏览器中执行，不调用 TinyPNG 或其他外部压缩服务。后端服务器不承担常规图片压缩，只执行不可省略的安全、权限、结构与一致性验证。没有通过图片压缩与质量验证的版本不得推送发布分支或部署。

## 2. 非目标

- 本步骤不部署 production。
- 不处理视频、音频或 PDF 压缩；这些媒体需要独立的编码与验收策略。
- 不批量改写已有数据库媒体 URL。
- 不删除身份证、营业执照等敏感审核材料的原件。
- 不把设计原件、`.data` 备份或后端 runtime 上传目录纳入静态发布包。

## 3. 处理边界

### 3.1 静态运行图片

纳入版本化压缩与校验：

- `public/` 中会进入 `dist/` 的 JPEG、PNG、WebP。
- `src/assets/runtime/` 中由 Vite 打包的 JPEG、PNG、WebP。

排除自动改写：

- `design/source-assets/` 中的设计原件。
- `.data/`、`output/`、`outputs/` 与临时工作目录。
- `backend/runtime/`、正式媒体存储目录和数据库已引用的运行媒体。
- SVG、视频、音频、PDF、PSD、AI 等非 raster 发布图片。

### 3.2 用户上传图片

上传端本地压缩覆盖：

- 用户、技师和商户头像。
- IM 与 Social 图片。
- 首页轮播图、官方通知图片、店铺展示图、服务封面。
- 身份申请材料的页面预览图。

用户端、技师端、商户端和运营后台网页都必须在各自浏览器或 App 本机完成缩放、元数据清除、压缩和质量比较，再把合格结果上传。运营后台网页中的“后台上传”仍属于运营人员电脑上的浏览器本地处理，不得转移给后端服务器。

服务器收到结果后不做常规重编码，但必须独立完成鉴权、RBAC、所有权、请求长度、真实格式、受限解码、像素数、帧数、用途约束和 SHA-256 校验。服务端不能相信客户端声明的 MIME、尺寸、哈希或“已压缩”标记。不合格文件直接拒绝，不能静默转为服务器压缩。

## 4. 静态图片压缩方案

新增一个显式写入命令和一个只读门禁命令：

- `npm run optimize:production-images`：使用项目锁定版本的本地 `sharp/libvips` 压缩目标图片并更新 manifest。
- `npm run verify:production-images`：只读验证所有目标图片已登记、哈希匹配、能成功解码并满足质量与体积规则。

`npm run verify:production-build` 必须包含 `verify:production-images`。压缩命令不得在普通 build 中静默改写源码。

每张图片的 manifest 至少记录：相对路径、处理状态、原始 SHA-256、结果 SHA-256、原始/结果字节数、宽高、格式、Alpha、帧数、压缩配置、质量结果与例外原因。处理状态固定为 `optimized`、`lossless` 或 `kept-original`；只有动画不可安全重编码、没有体积收益或候选结果未通过质量门槛时才允许 `kept-original`，并且必须记录机器可校验的原因。新增或修改图片没有匹配 manifest 时，门禁失败。只读门禁校验当前文件与结果 SHA-256；原始 SHA-256 作为本次优化和 Git 审计证据，不要求仓库额外保留一份原图副本。

压缩命令必须先写入同目录受限临时文件，完成解码、结构、质量和体积校验后再原子替换；任何一步失败都保留当前 Git 文件不变。manifest 最后写入，不能记录未成功落盘的结果。

压缩规则：

- JPEG 使用本地 mozjpeg 编码，默认质量从 88 开始；禁止放大尺寸。
- 普通 PNG 优先使用高质量 palette 量化和最高压缩 effort，保持 PNG 路径、尺寸和 Alpha。
- 含文字、品牌图形、细线图标、二维码及关键 UI 图片使用无损或更高质量配置。
- WebP 使用固定质量和 effort 重新编码，仅在体积确实下降时替换。
- APNG、animated WebP 或其他多帧图片只有在帧数、循环和时长可验证时才允许压缩；否则保留原文件并在 manifest 中记录例外原因。
- 压缩结果节省不足 10% 且不足 32 KiB 时保留原文件，避免无意义重编码。
- 不删除仅凭静态搜索无法确认是否被 Seed 或数据库引用的图片。

## 5. 视觉质量硬门槛

压缩率不能覆盖质量失败。静态图片在开发机本地比较，用户上传图片在上传设备本地比较；每张候选结果都必须先解码，再与原图比较：

- 静态版本化图片的宽度、高度、视觉方向和帧数必须保持；任何非预期变化直接失败。
- 需要透明度的图片必须保留 Alpha，透明边缘不得出现黑边、白边或色带。
- 无损类别的解码像素必须完全一致。
- 摄影和插画类近无感压缩的结构相似度 SSIM 必须不低于 `0.99`。
- 关键 UI、文字、图标、排名标识和品牌图片使用无损，或 SSIM 不低于 `0.995` 并通过人工对比。
- 身份证件和需要 OCR 的材料原件不做有损压缩；压缩预览不能作为原件或 OCR 唯一输入。
- 未达到阈值时按更高质量重新编码；仍不合格则保留原图并记录原因。不得为了追求总体压缩率而降低单图阈值。

人工验收至少覆盖发布包中体积最大的图片、节省比例最高的图片，以及登录页、三端启动页、首页轮播图、头像/资料卡、IM/Social 图片、服务卡、排名图标、宠物素材和错误页。需要在移动端宽度、明暗主题和实际浏览器渲染中检查模糊、色带、文字边缘、透明边缘与裁切。

## 6. 用户上传图片架构

在现有上传调用点前增加共享的客户端图片优化能力，并继续复用后端既有 storage/service/repository 分层，不创建第二套媒体系统：

```text
Browser / App upload entry
  -> 在 Worker 或受控异步任务中按固定用途配置读取、定向、缩放、清除元数据、压缩、SSIM 和结果预览
  -> 只上传通过本地质量与体积门槛的 Blob/File
Route / Controller
  -> 鉴权、RBAC、请求长度与 Content-Type 输入校验
Service
  -> 业务用途、所有权、真实格式、受限解码、像素/帧/尺寸校验、事务和审计
Storage
  -> 不重编码，原子写入已经验证的最终字节
Repository
  -> 保存最终 URL、MIME、宽高、字节数、SHA-256 与审计证据
```

公开展示类图片只保存通过客户端门禁和服务端验证的优化版本。优化后的真实 MIME 和扩展名必须一致，API 返回值和数据库字段以服务器实际验证、计算和保存的最终文件为准。

敏感身份申请材料采用双产物：

- 原件：上传端不得有损压缩，仅保存到隔离的私有存储；服务器计算原始 SHA-256，继续受现有敏感读取权限和留存策略控制。
- 预览：由同一上传设备从原件本地生成，移除元数据并压缩后单独上传；普通界面只读取预览。
- 关联验证：服务器对原件和预览分别执行受限解码与格式校验，按视觉方向归一化后缩小到最长边不超过 256 像素的内存参考图，并要求两者 SSIM 不低于 `0.98`；不通过则整组拒绝。审核与 OCR 始终以原件为权威，预览不能单独改变审核结论。该低分辨率比较只用于低频敏感材料，不执行重编码落盘，也不应用于普通公开图片上传。

整个流程不得输出原始图片内容、data URL、私有路径或敏感元数据到日志。客户端不得把原图或中间画布写入长期浏览器存储；服务器临时文件必须使用受限权限并在成功或失败后清理。

## 7. 用途配置

客户端优化器使用代码内锁定的明确用途配置，而不是让页面调用方或最终用户自行传任意质量参数：

- `avatar`：按现有展示需求限制头像尺寸，优先近无感 WebP/JPEG；保留透明头像的 Alpha。
- `im`：按现有消息展示需求限制最长边，删除元数据，适合移动网络传输。
- `social`、`carousel`、`shop-presentation`、`service-cover`、`official-notice`：保持展示所需分辨率，按照片或透明图选择固定配置。
- `identity-preview`：高质量预览；原件不参与有损处理。

前后端共享同一份版本化用途合同：客户端合同决定压缩行为，服务器镜像合同决定可接受的 MIME、尺寸、像素、帧数和字节上限。页面调用方和最终用户不能指定质量、目标 MIME、最大尺寸或跳过压缩；服务器也不能仅凭客户端合同版本跳过实际文件验证。

上传图片若不需要缩放，客户端质量比较使用解码后的原始像素；若用途配置要求缩小尺寸，则先使用固定的高质量缩放基准生成同尺寸参考图，再比较编码结果。带 EXIF 方向的上传先按方向归一化，再清除元数据；最终宽高记录归一化后的真实显示尺寸。尺寸上限必须来自当前各业务入口的既有展示与上传约束，不在本步骤中任意降低。

浏览器或设备不支持所需解码、Alpha、方向处理、压缩或质量比较时，公开展示类图片上传必须给出明确的本地处理失败提示，不能回退为上传未经优化的大图，也不能请求服务器代压缩。敏感材料的未压缩原件上传属于明确用途，不视为回退。

压缩和 SSIM 作为上传任务运行，必须支持进度、取消和失败恢复，不得长时间阻塞页面主线程，也不能破坏现有 Social 异步上传、发布和重试语义。

## 8. 一致性与失败处理

- 客户端压缩或质量比较失败时不发起上传；服务端验证失败时不写文件、不写数据库。
- Storage 先写受限临时对象并校验最终哈希，再切换为正式对象；Repository 只保存已经成功落盘的正式对象信息。
- 正式文件写入成功但数据库事务失败时，沿用补偿删除机制。
- 内容寻址文件使用压缩后字节的 SHA-256；相同结果应去重。
- 敏感原件和预览使用独立文件键、存储区域和数据库关系，不能互相覆盖。
- 重复上传和并发上传必须保持幂等或在现有 checksum lock 下串行化。
- 旧 URL 继续可读；新上传从切换点开始使用优化结果，历史媒体回填另立微步骤。

## 9. 测试与验收

先补失败测试，再实现：

- 静态 manifest 缺失、哈希变化、无法解码、体积超标和质量阈值测试。
- 客户端 JPEG、PNG、WebP、Alpha、EXIF、方向归一化、压缩无收益、质量不达标和能力不支持测试。
- 服务端伪造 MIME、异常文件头、解码失败、像素炸弹、超限帧数、超限尺寸、超限字节和伪造哈希测试。
- 头像、IM、Social、内容发布、店铺展示、服务封面和身份预览的客户端调用与服务/API 测试。
- 压缩失败零写入、数据库失败补偿删除、重复上传去重和权限隔离测试。
- 敏感原件完整哈希、原件与预览关联、预览隔离、无公开原件 URL 和审计测试。

最终集成状态必须通过：

- 前端完整测试、lint、正式 production build 和 bundle audit。
- 后端完整 Jest、lint、build、Prisma 校验及相关真实存储测试。
- 图片 manifest、解码、尺寸、Alpha、帧数、SSIM 和发布包总体积检查。
- 关键页面浏览器视觉验收；对最大文件、最高压缩比和关键 UI 生成原图/结果图并排对比证据。
- `git diff --check`、干净 worktree 和精确 Git SHA 检查。

## 10. 推送、部署与回滚

所有图片和上传链路门禁通过后，才允许把最终 `main` 无强推地推送到私有 `origin/main`。staging 必须从该精确提交重新构建和打包，发布包不得包含设计原件、原始敏感材料、`.data` 或未登记图片。

部署后验证三套 API readiness、HTTPS、登录、关键图片 URL、浏览器本地压缩、服务端拒绝绕过请求、浏览器渲染和上传后返回的最终 MIME/尺寸/字节数。GitHub 提交、staging 部署版本和实际健康检查分别记录。

静态图片可通过普通 Git revert 恢复。上传链路回滚恢复旧服务版本，但不得删除已写入或仍被数据库引用的媒体；新旧格式必须保持读取兼容。
