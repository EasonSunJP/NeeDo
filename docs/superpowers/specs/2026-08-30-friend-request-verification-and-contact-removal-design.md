# NeeDo 好友验证、双向关系与单方会话删除设计

## 1. 状态与范围

本设计于 2026-08-30 经用户确认，属于 Step 13「IM / Social / Notification 后端化」内的一个独立微步骤。

当前“添加新好友”搜索结果被点击后，前端会直接写入通讯录、创建一对一会话并进入聊天。这绕过了已经存在的正式好友申请接口，也使通讯录、动态关注、红点、拒绝、过期和删除后的消息权限无法保持一致。

本微步骤只建立以下正式闭环：

1. 搜索账号后先进入账号信息页，再发送好友申请。
2. 好友申请具有待处理、接受、拒绝和 72 小时过期状态。
3. 接受申请时建立双方通讯录关系，并自动建立动态双向关注。
4. 手动取消动态关注不影响通讯录好友关系。
5. 任意一方删除好友时，双方通讯录关系和动态双向关注同时永久删除。
6. 删除方的一对一会话入口及历史访问权永久删除；另一方保留完整历史。
7. 非好友从保留的旧会话发送消息时由服务端拒绝，不写入消息表。
8. 删除或拒绝后允许按已确认规则重新申请。

本轮不扩展群聊、订单业务会话、系统通知会话、黑名单产品规则、陌生人私信或新的 Social 推荐算法。

## 2. 产品状态机

### 2.1 好友申请状态

`FriendRequestStatus` 增加 `EXPIRED`，完整终态为：

```text
PENDING ──接受──> ACCEPTED
   │
   ├──拒绝──> REJECTED
   │
   └──满 72 小时──> EXPIRED
```

- `PENDING` 是唯一可处理状态。
- 申请创建时由服务端写入 `expiresAt = createdAt + 72 小时`。
- 72 小时以数据库 UTC 时间为权威，客户端时间不能决定申请是否有效。
- 接受、拒绝和过期都是终态，终态记录不复用、不改回 `PENDING`。
- 接受或拒绝必须写入 `respondedAt`；过期必须写入 `expiredAt`。
- 接受和过期在同一时刻竞争时，事务内数据库时间与行锁决定唯一结果；`expiresAt <= NOW()` 的申请不能再接受或拒绝。

### 2.2 双方显示文案

| 服务端状态 | 发出方显示 | 接收方显示 | 接收方待处理红点 |
|---|---|---|---|
| `PENDING` 且未过期 | 等待对方验证 | 待处理 | 显示 |
| `ACCEPTED` | 成功添加 | 成功添加 | 不显示 |
| `REJECTED` | 被拒绝 | 已拒绝 | 不显示 |
| `EXPIRED` | 已过期 | 已过期 | 不显示 |

“新的朋友”列表按对方账号聚合展示该方向最新一条申请，避免拒绝后重新申请产生重复联系人卡片；旧申请记录仍保留在数据库和审计链路中。

### 2.3 重复申请与重新申请

- 同一发出方到同一接收方存在未过期 `PENDING` 时，再次提交返回原申请，`createdAt`、`updatedAt` 和 `expiresAt` 均不更新。
- 上述重复提交不新增 Notification、不发送新的收件方 SSE 提醒，也不重新触发红点；响应必须明确 `created: false`。
- 同一对账号存在反方向未过期申请时，不创建第二条申请；返回该待处理申请的关系状态，由原接收方在“新的朋友”中接受或拒绝。
- `REJECTED` 后可以立即重新申请。新申请是新的数据库记录、使用新的创建时间和独立 72 小时期，并给接收方产生一次新提醒和红点。
- `EXPIRED` 后重新申请同样创建新记录并产生一次新提醒。
- 已是好友时不能创建申请，返回稳定业务错误 `error.im.already_friends`。
- 现有黑名单、账号停用和隐私保护规则优先，失败时不得向发出方泄露对方的敏感状态。

## 3. 页面与交互

### 3.1 搜索与账号信息页

- “添加新好友”继续使用正式分页目录接口，不新增本地搜索数组。
- 点击搜索结果只打开共享 IM 账号信息页，不新增 Contact、不创建 Conversation，也不跳转聊天。
- 信息页复用用户提供的深色卡片结构：头像、名称、NeeDoID、标签区域和动态入口。
- 从搜索结果进入非好友信息页时，底部固定显示“取消”和“添加好友”。
- “取消”关闭当前信息页并返回搜索结果，不产生数据变更。
- “添加好友”调用正式好友申请 API。成功后按钮进入“等待对方验证”状态，不能被连续点击制造重复申请。
- 对方已有待处理申请时，信息页显示可处理状态，不提供反方向重复申请按钮。
- 已是好友时信息页显示现有好友操作，不再显示“添加好友”。
- 标签编辑只沿用现有好友标签权限；非好友信息页不得新增对方标签写入能力。

### 3.2 收件方红点

- 只有当前账号收到的、未过期、未处理申请计入红点。
- 收件方通讯录底部导航 icon 和“新的朋友”入口 icon 同时显示红点。
- 发出方自己的等待验证申请不计入红点。
- 红点是服务端未处理申请数量的派生结果，打开列表后仍保留，直到接受、拒绝或过期。
- 72 小时内重复申请不改变数量，也不产生新的视觉提示。
- 接受、拒绝、过期和新的有效申请通过正式 SSE 更新；页面重载或断线重连后以正式 bootstrap/unread API 为权威恢复。

### 3.3 新的朋友列表与处理页

- 列表同时呈现相关的收件和发件状态，但卡片账号必须始终是“对方”，不能把发出方自己的资料显示成联系人。
- 每个卡片使用服务端返回的安全公开资料，包括头像、显示名和 NeeDoID，不通过占位用户补齐正式数据。
- 点击收到的待处理申请进入账号信息页：头部右侧是关闭按钮，底部是“拒绝”和“添加好友”。
- 关闭按钮返回“新的朋友”列表，不改变申请状态。
- 接受或拒绝进行中禁用两个按钮；服务端成功后再更新为终态。
- 已处理或已过期记录只显示终态，不再提供接受、拒绝按钮。
- 接受、拒绝失败时保留原状态并显示 i18n 错误，不得本地假成功。

## 4. 正式 API 与权限边界

继续使用并完善现有正式接口：

- `GET /api/v1/im/directory`：分页搜索可申请账号。
- `GET /api/v1/im/directory/:userId`：返回账号信息页所需的安全公开资料与当前关系摘要。
- `GET /api/v1/im/friend-requests`：分页返回当前账号相关申请、方向和双方安全公开资料。
- `POST /api/v1/im/friend-requests`：创建申请或幂等返回当前有效申请。
- `POST /api/v1/im/friend-requests/:id/accept`：仅接收方接受。
- `POST /api/v1/im/friend-requests/:id/reject`：仅接收方拒绝。
- `DELETE /api/v1/im/contacts/:contactId`：删除当前账号与该联系人的正式好友关系。

所有接口继续遵守统一 JSON envelope、Zod、OpenAPI、JWT 和既有权限：

- 目录和资料读取使用通讯录读取权限；
- 创建申请使用 `friend-request:create`；
- 列表使用 `friend-request:list`；
- 接受、拒绝使用 `friend-request:respond`；
- 删除好友使用 `contact:delete`。

申请创建响应为 `{ friendRequest, created }`。列表和资料响应不得包含手机号、邮箱、内部认证状态、token、密码字段或仅后台可见资料。Controller 只处理请求和响应，状态机、事务及权限后的业务校验位于 Service，Prisma 访问只位于 Repository。

创建、接受、拒绝、过期和删除好友都写入对应 AuditLog。审计只记录操作者、申请/关系 ID、双方账号 ID、状态变化、时间和结果，不记录好友申请正文、聊天内容或其他敏感资料。过期任务使用系统操作者标识，并保留触发来源。

## 5. 数据模型与并发控制

### 5.1 FriendRequest

Prisma schema 和 migration 增加：

- `FriendRequestStatus.EXPIRED`；
- `expiresAt DateTime`；
- `expiredAt DateTime?`；
- 面向“方向 + 状态 + 过期时间 + 未删除”的复合索引；
- 面向收件方待处理红点查询的复合索引。

历史申请继续保留 `id`、`createdAt`、`updatedAt` 和 `deletedAt`。本功能不通过删除申请记录表达状态。

创建申请时按排序后的两个 User ID 获取事务锁，再检查：

1. 双方账号均有效且不是同一账号；
2. 不存在有效好友关系；
3. 是否已有任一方向的未过期 `PENDING`；
4. 是否需要先把过期的 `PENDING` 原子更新为 `EXPIRED`。

只有在检查后确实创建新记录，才同时创建 Notification 和发布收件方 `friend_request.created` 事件。该锁顺序保证双击、双设备并发和双方同时申请不会生成两条有效待处理记录。

### 5.2 过期处理

过期采用两层服务端保障：

- 正式后台过期任务批量把 `expiresAt <= 数据库当前时间` 的 `PENDING` 更新为 `EXPIRED`，写入 `expiredAt` 并发布双方刷新事件；
- 列表、红点、创建申请、接受和拒绝接口在事务或查询边界再次执行过期判断，避免任务调度间隔形成可接受的过期窗口。

红点查询必须直接排除 `expiresAt <= NOW()` 的记录，即使后台任务尚未写回 `EXPIRED`。前端可以根据响应中的 `expiresAt` 安排一次本地刷新，但本地计时只用于及时刷新画面，不是状态权威，也不新增轮询。

### 5.3 一对一会话访问类型

为避免好友规则误伤群聊、订单、应聘或系统业务会话，Conversation 增加明确的访问策略：

- `FRIENDSHIP_REQUIRED`：普通账号好友一对一会话；
- `BUSINESS_CONTEXT`：由订单、技师应聘等正式业务关系授权的一对一会话；
- `GROUP_MEMBERSHIP`：群聊按成员关系授权。

所有新建会话路径必须显式写入策略。现有会话 migration 按确定规则回填：群聊为 `GROUP_MEMBERSHIP`；由 `technician_application` 双向 Contact 建立的一对一会话为 `BUSINESS_CONTEXT`；其余普通一对一会话为 `FRIENDSHIP_REQUIRED`。

`FRIENDSHIP_REQUIRED` 会话保存规范化的账号对 key，用于好友删除后仍能定位同一共享会话。该 key 只约束好友一对一会话，不限制同一账号对合法存在的独立业务会话。

migration 在建立唯一约束前执行只读重复账号对检查。若发现同一账号对存在多条普通好友一对一会话，migration 必须停止并输出精确 ID，重复数据修复作为独立受审计微步骤处理；不得在本 migration 中静默合并或删除历史消息。

## 6. 接受好友申请的原子事务

接收方点击“添加好友”后，Service 在一个事务中完成：

1. 锁定申请并确认操作者是接收方、状态为 `PENDING` 且未过期；
2. 把申请更新为 `ACCEPTED` 并写入 `respondedAt`；
3. 创建或恢复遗留数据中的 A→B 与 B→A 两条 Contact，来源统一为 `friend_request`；
4. 创建或恢复 A→B 与 B→A 两条 Follow；
5. 若该账号对存在因一方删除好友而只剩单方参与记录的 `FRIENDSHIP_REQUIRED` 会话，重新创建缺失方的 ConversationParticipant；其新 `createdAt` 是该方重新获得历史可见性的下界；
6. 写入包含申请 ID、双方账号 ID 和新增关系摘要的 AuditLog，不记录申请消息或聊天内容。

任一步失败全部回滚。提交后分别向双方发布好友申请更新、通讯录更新、Social 关注更新和 unread 刷新事件。双方“新的朋友”列表均显示“成功添加”，双方通讯录均出现对方，双方动态默认互相关注。

## 7. 动态关注与好友关系

- 接受好友申请会建立两条独立 Follow，因此双方自动互相关注。
- 用户在动态中手动取消关注只删除当前方向的 Follow，不修改任一 Contact，不解除好友，也不替对方取消关注。
- Social 当前“互相关注即自动加入通讯录”的反向耦合必须移除；关注关系不能绕过好友验证建立通讯录好友。
- Social 当前“取消关注同时删除通讯录”的耦合必须移除；手动取消关注只影响动态。
- 删除通讯录好友是唯一同时解除双方好友关系和双方动态关注的本流程入口。

## 8. 单方删除好友与历史删除

### 8.1 删除事务

假设 A 点击删除好友 B。`DELETE /im/contacts/:contactId` 在单个事务中：

1. 锁定 A、B 的好友关系并验证 A 有权删除；
2. 物理删除 A→B 与 B→A 两条 Contact；
3. 物理删除 A→B 与 B→A 两条 Follow；
4. 找到 A、B 的 `FRIENDSHIP_REQUIRED` 一对一会话，物理删除 A 的 ConversationParticipant；
5. 保留 B 的 ConversationParticipant、Conversation 和共享 Message；
6. 写入 AuditLog，记录操作者、对方账号、被删除关系 ID、会话 ID 和删除数量，不记录消息正文。

这是用户明确确认的例外：好友 Contact、自动 Follow 和删除方 ConversationParticipant 不使用软删除。表上的 `deletedAt` 仍保留以兼容全局 schema 规范和历史数据，但本操作不写 `deletedAt`，而是执行受事务和审计保护的精确物理删除。禁止按目录、通配条件或未解析账号对进行批量删除。

### 8.2 “删除”而非“隐藏”

- 不使用 `hiddenAt` 表达本次删除，也不保留可恢复的删除方 ConversationParticipant。
- A 的会话列表、搜索历史入口、未读数、置顶、静音和最后阅读状态随参与记录一起永久删除。
- A 此后无权读取该会话的旧消息；直接请求旧 conversation/message API 必须返回无访问权错误。
- 共享 Message 不能物理删除，因为 B 必须保留完整历史；它们仅继续通过 B 的有效参与记录对 B 可见。
- B 的会话入口和历史内容不改变，但在双方不是好友期间发送新消息会失败。
- 既有 Message、撤回痕迹、reaction 等共享历史不因 A 删除好友而从 B 的视图消失。

### 8.3 重新成为好友后的历史边界

- 删除后双方都可从对方信息页或目录重新申请。
- 新申请按正常 72 小时状态机处理。
- 再次接受时，在原 `FRIENDSHIP_REQUIRED` 会话为缺失方创建全新的 ConversationParticipant。
- 删除方只可读取这条新参与记录创建时及之后的消息，旧历史不恢复。
- 未删除方保留原参与记录，因此旧历史和重新成为好友后的新消息继续位于同一会话中，不生成两个聊天入口。
- Message 列表、搜索、媒体和定位接口都必须应用参与记录 `createdAt` 可见性下界，不能只在会话列表层过滤。

## 9. 消息发送权限

发送 `FRIENDSHIP_REQUIRED` 一对一消息前，服务端在写 Message 之前校验：

1. Conversation 和发送方 ConversationParticipant 有效；
2. 双方存在互为对方的有效 Contact；
3. 双方账号仍有效，且现有屏蔽规则允许发送。

任一好友关系缺失时返回稳定错误 `error.im.not_friends`。前端显示“对方不是你的好友，信息发送失败”，保留用户可重试的失败气泡或输入内容，但不得向正式 Message 表写入失败消息、增加对方未读数或发布新消息 SSE。

`BUSINESS_CONTEXT` 一对一会话继续按订单、应聘等既有业务授权校验；`GROUP_MEMBERSHIP` 继续按群成员关系校验。它们不能因为双方不是通讯录好友而被本规则错误阻断。

## 10. 前端正式数据流

- `ImApiContract`、formal adapter 和 store 补齐 `createFriendRequest`、资料读取及终态刷新，不再让页面直接调用 `addContact + ensureDirectConversation`。
- 搜索结果、信息页、好友申请列表、通讯录和聊天页共用服务端关系摘要，不在不同页面各自推导另一套状态机。
- 收到 `friend_request.*`、`contact.updated`、`social.follow.updated` 或会话参与变化事件后，沿用现有正式 bootstrap/SSE 刷新边界；断线重连后服务端快照覆盖临时本地状态。
- 联系人删除成功后，删除方 store 立即移除好友和该会话；另一方只移除好友关系，保留会话和消息。
- 如果 SSE 丢失或页面在后台，重新进入页面和刷新仍必须得到相同终态。
- 用户端、技师端和商户端继续共用 role config 与正式组件，不能为某一端新增平行 demo 页面。

## 11. i18n、错误和可访问性

所有新增可见文案与错误键覆盖当前五种语言边界：简体中文源文案、繁体中文、日文、英文、韩文。至少包括：

- 取消、添加好友、拒绝、关闭；
- 等待对方验证、待处理、成功添加、被拒绝、已拒绝、已过期；
- 对方不是你的好友，信息发送失败；
- 已是好友、申请已过期、申请状态已变化、申请发送失败、删除好友失败。

按钮使用语义化 `button`，进行中与不可处理状态有真实 `disabled`，关闭按钮有可访问名称和可见焦点。红点不能是唯一状态表达；列表文字必须同时说明状态。

## 12. 测试先行与验收

### 12.1 后端自动化

实施前先写会失败的测试，至少覆盖：

1. 创建申请、双方资料安全映射和权限校验。
2. 同方向 72 小时内重复申请返回同一 ID，时间不变，无第二条 Notification。
3. 反方向并发申请只产生一个有效 `PENDING`。
4. 拒绝后立即申请生成新 ID、新时间、新提醒。
5. 满 72 小时后旧记录变为 `EXPIRED`，新申请生成新提醒。
6. 过期与接受并发只能得到一个合法终态。
7. 接受事务创建双向 Contact、双向 Follow 和 AuditLog。
8. 手动取消单向 Follow 后 Contact 和反向 Follow 不变。
9. A 删除 B 后双方 Contact、双方 Follow 被物理删除，只有 A 的 ConversationParticipant 被物理删除。
10. B 的旧消息列表仍完整；A 的旧会话和消息接口无权访问。
11. 删除好友后从 B 的旧会话发送失败且 Message、unread、SSE 均不增加。
12. 重新接受后 A 只能看到新参与时间之后的消息，B 保留完整历史且只有一个会话入口。
13. 业务会话和群聊不被好友发送门禁误伤。
14. friend request、contact delete、message send 的 RBAC、Zod、OpenAPI 和统一错误 envelope。
15. migration、索引、真实 MySQL 时间边界和事务并发行为。

Service、Repository 和 API 集成测试使用正式 schema 与隔离测试数据库；生产代码不得新增 mock、fake API 或本地成功分支。

### 12.2 前端自动化

至少覆盖：

- 点击目录结果进入资料页且不调用 addContact、ensureDirectConversation 或 navigate-to-chat；
- 搜索资料页“取消 / 添加好友”状态；
- 收件方双红点只统计收到的有效待处理申请；
- 申请列表始终显示对方账号及完整状态矩阵；
- 收件处理页的关闭、拒绝、添加好友及重复点击保护；
- 接受后的双方通讯录/Social 刷新；
- 手动取消关注不删除 Contact；
- 删除方移除会话，被删除方保留会话；
- 非好友发送错误文案和失败消息不进入成功状态；
- 五语言文案、窄屏底部按钮和头部关闭按钮可访问性。

### 12.3 正式双账号浏览器验收

在正式前后端、真实测试账号和移动视口约 `440×956` 下完成：

1. A 搜索 B，点击结果只进入资料页。
2. A 申请后显示“等待对方验证”；B 的通讯录和“新的朋友”出现红点并显示“待处理”。
3. A 在 72 小时内重复申请，B 不出现新提醒，申请时间不变化。
4. B 拒绝后，A 显示“被拒绝”，B 显示“已拒绝”；A 可立即重新申请且 B 得到一次新提醒。
5. 重新准备申请并由 B 接受，双方显示“成功添加”、双方通讯录出现对方、双方动态互相关注。
6. A 手动取消动态关注，双方仍是通讯录好友。
7. A 删除 B，双方通讯录和双方动态关注解除；A 的会话与历史入口消失，B 的旧历史保留。
8. B 从旧会话发送，出现“对方不是你的好友，信息发送失败”，刷新后数据库没有该失败消息。
9. 双方重新申请并接受后，A 不恢复旧历史，B 保留旧历史，新消息继续正常收发。
10. 用可控数据库时间或专用测试时钟证明恰好 72 小时的过期边界及过期后新提醒。

至少分别验证普通用户视角，并抽查技师端、商户端共享路由。每一步都核对刷新/重连后的正式状态、SSE、红点、控制台错误和横向溢出；自动化测试、lint 和 build 不能替代可见交互验收。

## 13. 迁移、发布与回滚边界

发布顺序：

1. 应用 Prisma migration 和索引；
2. 发布兼容新旧前端响应的后端；
3. 启用过期任务和新的 SSE/unread 计算；
4. 发布前端页面与 store；
5. 完成正式双账号验收后再移除旧的“直接加联系人并聊天”路径。

回滚代码时不得删除申请、消息或审计记录。新增字段可暂时保留，由旧版本忽略。必须明确：好友删除后的 Contact、Follow 和删除方 ConversationParticipant 是按用户要求物理删除，单纯回滚代码不能恢复；唯一正式恢复路径是重新发送并接受好友申请，且删除方旧历史仍不恢复。任何数据库恢复都属于独立运维操作，不在本功能自动回滚范围内。

## 14. 完成定义

本微步骤只有在以下条件全部满足后才算完成：

- 搜索结果不再直接加好友或打开聊天；
- 72 小时申请状态机、重复申请、拒绝后立即重申和双方状态文案均由服务端权威实现；
- 红点、Notification、SSE、刷新和重连一致；
- 接受申请原子建立双向 Contact 与双向 Follow；
- Social 手动取消关注与通讯录好友解耦；
- 单方删除原子物理删除双方好友/关注关系及删除方会话参与记录；
- 删除方旧历史不可恢复，未删除方旧历史保留；
- 非好友消息在服务端写入前被拒绝；
- 普通好友、业务会话和群聊权限边界不混淆；
- schema migration、Zod、OpenAPI、RBAC、AuditLog、五语言、测试、lint、正式构建和双账号浏览器验收全部通过；
- 没有新增 mock、placeholder、轮询、硬编码敏感信息、`TODO`、`FIXME` 或未实现分支。
