# 用户日程“日历来源”按钮恢复设计

## 背景与根因

用户端正式日程页仍然复用 `UnifiedUserCalendar`，现有组件也保留了“日历来源”按钮、来源选择面板及正式模式交互测试。

`UnifiedUserCalendar` 在 `formalOnly` 模式下默认把 `showSourceDrawer` 设为 `false`。技师正式日程页面已经显式传入 `showSourceDrawer`，但 `UserSchedulePage` 在切换到正式用户资料与正式日程后只传入了 `formalOnly`，没有显式开启来源面板。因此用户日程页同时隐藏了入口按钮和既有面板。

## 目标行为

- 用户端日程标题左侧恢复圆形菜单按钮，位置与已批准界面一致。
- 点击按钮打开现有“日历来源”面板。
- 面板继续显示 NeeDo 同步、我的行程、技师端行程、商户端行程、ToDo 与生日等现有来源。
- 正式模式继续禁止浏览器本地业务日程持久化。
- 正式用户页不恢复本地新增行程悬浮按钮，也不改变正式订单读取逻辑。

## 实现方案

只修改用户日程页的组件调用：在 `UserSchedulePage` 向 `UnifiedUserCalendar` 显式传入 `showSourceDrawer`。

不修改 `UnifiedUserCalendar` 的全局默认值，因为其他正式日历页面可能有不同的产品边界；不新增页面级按钮或复制来源面板，避免形成第二套交互。

## 测试与验收

1. 先扩展 `UserSchedulePage` 的组件测试，要求正式用户日历同时收到 `formalOnly` 与 `showSourceDrawer`，并确认该测试在实现前失败。
2. 添加最小生产代码使测试通过。
3. 运行用户日程页测试和现有 `UnifiedUserCalendar.formal` 测试，确认按钮能够打开既有来源面板，且正式模式不写入本地业务日程。
4. 运行前端构建。
5. 在用户端移动视口打开正式日程页，确认按钮可见、位置正确、可点击并打开来源面板；同时检查控制台和横向溢出。

## 变更边界

- 不修改后端、数据库、migration、RBAC 或正式日程 API。
- 不修改来源面板的视觉设计、来源清单或同步规则。
- 不改动当前工作区中已有的技师排班和联系事件时间线变更。
