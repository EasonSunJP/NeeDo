## 2. 目标与非目标

### 2.1 目标

1. 运营后台和商户/店铺后台只保留一个“数据大盘”入口，旧的重复总览页面退役。
2. 大盘使用正式数据库口径，展示当前周期、上一等长周期和环比。
3. 每个指标都有说明、计算公式和可追溯的详情页；明确声明无需详情的测试入口除外。
4. 三个排行榜支持按 GMV/次数切换，并遵循统一的完成订单口径和确定性排序。
5. 补齐用户、技师和后台之间的正式履约、追加服务、结账、支付确认与互评流程。
6. 打通运营后台首页轮播图与用户端首页的同一份已发布数据。
7. 建立会员、代理商、运营成本、服务类型和搜索趋势的正式管理及分析能力。

### 2.2 非目标

- 不在一个提交中完成全部功能；每个阶段必须单独验收后再进入下一阶段。
- 不允许运营人员任意编辑图表布局。“增减图表”只表示通过图例显示或隐藏预先定义的数据序列。
- 首版结账采用单一支付方式全额结算，不实现现金与 NDP 混合拆分支付。
- “加盟商”和“供货商”首版仅为带 `TEST` 标记的顶部导航入口，不可点击且无详情页。
- 车费、消耗品销售总额和消耗品销售利润只预留正式接口契约；未接入数据源时不得显示伪造数字。

## 4. 正式订单履约与结算状态机

### 4.1 状态定义

沿用现有 `PENDING`、`CONFIRMED`、`IN_SERVICE`、`COMPLETED`、`CANCELLED`，新增：

- `AWAITING_CHECKOUT`：服务已结束，订单金额已汇总，等待选择支付方式。
- `AWAITING_PAYMENT_CONFIRMATION`：用户已选择现金或其他线下方式，等待技师确认收款。

退款/冲正不通过修改上述履约状态来隐藏，而由正式支付/退款记录表达，并在分析层排除已全额退款或已冲正的订单。

```text
PENDING
  -> CONFIRMED
  -> IN_SERVICE
  -> AWAITING_CHECKOUT
       -> NDP 支付成功 -> COMPLETED
       -> 现金/其他方式 -> AWAITING_PAYMENT_CONFIRMATION
                            -> 技师确认收款 -> COMPLETED

任一允许取消的前置状态 -> CANCELLED
COMPLETED -> 双向评价（不改变订单完成状态）
```

### 4.2 开始服务

- 用户到店或技师到达后，用户或技师都可以发起“开始服务”。
- 技师发起时必须输入用户提供的一次性服务验证码；验证码校验、失败次数限制和过期规则由后端执行。
- 成功开始后写入服务会话与事件记录，包括订单、操作者、开始时间、原计划结束时间和请求幂等键。
- 同一订单重复提交开始请求必须幂等，不能创建多个并行服务会话。

### 4.3 追加服务

- 服务中可打开追加服务页，选择店铺当前可售的服务项目。
- 每条追加项必须保存服务名称、服务项目 ID、价格、增加时长、货币、发起人、接受人和当时的服务快照。
- 追加服务必须由另一方确认后生效；生效后增加订单应付金额并延长预计结束时间。
- 后续修改服务目录或价格不能反向改变已接受追加项。

### 4.4 结束服务与结账

- 到达预计结束时间时，后端定时任务幂等地将订单推进到 `AWAITING_CHECKOUT`。
- 用户或技师也可以提前点击“结束服务”；未到时间时必须显示确认提示，并在确认后进入 `AWAITING_CHECKOUT`。
- 结账应付金额：

```text
原订单成交价
+ 已接受追加服务金额
- 后续有效优惠/减免
= 订单结账应付金额
```

- 结账页显示应付日元金额，并提供“现金支付”“NDP 支付”“其他方式支付”。
- “其他方式”保存正式支付方式代码、显示名称和可选的交易参考号，不能只保存自由文本结果。

### 4.5 支付完成证据

- NDP：钱包扣款及账本事务成功后，订单自动进入 `COMPLETED`。
- 现金/其他方式：用户选择方式后进入 `AWAITING_PAYMENT_CONFIRMATION`；技师点击“确认收款”并成功写入审计记录后进入 `COMPLETED`。
- 运营或商户管理员的异常代确认必须具备独立 permission、填写原因，并写入审计日志，不能静默代替技师。
- 未完成、已取消、已全额退款或已冲正订单不进入消费、GMV、次数和排行榜。

分析中的“消费金额”定义为已经完成订单的结账应付金额，不声称平台已验证现金实际到账。

### 4.6 NDP 兑换比例

- 默认比例为 `1 NDP = 1 JPY`。
- 运营设置可以发布新比例，必须包含版本、NDP 数量、JPY 数量、生效时间、设置理由、操作者和审计记录。
- 结账创建时保存不可变的比例版本和比例快照；后续调整不能改变历史订单。
- 同一时刻只允许一个有效版本，发布与修改需要专用 RBAC permission。

### 4.7 完成后的评价

- 仅 `COMPLETED` 订单允许评价。
- 用户评价店铺/技师，技师评价用户，均关联订单和评价对象。
- 每个方向对同一订单只能提交一次；跳过评价不会影响订单完成。
- 优先复用现有正式评价模型和 API；缺少的关联字段通过 migration 补齐，不创建并行 mock 评价体系。

### 4.8 需要补齐的正式页面

- 用户端：开始服务确认、服务中计时、追加服务确认、结束服务确认、结账与支付方式、支付结果、用户评价。
- 技师端：验证码开始服务、服务中计时、追加服务确认、结束服务、线下收款确认、技师评价用户。
- 商户/运营后台：订单履约事件时间线、结账快照、支付证据、退款/冲正和异常代确认审计。

## 5. 数据大盘共享分析契约

### 5.1 筛选器

运营大盘统一支持：

- 城市：全部城市或单个城市。
- 时间：今日、近 7 天、近 30 天、本周、本月、今年、自定义。
- 点击“检索”应用条件，点击“重置”恢复默认值。

商户/店铺大盘继承时间筛选；城市及店铺范围受当前账号和 RBAC 限制。商户账号可通过店铺信息卡右侧按钮切换其有权访问的店铺。

### 5.2 当前周期与上一周期

- 上一周期与当前周期等长且紧邻当前周期之前。
- 当前值与上一周期值使用同一过滤条件、时区和业务口径。
- 环比：`(当前值 - 上期值) / 上期值 × 100%`。
- 当前值与上期值相同显示 `+0%`。
- 上期为 0 且当前大于 0 显示 `+100%`；当前为 0 且上期大于 0 显示 `-100%`。
- 金额计算使用整数最小货币单位或 Decimal，不能使用浮点累计。

### 5.3 指标卡统一响应

每项指标至少返回：

```json
{
  "metricKey": "new_paid_members",
  "currentValue": 12,
  "previousValue": 8,
  "comparisonPercent": 50,
  "comparisonDirection": "up",
  "unit": "people",
  "dataStatus": "ready",
  "description": "当前周期首次付费加入会员的去重用户数",
  "formula": "COUNT(DISTINCT first_paid_membership_user_id)",
  "detailRoute": "/admin/analytics/members"
}
```

- 标题右侧统一提供圆形 `i`，点击展示 `description` 和 `formula`。
- `detailRoute` 存在时整卡可点击进入详情页。
- 明确无需详情的项目返回 `detailRoute: null`，页面不得制造空白详情页。
- 保留接口未接通时返回 `dataStatus: "not_connected"` 与 `currentValue: null`，不能返回 `0` 冒充真实数据。

### 5.4 详情页图表

- 图表序列由产品预设，不允许运营人员自行增加、删除或改写计算方式。
- 用户可点击图例显示或隐藏“增加”“减少”等已有序列。
- 详情页继续使用城市、时间等统一筛选器，并展示与卡片一致的口径说明。

## 6. 综合数据概要指标目录

### 6.1 运营财务

| 指标 | 计算口径 | 详情 |
|---|---|---|
| 营业总额 | 筛选范围内符合完成口径的订单结账应付金额合计 | 有 |
| 车费 | 预留正式数据源 | 有；未接通时显示数据源未接通 |
| 优惠金额 | 原始价格合计减成交优惠后价格合计；覆盖情报与店铺折扣行为 | 有 |
| 消耗品销售总额 | 预留 Store 正式销售数据源 | 有；未接通时显示数据源未接通 |

### 6.2 佣金统计

| 指标 | 计算口径 | 详情 |
|---|---|---|
| 专属技师佣金 | 日薪额度/底薪日摊销 + 已结算分成；月薪或月度底薪按所在自然月日数折算每日额度，再按范围内有效工作日计入 | 有 |
| 兼职技师佣金 | 与专属技师相同，但按技师跨多个店铺的有效收入汇总 | 有 |
| 营销佣金 | 联盟营销中承接方已经确定的佣金 | 有 |
| 代理商分佣 | 已满足条件的固定成功奖励 + 该代理商引荐店铺的平台纯利润 × 有效分成比例 | 有 |
| NDP 收入 | 筛选范围内已结算的平台 NDP 收入 | 有 |
| 联盟营销收益 | 联盟营销为平台带来的、已经确定的 NDP 收益 | 有 |
| 消耗品销售利润 | 不含消费税的销售基数 × 平台有效分成比例 | 有；数据源未接通时显示未接通 |

专属/兼职技师的薪酬规则必须版本化并保留生效区间。若一个筛选范围跨越自然月，应分别按各月日数计算，不允许统一除以 30。

### 6.3 用户与增长

| 指标 | 计算口径 | 详情 |
|---|---|---|
| 新增用户 | 当前范围首次完成正式注册的去重用户 | 有 |
| 新增付费会员 | 当前范围首次购买并激活付费会员卡的去重用户；排除赠送、试用和续费 | 有，含会员列表 |
| 技师入驻 | 当前范围首次成为有效技师身份的去重用户 | 有 |
| 代理商入驻 | 当前范围首次被运营正式标记为代理商的去重用户 | 有 |
| 加盟商入驻 | 当前范围首次被标记为加盟商的去重用户 | 无；功能为 `TEST` |
| 供货商入驻 | 当前范围首次被标记为供货商的去重用户 | 无；功能为 `TEST` |

## 7. 已结算平台纯利润与运营成本

代理商分佣使用的店铺平台纯利润公式为：

```text
已结算平台收入（订单平台服务费 + SaaS 费）
- 用户返点
- 退款/冲正
- 支付通道费
- 消费税
- 运营成本均摊
= 店铺平台纯利润
```

运营成本由运营后台正式设置，首批支持人件费、服务器、第三方 API 等类别，也允许在受控类别管理中增加其他项目。每一项成本必须单独选择一种分摊方式：

1. 活跃店铺等额分摊。
2. 按店铺平台收入比例分摊。
3. 直接指定一个或多个店铺及金额/比例。

成本项目、金额、币种、期间、分摊方式、目标店铺、版本、生效时间、设置理由和操作者均需持久化并可审计。历史结算引用不可变快照，后续规则调整不重算已确认结算。

## 8. 代理商管理

- 代理商首先是正式 NeeDo 用户，由运营人员从用户管理中标记为代理商。
- 代理商可关联其介绍入驻的一个或多个店铺，关联记录包含来源、确认时间和操作者。
- 每个代理商可独立设置：固定成功奖励（日元）、平台纯利润分成比例、支付方式、生效时间和规则版本。
- 固定奖励只在规则定义的成功条件首次满足时产生一次，必须幂等。
- 分佣按店铺、期间和规则版本生成结算明细，保留计算输入、扣减项、结果、支付状态和支付凭证。
- “中介”账号必须关联正式用户 ID，不允许独立创建脱离 User Management 的账号。
- 运营后台顶部“代理”入口进入正式代理商列表与详情管理页。

## 9. 会员详情与会员列表

商户/店铺端会员大卡的大字显示会员数，小字显示利用者数；它与运营增长指标“新增付费会员”是两个不同口径：

- 会员数：当前持有该店铺有效会员卡的去重用户数。会员资格来源以正式会员卡记录为准，不以是否在筛选期内下单判断。
- 利用者数：筛选范围内至少有一笔该店铺完成订单的去重用户数，重复利用不重复计数。
- 新增付费会员：继续使用第 6.3 节口径，只计算当前范围首次购买并激活付费会员卡的用户，排除赠送、试用和续费。

会员详情页包括：

- 会员增加数、减少数和净变化的预设图表；图例可逐项显示/隐藏。
- 正式会员列表，必须分页。
- 筛选条件：城市、时间、NeeDo ID、昵称。
- 列表至少显示 NeeDo ID、昵称、城市、会员卡/套餐、首次付费时间、当前状态和到期时间。
- 会员数 API 即使会员卡功能尚未全部完成，也必须先保持稳定契约，未具备数据时明确返回状态而不是前端硬编码。

## 10. 三个 TOP10 排行榜

### 10.1 共通规则

- 支持“按 GMV”和“按完成次数”切换。
- GMV 为完成订单的结账应付金额，不宣称现金已由平台验证到账。
- 次数为完成订单数。
- 未完成、取消、全额退款和冲正订单全部排除。
- 金额或次数完全相同时，依次按：另一项指标降序、注册时间升序、数字 ID 升序。
- 城市和时间条件与页面顶部筛选器一致。

### 10.2 排行榜类型

1. 服务项目 TOP10：按服务项目汇总完成订单及其已接受追加服务。
2. 技师 TOP10：可按运营后台服务类型筛选；优先扩展现有正式技师排行 API。
3. 用户消费 TOP10：可按运营后台服务类型筛选，金额使用该用户完成订单结账应付金额。

排行榜响应同时返回 `gmv`、`completedCount`、`registeredAt` 和稳定对象 ID，以便前端切换时不制造不同口径。

## 11. 运营服务类型与搜索趋势

### 11.1 服务类型与搜索标签

- 新增“运营服务类型设置”，管理家政服务、放松休闲、宠物相关等正式服务类型。
- 服务项目必须关联正式服务类型；搜索页标签读取同一份已发布配置。
- 配置包含多语言名称、排序、启停、版本和审计，不允许用户端保留并行静态标签。

### 11.2 搜索事件与趋势

- 用户真正执行搜索时，后端记录标准化关键词、原始关键词、城市、时间、服务类型、结果数和匿名化用户/会话标识。
- 不记录输入框尚未提交的文字。
- 搜索关键词 TOP10 支持城市和时间筛选。
- 可添加多个关键词进行对比，展示原始搜索次数与 `0-100` 归一化趋势；归一化值不是搜索次数，UI 必须清楚标注。
- 关键词标准化规则、同义词和服务类型映射由正式服务设置管理，变更可审计。

## 12. 首页轮播图正式联通

现状问题是后台无草稿时只展示“从历史版本创建草稿”等版本操作，没有只读渲染当前已发布轮播内容，因此用户看到“后台为空”，而用户端仍显示已发布数据。

修复要求：

1. 后台无草稿时，也必须只读展示当前 `USER_HOME` 已发布版本的全部轮播项、顺序、图片和五语言文案。
2. 创建新草稿时从当前已发布版本完整克隆，不能从空数组开始。
3. 用户端首页和运营后台预览读取同一个已发布 API 响应，不保留静态 fallback。
4. 发布、停用、回滚继续使用现有版本机制，并保留 RBAC 和审计。
5. 集成测试直接比较后台已发布预览与用户端轮播 API 的版本号及轮播项内容。

## 13. 导航与页面整合

- 运营后台导航“PF运营”改为“运营管理”。
- 运营和商户后台的“总览”与“数据大盘”合并为一个“数据大盘”，旧重复页面和路由在迁移验证后删除。
- 删除前必须建立旧 URL 到新大盘的兼容跳转，确认没有菜单、快捷入口和深链仍依赖旧路由后，再在独立微步骤移除旧组件。
- 顶部增加“加盟商 `TEST`”和“供货商 `TEST`”，首版不可点击。
- 代理入口连接正式代理商管理页。
- 商户店铺信息卡保留，并展示账号类型（年费、月费、试用期）、NDP 钱包余额和有权限店铺切换。

## 14. API、数据分层与权限要求

### 14.1 正式分层

所有新增接口遵守 `Route -> Controller -> Service -> Repository -> Prisma`，使用 `/api/v1/`、Zod、OpenAPI、统一响应格式和分页契约。Controller 不写计算逻辑，不直接访问 Prisma。

### 14.2 建议的数据边界

实施时优先复用现有模型，缺失能力再以 migration 增补。需要覆盖的正式数据边界包括：

- 订单服务会话与履约事件。
- 订单追加服务及其不可变价格/时长快照。
- 订单结账、支付选择、收款确认和 NDP 比例快照。
- 代理商身份、引荐店铺、规则版本、结算和支付记录。
- 运营成本项目、版本和店铺分摊结果。
- 服务类型、搜索标签、搜索事件及按日聚合。

### 14.3 RBAC 与审计

至少拆分以下权限：

- 查看运营/商户大盘和各详情。
- 管理 NDP 比例。
- 标记代理商、加盟商、供货商。
- 管理代理奖励、分佣与支付。
- 管理运营成本及分摊。
- 管理服务类型与搜索标签。
- 发布/停用/回滚轮播版本。
- 异常代确认线下收款。

所有身份标记、财务规则、比例、结算、支付、内容发布和异常订单操作必须记录操作者、前后值、理由、时间与请求关联 ID。

## 15. 错误、空状态与一致性

- 正式数据为空时显示“暂无数据”，不能以示例排行或演示曲线填充。
- API 未接通与真实值为 0 必须可区分。
- 指标卡、详情图表、导出和排行榜必须调用同一 Service 口径，不能分别在前端重算。
- 财务聚合、钱包扣款、收款确认、追加服务接受和规则发布均需事务与幂等保护。
- 城市、店铺和用户范围必须由后端 RBAC 约束，不能只依赖前端隐藏。
- 时间计算以业务时区解释筛选边界，数据库继续存 UTC，API 使用 ISO 8601。

## 16. 验收标准

### 16.1 轮播图

- 后台没有草稿时能看到当前已发布的 5 条正式轮播内容，而不是空白编辑区。
- 后台预览与用户端首页取得相同发布版本、顺序和多语言文案。
- 创建草稿后内容与已发布版本一致，修改草稿不会影响线上版本，发布后用户端才变化。

### 16.2 履约与支付

- 用户与技师分别完成开始服务、追加服务、到时/提前结束、三种支付路径和双向评价的浏览器回放。
- NDP 支付必须有钱包账本证据；现金/其他方式必须有技师收款确认与审计证据。
- 刷新或更换浏览器后状态仍由正式 API 恢复，不依赖 `localStorage`。
- 重复点击、重复请求和并发请求不会重复扣款、重复追加或重复完成。

### 16.3 数据与排行

- 每张指标卡显示当前值、上一周期值、正确符号的环比、说明和公式。
- 预留数据源显示“未接通”，真实 0 显示 0。
- 会员增加/减少图例可显示隐藏，会员列表可按城市、时间、NeeDo ID、昵称检索且分页。
- 三个排行榜可切换 GMV/次数；对完全相同样本验证注册时间和数字 ID 的稳定排序。
- 完成、取消、退款、冲正和线下确认样本的统计归属符合本设计。

### 16.4 权限与审计

- 无权限账号不能读取跨城市/跨店铺数据，不能修改比例、规则、身份或结算。
- 所有关键变更可从审计记录还原操作者、前后值、理由和生效版本。

### 16.5 工程门禁

- 无新增 mock、demo、placeholder、fake API、`TODO` 或 `FIXME`。
- migration、Prisma schema、物理表和 `_prisma_migrations` 状态一致。
- lint、类型检查、单元测试、API 集成测试和生产 build 通过。
- 在项目标准端口、正确 PID/cwd/分支上完成桌面与窄屏浏览器验收，并检查控制台错误与横向溢出。
