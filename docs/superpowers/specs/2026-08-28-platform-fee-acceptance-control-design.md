# NeeDo 店铺平台使用费、接单控制与待处理订单规则设计

**日期：** 2026-08-28  
**适用阶段：** Step 10 Booking / Order 状态机、Step 11 NDP 账本与 Step 12 正式后台  
**状态：** 用户已逐段确认；必须按独立微步骤实施

## 1. 目标

本设计把现有固定由店铺承担的每单 500 NDP 平台使用费，升级为可运营、可审计且不会因余额不足自动停止月费商户业务的正式规则。同时补齐集团/店铺暂停接单、普通用户单一待处理订单和最高级付费用户例外。

核心要求：

1. 全局平台使用费默认开启，默认每单 500 NDP，运营可修改全局金额。
2. 运营可按店铺单独开启或关闭平台使用费；店铺默认收费。
3. 商户店铺后台可选择平台费由店铺或该订单实际服务技师承担。
4. 本地正式测试店铺全部关闭平台使用费，确认订单时不冻结 NDP。
5. 用户完单返点默认 100 NDP，但仅在店铺启用平台使用费且订单满足结算条件时发放。
6. 余额不足不自动阻止接单；每笔订单必须显式确认是否继续，运营和商户可另行人工暂停接单。
7. 普通用户全平台只能保留一笔 `PENDING` 订单；`black` 黑卡会员可以同时保留多笔。

本设计不新增浏览器 mock、静态演示费用、前端本地钱包或绕过正式账本的余额修改。

## 2. 现状与必须修正的问题

当前正式费用规则同时存在：

- Booking 平台使用费：500 NDP，`b_platform_fee`。
- Booking 用户完单返点：100 NDP，`user_reward`。
- Request 用户调度费：500 NDP，`c_request_dispatch_fee`。
- 商户强制取消赔付：500 NDP，`penalty`。

本次只修改 Booking 平台使用费及其与 100 NDP 用户返点的关系。Request 调度费、取消赔付和联盟营销返点不在本次范围内。

现有实现的问题包括：

1. Booking 接单冻结固定使用店铺钱包，没有真正按费用计算结果的 `payerType` 选择钱包。
2. 完单和取消也固定读取店铺钱包，不能支持技师承担。
3. 余额不足直接回滚确认，没有人工继续接单和欠费状态。
4. 通用实体停用会隐藏时段并阻止用户预约，不能表达“用户仍可下单，但服务方暂停确认”。
5. 本地正式数据库中有 4,348 笔 `PENDING` 订单，72 个测试用户同时拥有多笔，最高为 119 笔；这些用户需要升级为黑卡测试用户，而不能伪装成普通用户例外。

## 3. 已确认的业务规则

### 3.1 全局金额与店铺收费开关

- 全局 `b_platform_fee` 默认金额为 500 NDP。
- 运营后台可以修改全局金额；修改只影响修改后确认的新订单。
- 每家店铺的平台费收费开关默认开启。
- 运营后台可以按店铺开启或关闭收费。
- 店铺没有显式策略记录时，服务端按“收费开启、店铺承担”解析，禁止因数据缺失而漏收。
- 本地正式测试数据中的全部测试店铺显式设为关闭收费。

### 3.2 承担者

- 商户店铺后台可以选择 `shop` 或 `technician`。
- `shop` 使用该店铺的 SHOP 钱包。
- `technician` 使用订单实际服务技师所对应 User 的 USER 钱包。
- 技师承担的欠费绑定技师全局账号；技师转到其他店铺后，负余额和未结欠费仍然存在。
- 店铺设置为技师承担但订单没有明确服务技师时，不能确认订单，服务端返回明确冲突。

### 3.3 接单时锁定

每笔订单确认时锁定并持久化：

- 是否收取平台费。
- 全局平台费金额。
- 费用承担者类型和业务 ID。
- 实际钱包所有者类型和钱包所有者 ID。
- 命中的费用规则和店铺策略版本。
- 接单时间和返点资格基础状态。

订单确认后修改全局金额、店铺收费开关或承担者，不改变该订单已经锁定的费用与钱包。取消和完单必须使用原始快照及原 WalletHold，不能按当前配置重新选择承担者。

### 3.4 店铺关闭平台费

- 接单平台费为 0。
- 不创建 `WalletHold`、`LedgerTransaction` 或 `WalletLedger`。
- 不改变任何钱包余额。
- `FeeCalculationLog` 与 `OrderFinancial` 仍记录零费用及关闭原因，保留审计证据。
- 用户 100 NDP 返点同时关闭，返点状态固定为 `disabled`，展示 0 NDP。

### 3.5 余额不足与人工继续接单

余额不足不得因商户已经支付月费而自动停止业务。

第一次确认订单时：

1. 服务端在同一事务中读取有效费用配置、承担者、钱包和暂停接单状态。
2. 钱包余额不足时返回结构化冲突，包含平台费、承担者、可用余额和缺口。
3. 本次请求不能修改订单、历史、费用、钱包或通知。

操作者明确选择继续后：

1. 第二次请求携带不足余额确认标识、幂等键和费用预览版本。
2. 服务端重新校验暂停状态、订单状态、承担者和规则版本。
3. 条件仍一致时将完整平台费转入冻结，并允许可用余额形成负数。
4. 订单进入 `CONFIRMED`，写入状态历史、费用快照、冻结、负余额缺口和人工确认审计。

未经此专用确认路径，任何普通账本操作都不得突破余额下限。

### 3.6 取消、完单、补交与返点

- 订单在完成前取消时释放原承担者的冻结，并撤销该订单尚未结算的负余额影响。
- 订单完成时从原冻结中扣除平台费。
- 接单时无欠费或在完单前已经补足：完单后立即发放 100 NDP 用户返点。
- 完单时仍存在欠费：返点状态为 `pending`，用户端显示 0～100 NDP 和截止时间。
- 返点截止时间为订单完成时间后连续 7×24 小时。
- 只有正式钱包充值审核成功才视为补交；其他奖励、退款或内部余额变化不能伪装成补交。
- 补交按承担者钱包下未结欠费的接单时间 FIFO 分配。
- 在截止时间内结清该订单欠费后，系统自动向用户发放 100 NDP，并将返点状态改为 `paid`。
- 超过截止时间仍未结清，返点状态改为 `expired`，金额固定为 0。
- 截止后补交仍用于偿还平台费欠款，但绝不补发已经过期的用户返点。
- 同一充值、欠费抵扣和合资格返点必须在同一数据库事务中完成，失败整体回滚。

## 4. 暂停接单

### 4.1 与实体停用分离

暂停接单不是店铺停业、账号封禁或 SaaS 终止。开启后：

- 用户仍可查看可预约时段并创建订单。
- 新订单保持 `PENDING`。
- 商户、店铺和技师仍可读取列表和订单详情。
- `PENDING -> CONFIRMED` 被服务端阻止。
- 已确认订单的履约、取消、支付和售后不因接单暂停而自动改变。

因此不得直接复用会隐藏时段、阻止预约或批量阻塞 ScheduleSlot 的现有 `EntitySuspension` 行为。

### 4.2 作用域与权限

- 运营后台可以暂停或恢复一个 MerchantAccount 集团，也可以单独控制一家 Shop。
- 商户集团后台可以控制自己的整个集团，也可以控制集团内指定店铺。
- 店铺身份只能控制自己。
- 集团暂停对当前有效 membership 下全部店铺生效。
- 单店暂停只影响该店铺。
- 多个有效暂停同时存在时，必须全部解除后才可确认订单。
- 店铺不能解除集团或运营创建的暂停。
- 商户不能解除运营创建的暂停。
- 运营可以解除任意层级暂停。
- 每次暂停和恢复都记录理由、操作者、来源、范围、时间和审计日志。

暂停检查必须在订单确认事务内再次执行，不能只依赖页面按钮禁用。

## 5. 普通用户单一 PENDING 订单

### 5.1 规则

- 除 `black` 会员外，用户在全平台任何店铺最多保留一笔 `PENDING` 订单。
- `black` 是唯一允许同时保留多笔 `PENDING` 的最高级付费会员代码。
- 限制由服务端读取 CustomerProfile.membershipLevel 决定，前端标签不是权限来源。

### 5.2 新订单替换

普通用户创建新订单时，服务端在一个事务内：

1. 锁定用户或等价的单一并发保护记录。
2. 锁定并验证新 ScheduleSlot、服务和容量。
3. 找出该用户全部现有 `PENDING` 订单。
4. 自动取消旧订单，释放对应时段容量，并为每笔写入 `superseded_by_new_pending_order` 状态历史。
5. 创建新订单及初始状态历史。
6. 提交后向相关参与方创建正式通知。

新订单任一步失败时，旧订单取消、容量变化和历史写入全部回滚。`CONFIRMED`、`IN_SERVICE`、`COMPLETED` 等订单不受影响。

黑卡到期或降级时不立即批量取消已有订单。该用户下一次创建新订单时，才按普通用户规则替换旧 `PENDING`，避免无提示的大规模取消。

### 5.3 本地正式数据对齐

- dry-run 重新统计所有多 `PENDING` 用户、涉及订单和资料记录。
- 当前已知 72 个相关测试用户升级为 `black`，保留原订单。
- future operations 生成器必须保证只有 `black` 用户会生成多笔并存的 `PENDING`。
- apply 前后分别核对账号数、黑卡升级数、PENDING 分布、订单历史、ScheduleSlot bookedCount 和未来数据 checker。
- 该升级仅针对本地正式测试数据脚本和本地测试数据库，不得在生产环境按订单数量自动授予付费会员。

## 6. 数据模型

### 6.1 ShopPlatformFeePolicy

独立店铺策略包含：

- `shopId` 唯一关联。
- `feeEnabled`，默认 true。
- `payerType`，仅允许 `SHOP` 或 `TECHNICIAN`，默认 `SHOP`。
- `version`，用于乐观并发控制。
- `createdById`、`updatedById`。
- `createdAt`、`updatedAt`、`deletedAt`。

运营只修改 `feeEnabled`；商户/店铺只修改其权限范围内的 `payerType`。不得通过一个通用写接口同时越权修改两类字段。

### 6.2 OrderAcceptancePause

接单控制记录包含：

- `subjectType`：`MERCHANT_ACCOUNT` 或 `SHOP`。
- `merchantAccountId` 或 `shopId`，二者严格二选一。
- `authorityType`：`OPERATIONS`、`MERCHANT` 或 `SHOP`。
- `status`：`ACTIVE` 或 `RELEASED`。
- `reasonCode` 和必填说明。
- `createdById`、`releasedById`、`startsAt`、`releasedAt`、`releaseReason`。
- `activeKey` 唯一约束，用于同一来源和作用域的幂等活动记录。
- `createdAt`、`updatedAt`、`deletedAt`。

### 6.3 OrderFinancial 补充快照

在现有平台费与返点字段基础上补充：

- `platformFeeEnabledSnapshot`。
- `platformFeePolicyVersion`。
- `platformFeeAmountNdpSnapshot`。
- `platformFeeWalletOwnerType`。
- `platformFeeWalletOwnerId`。
- `platformFeeShortfallNdp`。
- `platformFeeDebtStatus`：`NONE`、`OUTSTANDING`、`SETTLED`。
- `userRewardStatus`：`DISABLED`、`IMMEDIATE`、`PENDING`、`PAID`、`EXPIRED`。
- `userRewardDeadlineAt`。
- `userRewardGrantedAt`。

承担者业务 ID 继续使用现有 `platformFeePayerType` 和 `platformFeePayerId`；钱包 ID 快照用于后续取消、完单和补交，避免技师换店或配置变化后选错钱包。

## 7. 正式接口与 RBAC

### 7.1 运营后台

- 读取和修改全局 Booking 平台费金额。
- 分页读取店铺收费策略和欠费摘要。
- 修改单店 `feeEnabled`。
- 创建和解除集团/单店暂停接单。
- 分页查看负余额、待补交平台费、返点截止时间和过期状态。

### 7.2 商户集团与店铺

- 读取当前店铺平台费金额、收费开关、承担者和余额状态。
- 商户集团修改所属店铺 `payerType`。
- 店铺身份修改自身 `payerType`。
- 商户集团创建/解除自己创建的集团或单店暂停。
- 店铺创建/解除自己创建的本店暂停。
- 不允许商户或店铺修改全局金额、运营收费开关或解除运营暂停。

### 7.3 订单确认

订单确认请求增加可选的不足余额确认对象，至少包含：

- 客户端生成的幂等键。
- 服务端上一次返回的费用预览版本或签名。
- 明确的人工继续确认标识。

余额不足的第一次请求返回结构化 409；暂停接单、未指定技师、预览过期和订单状态变化使用不同错误码。Node/Prisma 原生错误不得透传。

### 7.4 OpenAPI 与列表要求

所有新写接口：

- 使用 Zod。
- 声明 OpenAPI request、response 和错误。
- 使用 JWT、身份作用域和细粒度 permission。
- 列表分页。
- 写入 AuditLog。
- 不接受客户端传入任意 shopId 绕过当前商户/店铺身份范围。

## 8. 页面行为

### 8.1 运营后台

财务页新增正式平台费区域，替换现有仅展示的“结算规则配置”按钮：

- 全局金额编辑。
- 店铺收费开关和当前承担者只读展示。
- 店铺负余额和欠费订单计数。
- 返点待补交/即将过期状态。
- 集团/单店暂停与恢复操作。

### 8.2 商户集团和店铺后台

- 店铺平台费承担者选择。
- 集团和单店暂停控制，按身份隐藏越权操作。
- 每笔余额不足订单显示承担者、平台费、可用余额、缺口和继续接单风险说明。
- 第一次确认不成功后，必须经过明确二次确认才能继续。

### 8.3 技师端

- 当当前订单由该技师承担且余额不足时，显示相同的结构化警告。
- 技师只能对自己有确认权限的订单执行二次确认，不能改变店铺策略。
- 暂停接单时仍可查看订单详情，但确认按钮显示暂停来源和原因。

### 8.4 用户端

- 正常完单返点：100 NDP。
- 待补交：0～100 NDP，并显示截止时间。
- 店铺关闭平台费：0 NDP，说明该单不参与返点。
- 超时：0 NDP，说明补交期限已结束。
- 页面只展示服务端返回的状态和金额，不自行推算截止时间或返点资格。

所有新增用户可见文案必须补齐现有多语言资源。

## 9. 自动任务与充值联动

- 正式钱包充值审核成功后，在同一事务中调用欠费分配服务。
- 欠费按 Wallet owner 和接单时间 FIFO 锁定处理。
- 每笔欠费只允许被一个充值抵扣一次。
- 已完成且在截止时间内结清的订单发放一次 100 NDP 返点。
- 定时任务扫描已过截止时间的 `PENDING` 返点并标记 `EXPIRED`。
- 接口读取时也按服务端时间解析过期状态，避免定时任务短暂延迟造成错误补发。
- 充值与到期任务并发时锁定同一 OrderFinancial，并以数据库时间和状态条件保证唯一结果。
- 所有自动任务必须有有限批次、稳定游标、幂等键、错误日志和可重试能力。

## 10. 错误与事务边界

- 费用配置缺失：按默认收费 500 NDP 与店铺承担解析，并记录默认来源。
- 技师承担但无技师：409，订单保持 `PENDING`。
- 余额不足且未二次确认：409，零写入。
- 费用预览版本变化：409，要求重新展示最新金额与缺口。
- 有效暂停：409，返回暂停作用域、来源和原因；不泄露无权查看的内部说明。
- 并发创建普通用户新订单：最多一个最终 `PENDING`，失败事务不得取消成功事务的新订单。
- 并发充值/过期：返点只能 `PAID` 或 `EXPIRED` 二选一，不重复发放。
- 任一账本、订单历史、费用快照、返点或审计写入失败时，所属业务事务整体回滚。

## 11. 测试与验收

### 11.1 单元与集成测试

覆盖：

- 全局 500 NDP 默认及金额修改。
- 单店收费开关与默认收费回退。
- 店铺承担和技师承担的钱包解析。
- 技师换店后仍使用原钱包快照。
- 零费用无 WalletHold/账本变化，返点关闭。
- 余额不足第一次零写入、二次确认形成负余额。
- 取消恢复负余额、完单结算。
- 即时返点、7 天内补交返点、截止后不返点。
- 多笔欠费 FIFO 与充值幂等。
- 集团/单店暂停的权限、叠加和解除优先级。
- 暂停时可创建和查看 PENDING，但不能确认。
- 普通用户新单替换旧 PENDING，黑卡多单例外，并发仅留一笔。
- RBAC、Zod、OpenAPI、分页和审计。

### 11.2 本地正式数据库

先 dry-run，再在明确授权范围内 apply：

- 创建并核对店铺平台费策略。
