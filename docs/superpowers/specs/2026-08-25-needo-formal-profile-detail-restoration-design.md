# NeeDo 正式用户、员工与技师完整信息卡恢复设计

## 1. 背景与问题

2026-08-25 的正式数据接入将商户员工、运营技师和客户详情从原有的集中式详情卡替换为基础资料表单。该变更避免了旧组件继续显示前端推算或模拟的评分、收入、排班、权限和时间线数据，但同时移除了原有完整信息架构，导致运营人员只能看到少量基础字段。

本次修复恢复“从列表直接打开集中详情抽屉”的交互与原有分区结构，同时坚持正式开发边界：所有展示值必须来自受 RBAC 保护的正式 API 和数据库；尚无正式合同的数据只显示明确的未接入状态，不生成模拟值。

## 2. 目标与范围

### 2.1 员工与技师详情

恢复以下七个页签：

1. 基础资料
2. 状态与数据
3. 技能与服务
4. 排班偏好
5. 薪酬设置
6. 权限与账号
7. 时间线

商户后台使用当前登录店铺范围；运营后台使用平台范围。两端复用同一个正式详情组件和同一套响应结构，只通过作用域与可用操作区分。

### 2.2 客户详情

恢复以下四个页签：

1. 基础资料
2. 预约与消费
3. 权限与账号
4. 时间线

商户后台只读取该客户与当前店铺有关的预约和消费数据；运营后台可以读取平台范围内的正式客户档案。商户端不得借由详情接口访问其他店铺的预约、消费或跨作用域账号资料。

## 3. 数据设计

列表 API 继续保持分页和轻量响应。点击一条记录后，前端再请求对应详情接口，避免把服务、排班、薪酬、角色、身份、审计记录等嵌套数据装进每一条列表记录。

新增或补齐以下只读接口：

- `GET /api/v1/backoffice/technicians/:id`
- `GET /api/v1/merchant-admin/technicians/:id`
- 现有 `GET /api/v1/backoffice/customers/:id` 返回完整客户详情
- 现有 `GET /api/v1/merchant-admin/customers/:id` 返回当前店铺作用域内的完整客户详情

技师详情响应包含：

- 正式基础资料、账号资料、店铺归属和审核状态
- 真实预约状态统计、已完成服务金额和评分汇总
- 今日、本周、本月正式排班时长及近期排班
- 正式技师服务项目
- 当前有效薪酬方案；不存在时返回 `null`
- 作用域内角色与身份
- 可关联到该档案的真实审计记录

客户详情响应包含：

- 正式基础资料与账号状态
- 作用域内预约数量、状态统计、消费总额、最近和下一次预约
- 最近正式预约记录
- 作用域允许查看的角色与身份
- 可关联到该档案的真实审计记录

不会从前端 ID、姓名、数组长度或固定公式推算业务指标。接单率、迟到、排班偏好规则等尚无正式数据合同的字段，在界面中显示“尚未接入正式数据”，不返回伪造数值。

## 4. 前端结构

新增共享的正式详情面板：

- `FormalTechnicianDetailPanel`
- `FormalCustomerDetailPanel`

页面职责保持简单：

- 列表页负责分页、搜索、选择记录和现有写操作。
- API adapter 负责获取正式详情响应。
- 详情面板只消费正式详情视图模型，不读取 mock、浏览器存储或旧实体 store。

视觉结构沿用已确认的图 1：顶部身份摘要、横向页签、分区卡片和数据网格。抽屉继续复用现有可调整宽度的 `Drawer`，不改后台导航和列表布局。

时间线使用现有统一事件时间线视觉。由于本次没有正式档案评论合同，时间线仅展示真实审计与状态记录，不提供本地追加的假评论入口。

## 5. 写操作与错误处理

现有资料保存、审核、软删除操作继续使用原有受保护接口，不把写逻辑放入详情展示组件。

- 详情加载失败：抽屉保留，展示明确错误和重试按钮。
- 详情为空或越权：后端返回统一 `404` 或 `403`，前端不回退到列表记录或 mock。
- 写操作成功：重新加载列表和当前详情，保证抽屉与数据库一致。
- 写操作失败：保留用户输入并显示后端错误，不伪装成功。

## 6. 安全与性能

- 所有详情接口继续使用现有 Zod 路径参数校验、JWT 和对应 RBAC 权限。
- 商户作用域从认证身份派生，不接受客户端传入店铺 ID。
- 列表保持分页；详情只在用户打开记录时加载。
- 关联数据使用有限字段和有限条数，避免无界查询与 N+1。
- 响应禁止包含 `passwordHash`、token、OTP 或其他敏感凭证。
- 详情读取写入审计日志。

## 7. 测试与验收

### 7.1 自动化测试

- 后端服务/API 测试覆盖平台与商户详情读取、店铺范围隔离、无权限拒绝和审计记录。
- Repository 映射测试覆盖真实统计、服务、排班、薪酬、账号、角色、身份和空数据。
- 前端 API 测试覆盖四个详情路径。
- 前端组件/页面测试覆盖七个技师页签、四个客户页签、正式详情请求、加载失败重试及无 mock 依赖。
- 运行前端 lint、test、build，以及后端 lint、test、build。

### 7.2 可视验收

- 在商户后台员工列表打开至少一名正式技师，确认七个页签全部存在且内容来自 API。
- 在商户后台用户管理打开至少一名正式客户，确认四个页签全部存在。
- 在运营后台技师管理和客户资料重复检查同一结构。
- 检查桌面默认宽度和约 390px 窄视口，确认页签可滚动、内容不横向溢出、抽屉可关闭。

## 8. 非目标

- 不新增 Review 表或评价写流程。
- 不新增排班偏好、迟到或接单率数据模型。
- 不恢复任何旧 mock、浏览器持久化薪酬草稿或推算数据。
- 不重构后台导航、列表或其他 Step 12 页面。
- 不修改 Prisma schema；复用现有正式数据表。
