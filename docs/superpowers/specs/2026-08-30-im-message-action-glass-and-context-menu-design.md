# NeeDo 消息操作玻璃菜单与全局右键规则设计

## 1. 状态与目标

本设计于 2026-08-30 经用户确认，并按后续订正更新。

本次只处理三个相互关联的前端问题：

1. 消息长按或桌面右键打开操作菜单后，六个正式按钮、快捷表情与更多表情必须保持可操作。
2. 消息操作菜单改为与 NeeDo 导航同源的液态玻璃容器。
3. 消息操作菜单出现时，聊天输入框必须继续显示并保留状态；只有媒体进入全屏浏览时才隐藏。

用户同时明确：NeeDo 所有页面都不需要浏览器原生右键菜单。因此，全局禁止原生 `contextmenu` 是本次正式产品规则，不再只作为聊天页局部补丁。

本轮不修改消息 REST/SSE、RBAC、数据库、Prisma migration、撤回期限、个人删除语义或表情持久化协议。

## 2. 已确认的交互规则

### 2.1 全局禁止浏览器原生右键菜单

- NeeDo 的用户端、技师端、商户端、运营后台及其他由当前前端入口承载的页面，统一阻止浏览器原生右键菜单。
- 阻止逻辑必须位于共享应用边界，并在 NeeDo 组件处理事件后于文档冒泡边界取消默认行为，不能依赖每个页面或组件各自补 `onContextMenu`。Chrome 实测表明捕获阶段过早取消会吞掉 React 的自定义消息菜单。
- 监听只执行 `preventDefault()`，不得吞掉正常左键、键盘、滚动、拖动、文本输入或 NeeDo 自有菜单逻辑。
- 聊天消息的桌面右键仍然打开 NeeDo 消息操作菜单；全局规则只禁止浏览器菜单，不得阻止该业务回调。
- 消息菜单已经打开后，在菜单本体、箭头、快捷表情、按钮或遮罩区域再次右键，也不得出现浏览器原生菜单。
- 组件级防护可以保留为纵深保护，但共享全局规则是最终权威边界，避免 React 重渲染或 portal 切换时出现空隙。

### 2.2 长按、松手与菜单点击

- 长按达到现有阈值后打开 NeeDo 消息菜单。
- 触发长按的同一轮松手及其合成 click 不得立即关闭菜单或触发消息媒体预览。
- 松手保护只能抑制打开手势的尾部事件；随后用户对六个操作、快捷表情和更多按钮的第一次真实点击必须立即生效。
- 菜单内 pointer、click 与 contextmenu 事件不得被聊天记录的关闭逻辑、文字选区、页面拖动或遮罩抢占。
- 回复、转发、复制、信息置顶、撤回、删除继续使用现有正式回调与权限规则，不新增假成功。
- 快捷表情继续调用正式 reaction mutation；同一消息、同一表情的进行中请求仍保持去重。

### 2.3 输入框持续存在

- 聊天输入组件不再与消息菜单二选一渲染。
- 消息菜单打开时，输入框、已有草稿、引用草稿、语音模式及已打开的输入面板状态不得因为卸载而丢失。
- 菜单作为独立 portal 浮层显示在聊天内容和输入框上方；遮罩存在时，输入框保持可见但暂时不接受误触。
- 关闭消息菜单后，输入框恢复可操作，原草稿和原模式保持不变。
- 只有媒体进入全屏预览时才隐藏输入框；退出全屏预览后恢复原输入框状态。
- 普通图片气泡仍在聊天列表内、媒体选择器打开、消息菜单打开、撤回提示显示等状态，都不能隐藏输入框。

## 3. 玻璃视觉语言

消息菜单不复制一组固定颜色，而是复用底部导航 `.client-liquid-glass-nav` 的材质规则并提取共享玻璃表面类：

- 使用 `--client-elevated`、`--client-bg`、`--client-line`、`--client-text` 和现有主题变量；
- 使用与导航同源的半透明渐变、细边框、内高光、悬浮阴影、模糊、饱和度与对比度；
- 日间、夜间、深绿、黑金、活力黑白、冷黑灰和霓虹主题均保持可读；
- 菜单箭头必须使用同一玻璃背景和边框，不能留下实色接缝；
- 六个操作单元可以保留略深的内部层级，但外层容器必须清晰呈现导航同款玻璃材质；
- 快捷表情保持当前紧凑布局和触控尺寸，不因视觉调整缩小命中区域；
- `prefers-reduced-motion: reduce` 下不得依赖位移动画才能命中按钮。

本次签名视觉是“导航同源的悬浮玻璃消息卡”，而不是新增独立品牌风格。

## 4. 组件与状态边界

主要实现边界：

- 共享前端入口：安装和卸载一次全局 `contextmenu` 文档冒泡监听，覆盖当前 NeeDo 所有页面，同时让消息组件优先打开 NeeDo 菜单。
- `src/features/im/components.tsx`：`ImMessageActionSheet` 继续作为唯一消息操作菜单；接入共享玻璃表面类并完整保护菜单层事件。
- `src/features/im/pages.tsx`：`ImConversationRoomPage` 始终渲染 `ImChatComposer`；消息菜单和媒体全屏预览分别作为独立状态层处理。
- `src/styles.css`：提取导航与消息菜单共用的液态玻璃材质规则，不用 TSX 复制主题分支。
- 相关测试：覆盖全局右键规则、长按尾部事件、真实按钮点击、快捷表情点击、输入框持续挂载和媒体全屏例外。

不得新增第二套消息菜单、第二套输入框、页面级 mock、全局轮询或新的后端接口。

## 5. 错误与可访问性

- 原生右键被禁止后，不显示替代性的空菜单或提示。
- NeeDo 消息菜单仍使用语义化 `button`、可见焦点环和现有 `aria-label`。
- 禁用的撤回按钮继续真实禁用；其他按钮不得因遮罩或透明层变成“看得到、点不到”。
- 复制、撤回、删除和 reaction mutation 失败继续使用现有提示与回滚逻辑。
- 菜单打开期间输入框虽然可见，但遮罩负责阻止误触；不能通过给输入框永久设置 `disabled` 破坏关闭后的状态。
- 媒体全屏预览需保持明确的关闭入口；退出后恢复输入框，不重置草稿。

## 6. 测试先行要求

实施前先增加会失败的回归测试，至少覆盖：

1. 在共享应用边界派发可取消的 `contextmenu`，事件始终 `defaultPrevented=true`。
2. 消息气泡右键同时触发 NeeDo 菜单且不会放行浏览器默认菜单。
3. 消息菜单本体、操作按钮、快捷表情、更多按钮和遮罩上的右键均被阻止。
4. 长按打开后，同一轮 pointerup/click 不关闭菜单；紧接着第一次点击回复或快捷表情立即执行一次。
5. 六个正式操作分别通过完整 pointerdown、pointerup、click 序列执行一次，不被外层捕获逻辑吞掉。
6. 快捷表情和更多表情使用相同真实点击序列并执行一次。
7. `menuState` 存在时 `ImChatComposer` 仍在 DOM 中，草稿与面板状态没有因卸载重置。
8. 媒体全屏预览打开时输入框不渲染，退出后输入框和原草稿恢复。
9. 消息菜单使用共享液态玻璃类和主题变量，箭头与菜单表面材质一致。

测试必须先观察到正确原因的失败，再实施最小修复。

## 7. 正式浏览器验收

在 `http://127.0.0.1:5180` 正式前后端组合上验收：

- Chrome 桌面右键消息：只出现 NeeDo 菜单，不出现浏览器菜单；
- Chrome 在普通 NeeDo 页面空白区和控件区右键：浏览器菜单不出现；
- 约 `440×956` 移动视口长按消息，松手后菜单保持打开；
- 逐项实际点击回复、转发、复制、信息置顶、撤回、删除、快捷表情和更多表情；
- 对会产生持久化或删除结果的操作使用受控正式测试消息，并核对刷新后的服务端权威状态；
- 菜单打开时输入框容器仍完整可见；关闭后草稿和输入模式不丢失；
- 普通聊天、菜单打开、媒体全屏打开和退出四个状态的输入框显隐符合规则；
- 至少检查一个日间主题和截图对应的夜间主题；
- 页面横向溢出为 0，新增应用 console error 为 0。

自动化测试、lint 和构建不能替代这些可见交互验收。

## 8. 回滚边界

本轮无 API、数据库或 migration 变更。若验收失败，只回滚：

- 全局 `contextmenu` 文档冒泡监听；
- 消息菜单共享玻璃类及相关样式；
- 输入框与菜单/媒体预览的渲染条件；
- 对应前端测试。

不得回滚或删除正式消息、反应、撤回、个人删除、SSE 或用户草稿数据。
