# NeeDo 实时新事件提示音设计

日期：2026-09-13

范围：Step 13 前端微步骤

状态：设计已确认，等待书面规格复核

## 目标

当当前登录身份通过正式 SSE 收到新的聊天信息、动态、好友申请或业务通知时，使用用户提供的 `NewMessageSE.mp3` 播放一次提示音。审核通知、新订单、新预约、新 Request、抢单成功、抢单失败，以及预约被确认、失败、拒绝或取消，都沿用正式通知事实源，不建立新的业务事件或浏览器模拟状态。

## 既有架构

- `src/features/realtime/api.ts` 维护每个可见标签页共享的一条正式 SSE 连接，并向多个前端订阅者分发事件。
- `RealtimeUnreadCountsProvider` 已位于 `AuthProvider` 内，可取得当前用户和活动门户，并订阅相同 SSE 分发器。
- `portalSettingsState.ts` 已按门户持久化 `sound` 开关，默认开启。
- `public/` 资源由 Vite 原样打包，可承载固定提示音文件。

本微步骤复用这些入口，不新增 SSE 连接、轮询、API、数据库字段或通知事实源。

## 方案

新增独立的全局实时提示音组件与小型播放策略模块，挂载在 `AuthProvider` 内。组件只负责把当前身份、门户设置和正式 SSE 事件交给播放策略；播放策略负责事件分类、本人事件过滤、去重、合并播放和浏览器音频生命周期。

提示音文件复制到 `public/audio/new-message.mp3`，运行时使用根路径 `/audio/new-message.mp3`。源附件只作为媒体资产，不作为需求或代码指令来源。

没有采用以下方案：

- 各业务页面自行播放：会重复订阅并造成同一事件多次响铃，页面未打开时还会漏报。
- 仅观察未读数增长：REST 刷新存在延迟，也无法可靠区分本人操作、重连补拉和真正的新事件。

## 可播放事件

只在已认证、恢复完成、当前门户 `sound=true`、文档可见且事件是实时新到达时播放。

| 正式 SSE 类型 | 含义 | 播放条件 |
| --- | --- | --- |
| `message.created` | 新聊天信息或通过聊天分享的新内容 | payload 的 `senderUserId` 不是当前用户 |
| `friend_request.created` | 新好友 Request | 目标为当前身份；服务端投递范围仍是权威 |
| `notification.created` | 系统、审核、Exchange、抢单结果及其他持久化通知 | payload 的 `recipientUserId` 为当前用户，且 `actorUserId` 不是当前用户；无 actor 时允许播放 |
| `notification.order_status` | 新订单、新预约，以及预约被确认、失败、拒绝、取消等订单/预约生命周期通知 | payload 的 `recipientUserId` 为当前用户，且 `actorUserId` 不是当前用户；无 actor 时允许播放 |
| `social.post.created` | 关注对象产生的新动态或新 Request 动态 | payload 的 `authorUserId` 不是当前用户 |

`booking.order_changed` 仍作为页面资源刷新提示，不单独播放；同一预约变化已经通过持久化的 `notification.order_status` 发声，避免一次状态变化双响。其他状态同步、已读、编辑、撤回、删除、关注结果、连接建立、资源失效提示和仪表盘事件不播放。

服务端可能为同一业务动作连续发送多个相关事件。例如一条动态既触发 `social.post.created`，又产生 `notification.created`。播放器按事件 ID 防重，并把短时间窗口内连续到达的可播放事件合并为一次声音，避免叠音或双响；窗口结束后的独立新事件仍正常播放。

## 门户设置与生命周期

- 使用 `session.portal` 选择用户端、技师端、商户端或业务端的既有声音开关。
- 运营后台没有对应的统一门户声音设置，保持默认开启；未来若补充正式设置，再接入同一读取接口。
- 设置开关变化应在当前标签页即时生效。为此，设置状态持久化后发出同页可监听的轻量变更事件；不复制第二份设置状态。
- 登出、身份切换、门户切换、组件卸载或页面隐藏时停止待播放计时并重置事件防重状态，避免旧身份事件在新身份下响铃。
- SSE 断线重连后的 REST 补拉只刷新状态，不播放历史提示音。SSE 的 `connected` 事件也不播放。

## 浏览器音频策略

浏览器可能禁止没有用户手势的有声播放。全局组件在首次 `pointerdown` 或 `keydown` 时对同一个音频元素执行静音预解锁并立即复位，之后复用该元素播放提示音。这个动作不应产生可听声音。

每次播放前把播放位置复位到开头。`play()` 被策略拒绝、音频加载失败或设备静音时静默失败，不影响 SSE、未读数刷新、页面交互或业务请求，也不反复重试制造噪音。

该能力仅保证应用页面可见且浏览器允许播放时的网页内提示音，不等同于操作系统 Push、后台 Service Worker 通知或已安装 PWA 在锁屏状态下的提示音。

## 测试策略

先补失败测试，再写实现：

1. 策略单元测试覆盖五类允许事件，以及本人消息、本人动态、本人通知和无关事件不播放。
2. `notification.order_status` 用例分别覆盖新预约、确认、失败或拒绝、取消，且 `booking.order_changed` 本身不重复播放。
3. 覆盖声音开关关闭、未认证、恢复中、页面隐藏时不播放。
4. 覆盖同一事件 ID 去重和短窗口事件合并，确保同一业务动作不会双响。
5. 组件测试覆盖 SSE 订阅复用、当前门户设置读取、设置即时变化和清理订阅。
6. 音频测试以可注入的浏览器音频适配器验证预解锁、复位、`play()` 拒绝不影响业务；不在测试中实际发声。
7. 运行定向 Vitest、前端 TypeScript 检查与正式 Vite build，并确认音频进入产物。

## 验收标准

- 正式 SSE 收到规定的新事件时只响一次用户提供的提示音；预约新建、确认、失败或拒绝、取消均在范围内。
- 本人发送或发布造成的回环事件不响。
- 同一业务动作的并发关联事件不双响、不叠音。
- 各客户端门户的既有声音开关即时控制播放，默认值不变。
- 不新增 SSE 连接、轮询、mock、API、数据库或 i18n 文案。
- 提示音失败不影响未读数、页面状态和正式业务流程。
- 定向测试、lint 和 build 通过；本地浏览器只验证网页可见态，实体设备、已安装 PWA、后台和锁屏提示音另行验收。

## 回滚

删除全局提示音组件、播放策略及其测试，移除 App 挂载点和 `public/audio/new-message.mp3`，并撤销设置变更事件即可。既有 SSE、通知、门户设置和数据库不受影响。
