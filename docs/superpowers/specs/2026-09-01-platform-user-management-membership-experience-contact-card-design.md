# NeeDo 平台用户管理、会员经验与联系人名片正式化设计

**日期：** 2026-09-01
**适用阶段：** Step 12 运营后台真实数据、Step 13 IM / Social / Notification 后端化
**状态：** 已完成逐段业务确认，待用户复核本文档
**范围：** 平台顾客会员、Lv.1–100 经验、运营后台用户管理二级入口、聊天联系人名片和联系人信息页

## 1. 背景与目标

当前仓库已经具备真实用户、顾客资料、运营用户详情、会员免费赋予、RBAC、审计、IM 联系人资料和店铺会员卡能力，但平台顾客会员仍以自由字符串存在，用户管理入口分散，Lv 标签来自非正式评分映射，聊天名片也可能退回缺少正式资料的简易旧卡。

本设计建立一套平台级、可审计、可版本化的数据来源，并让以下表面读取同一个正式事实：

1. 运营后台用户列表、分组、全局设置、会员等级和权益说明；
2. 用户中心昵称旁的 `Lv.x`；
3. 联系人信息页和聊天联系人名片；
4. 登录、服务完成、点赞、NDP 消费和会员续期产生的经验流水；
5. Request 优先、账号绑定和 eKYC 下单限制。

店铺自行发行的储值卡、次数卡和店铺权益卡不属于本设计的平台会员，二者不得混表或互相改变资格。

## 2. 已确认的核心决策

### 2.1 等级适用范围

- 只有顾客身份拥有 `Lv.1–100`。
- 技师身份和店铺商户身份不计算、不展示等级。
- 同一 User 同时具有顾客与技师身份时，经验仍归属于该 User 的顾客范围；技师卡面不显示等级。
- 所有既有用户在新体系启用时从 `Lv.1 / 0 EXP` 开始，不追溯历史事件；新注册并建立顾客身份的用户同样从 `Lv.1 / 0 EXP` 开始。

### 2.2 四档平台会员

平台会员固定为四档，不能新增、删除或改名：

| 系统代码 | 显示名称 | 默认有效期 | 默认经验倍率 |
| --- | --- | --- | ---: |
| `free` | 免费会员 | 永久 | 1 倍 |
| `silver` | 白银会员 | 30 天 | 2 倍 |
| `gold` | 黄金会员 | 30 天 | 5 倍 |
| `black_diamond` | 黑钻会员 | 30 天 | 10 倍 |

运营后台可以修改倍率、权益、卡面主题、说明和启停状态。修改必须发布新版本；历史经验继续使用事件发生时的会员版本快照。

### 2.3 会员价格

暂定月度卡面价值：

- 白银：300 NDP 等值；
- 黄金：1,999 NDP 等值；
- 黑钻：4,999 NDP 等值；
- 年费按 10 个月卡面价值计算。

价格和年费计价月数由运营后台配置，不写死在经验服务中。App Store、网站、线下转账或运营内部赋予的实际付款凭证不决定经验；会员资格在续期日成功更新时，以当时发布的卡面价值生成会员续期经验事件。

中途升级只按已确认的卡面价值差额生成经验；降级不扣除历史经验，新的会员版本从下一次有效期或续期规则开始生效。

## 3. Lv.1–100 曲线

Lv.100 的累计门槛固定为 20,000 EXP。前 30 级升级较快，之后逐步放缓，不使用直线增长。

V1 累计门槛公式：

```text
threshold(level)
= round(20000 * ((level - 1) / 99) ^ 1.8)
```

正式实现时预生成并测试 100 个整数门槛，不让不同客户端各自运行浮点公式。

关键门槛：

| 等级 | 累计 EXP |
| --- | ---: |
| Lv.1 | 0 |
| Lv.10 | 267 |
| Lv.20 | 1,025 |
| Lv.30 | 2,194 |
| Lv.50 | 5,639 |
| Lv.70 | 10,443 |
| Lv.90 | 16,512 |
| Lv.99 | 19,638 |
| Lv.100 | 20,000 |

达到 20,000 EXP 后等级固定为 Lv.100，但经验流水和总经验继续累计，便于审计和未来扩展。

## 4. 经验来源与计算

### 4.1 基础事件

| 事件 | 基础经验 | 幂等与范围 |
| --- | ---: | --- |
| 每日签到 | 1 EXP | 当前会员版本点亮签到权益时，日本日期内首次成功登录；Refresh Token 和重复登录不算 |
| 完成服务 | 10 EXP | 订单首次正式进入 `COMPLETED`；只奖励消费顾客 |
| 收到有效点赞 | 1 EXP | 同一点赞人和同一动态永久最多一次；取消不扣、重新点赞不重复 |
| NDP 消费 | 100 NDP = 1 基础 EXP | 只读取最终结算的钱包消费流水 |
| 会员续期 | 按已发布卡面价值折算 | 续期或有效资格更新成功时一次 |

签到、完成服务、有效点赞、NDP 基础经验和会员续期基础经验均乘以事件发生时的会员倍率。完成服务和有效点赞是独立基础事件；签到、NDP 基础经验和会员续期基础经验还分别受当前会员版本的签到权益、NDP 消费经验权益门禁控制。

### 4.2 NDP 基础经验权益

NDP 产生经验不是不可关闭的全局规则，而是一项会员权益；免费、白银、黄金、黑钻默认全部点亮。

常规规则：

```text
baseNdpExp
= benefitEnabled
  ? settledNdpAmount / 100
    * globalCampaignFactor
    * membershipMultiplier
  : 0
```

全局常规换算为 `100 NDP = 1 基础 EXP`。运营可发布有开始和结束时间的临时活动，例如 `100 NDP = 10 基础 EXP`，等价于活动系数 10。临时活动采用日本时区输入、UTC 持久化，有效时间不能重叠。

每笔事件保存全局规则版本、活动版本、会员等级版本和倍率快照。活动或倍率之后变化时，不重算历史经验。

### 4.3 各会员额外赠送经验

每档会员可独立配置：

```text
每消费 X NDP，额外赠送 Y EXP
```

额外赠送经验：

- 不乘会员倍率；
- 不受全局临时活动系数影响；
- 只读取实际结算的 NDP 消费，不把会员卡卡面价值计入额外赠送；
- 采用固定精度累计，不因拆分消费丢失余数；
- 权益关闭后只停止新事件，不扣除历史经验。

### 4.4 金额与精度

经验使用定点整数单位保存，建议 `10,000 units = 1 EXP`。所有金额计算先进入定点单位，不在每个前端显示层自行四舍五入。

会员费通过 NDP 支付时，会员续期事件和钱包消费流水必须共享业务来源并去重，不能发放两次基础经验。

退款引用原消费经验流水生成反向冲正条目，使用原活动、原倍率和原额外赠送规则；不得使用退款当天的新规则。

## 5. 运营后台用户管理信息架构

用户管理二级入口统一整改为：

```text
用户管理
├─ 用户列表
├─ 用户分组
├─ 用户全局设置
├─ 会员等级设置
└─ 会员权益说明
```

当前分散的账号管理、用户资料、CRM 和用户数据入口收拢到这套工作区。旧能力在完成迁移前保留路由兼容，但不能继续形成新的并行数据源。

## 6. 用户列表

### 6.1 数据范围

列表读取所有正式 User，而不只读取存在 CustomerProfile 的账号。任何响应都不得返回密码哈希、OTP、Token、eKYC 原文或其他敏感材料。

默认列：

- NeeDo ID、头像、昵称；
- 身份类型；
- 手机和邮箱绑定状态；
- 平台会员类型；
- Lv 和当前 EXP；
- 系统分组和手动分组；
- NDP 余额和累计完成消费；
- eKYC 状态；
- 注册时间、最后登录时间和账号状态；
- 详情、编辑、会员调整、分组调整和状态管理。

技师和店铺身份行不显示 Lv；同一账号具有顾客身份时，详情中的顾客范围可以显示等级。

### 6.2 查询与分页

支持按 NeeDo ID、昵称、手机、邮箱、会员类型、系统分组、自定义分组、身份类型、来源、账号状态、eKYC、Lv/EXP 范围、NDP 余额范围和注册时间筛选。列表必须服务端分页并建立对应索引，不允许一次性返回全量用户或 N+1 查询。

### 6.3 用户详情

详情抽屉分区：

1. 基础资料；
2. 会员与经验；
3. 预约与消费；
4. 账号、角色与权限；
5. 用户分组；
6. 操作审计。

已有正式用户详情和时间线应当复用，不能另建 mock 详情。

## 7. 用户分组

系统自动分组固定为：

- 免费用户；
- 白银会员；
- 黄金会员；
- 黑钻会员；
- 运营成员。

会员系统分组根据当前有效平台会员资格动态解析，四档互斥。运营成员根据有效运营角色动态解析，可以与会员分组重叠。

系统分组不能删除或修改名称；简介可以由有权限的运营人员维护。系统分组成员不能手动加入或移除。

自定义分组支持新增、修改名称和简介、手动加入或移除用户、批量操作和归档。归档分组只结束分组关系，不删除或停用用户。

## 8. 用户全局设置

### 8.1 开关

- 是否要求绑定手机；
- 是否要求绑定邮箱；
- 上门服务是否必须通过 eKYC；
- 到店服务是否必须通过 eKYC。

新注册用户在账号激活前满足已开启的绑定要求。已有用户不被即时强制退出，在下一次登录或受保护操作时进入补充绑定流程。

eKYC 开关由下单和 Request 发布后端执行，只限制开关生效后的新订单和新 Request，不追溯取消既有订单。

### 8.2 NDP 经验规则

页面显示当前常规规则 `100 NDP = 1 基础 EXP`，并提供临时活动列表、草稿、预约发布和冲突校验。

临时活动显示活动名称、开始/结束时间、活动倍率、状态、创建人、发布时间和示例计算。时间重叠时拒绝发布，不进行部分写入。

## 9. 会员等级设置与卡面主题

会员等级页只展示四档固定会员。点击某档后打开编辑窗口：左侧实时预览实际详细信息卡和简易信息卡，右侧编辑倍率、权益、说明和颜色，底部提供取消、保存草稿和发布。

详细信息卡可分别设置：

- 左上角荧光强调色；
- 大面积主体背景色；
- 各项目底色；
- 卡片外边框颜色；
- 项目边框颜色；
- 头像边框颜色。

简易信息卡可设置：

- 上部颜色；
- 下部颜色。

预览必须复用用户端实际卡片组件。系统自动计算文字对比色，并阻止发布可读性严重不足的组合。草稿不会影响用户端，只有发布版本生效。

## 10. 会员权益

权益目录只保留以下七项：

1. **优先下单**：具有有效权益的 Request 在普通 Request 前展示；同档按发布时间排序，不改变状态机、资格或价格。
2. **NDP 消费经验**：控制基础 NDP 经验和该档额外赠送配置；四档默认开启。
3. **会员签到**：日本日期内首次成功登录完成当天签到并发放一次签到经验；四档默认开启。
4. **专属客服**：服务号能力未实现前，只显示明确不可用的入口，不创建虚假服务号；未来接通后，权益失效时入口变灰且禁止发言。
5. **专属优惠**：保存权益配置和说明；正式优惠券发放必须等待服务号和优惠券发放能力，当前不得伪造优惠券。
6. **会员日**：保存权益配置和说明；具体活动由后续正式活动版本引用。
7. **生日礼**：保存权益配置和说明；正式发放必须具备生日资料、活动版本和发放流水。

权益说明页可编辑图标、多语言名称和简介、排序及全局状态。会员等级页只负责点亮或取消某档权益。全局停用优先于等级点亮状态。

V1 仅默认点亮四档的 NDP 消费经验和会员签到。优先下单、专属客服、专属优惠、会员日和生日礼默认关闭，由运营明确发布后才生效。关闭签到或 NDP 消费经验只影响之后的新事件，不冲正历史经验。

## 11. 联系人名片

### 11.1 发送流程

```text
聊天右下角“+”
→ 名片
→ 当前自己和有效好友列表
→ 选择一人
→ 发送简易联系人信息卡
```

候选仅包括当前自己和双向有效好友。前端只提交目标 User ID；服务端验证会话参与者、好友关系和候选合法性后，读取正式资料生成不可伪造的消息快照。

### 11.2 简易卡字段

- NeeDo 昵称；
- eKYC 绿色对钩；
- Lv 等级；
- NeeDo ID；
- 自我介绍，超出时省略；
- 会员简易卡上部和下部主题色。

技师和店铺身份不显示等级。快照保存发送时的公开资料、等级、会员类型、eKYC 状态和会员主题版本。历史消息不因之后会员到期或改色而变化；点击卡片后读取当前资料和当前关系。

旧联系人名片继续兼容。无法解析完整快照时显示安全降级卡片，不能让消息列表崩溃。

## 12. 联系人信息页

名片统一打开联系人信息页：

- 好友：显示“开始聊天”，进入双方会话；
- 非好友：显示“取消”和“添加好友”；
- 自己：只显示个人资料，不显示添加好友；
- 头部左侧保留返回按钮，右侧增加通用关闭按钮。

语言能力和自我介绍栏目始终存在。没有设置时显示“未设置”，不再隐藏整段布局。

联系人详细信息卡和简易名片都从正式等级账户、平台会员版本和 eKYC 状态读取数据，不再使用评分映射推导 Lv。

## 13. 正式数据模型

建议新增或正式化以下表。所有表遵守 `id / createdAt / updatedAt / deletedAt`、索引和软删除规范。

### 13.1 会员与权益

- `PlatformMembershipTier`：四个稳定系统代码和当前发布版本；
- `PlatformMembershipTierVersion`：倍率、有效期、说明、主题、价格、年费计价月数、状态和生效时间；
- `PlatformMembershipBenefit`：七项权益目录、多语言文案、图标、排序和全局状态；
- `PlatformMembershipTierBenefit`：某等级版本对权益的点亮状态及经过 Zod 校验的种类化配置；
- `PlatformMembershipEntitlement`：用户会员资格、来源、开始/结束时间、操作人和续期业务引用。

同一顾客同时只能存在一个有效平台会员资格。白银、黄金或黑钻到期后由服务端解析为免费会员，并自动改变系统分组、倍率和权益。

### 13.2 用户分组与策略

- `BackofficeUserGroup`：系统或自定义分组、名称、简介、状态和创建人；
- `BackofficeUserGroupMembership`：仅保存自定义组成员关系和操作人；
- `UserGlobalPolicyVersion`：四项全局开关、常规 NDP 换算和生效时间；
- `NdpExperienceCampaign`：临时倍率活动、时间范围、状态和发布人。

系统分组成员通过会员资格和运营角色查询派生，不建立需要异步同步的第二份成员事实。

### 13.3 经验账户与流水

- `UserExperienceAccount`：User 唯一账户、总定点单位、当前等级和乐观锁版本；
- `UserExperienceEntry`：事件类型、来源类型/ID、唯一幂等键、基础单位、活动系数、会员倍率、额外单位、最终单位、会员版本、策略版本、发生时间和反向条目引用。

经验流水不可更新或删除。修正只能新增补偿或冲正条目，并在同一事务内更新账户汇总。

## 14. 既有会员迁移

已知值按以下规则归一：

- `standard`、`free` → `free`；
- `silver` → `silver`；
- `gold` → `gold`；
- `black`、`黑卡`、`黑钻` → `black_diamond`。

迁移前必须扫描全部现有非空值。出现未知值时输出公开 ID 和值的安全清单并停止迁移，不静默降为免费。

现有 `CustomerProfile.membershipLevel` 在过渡期间只作为兼容读字段；正式写入统一走平台会员资格服务，避免双写分叉。后续独立微步骤再移除兼容字段。

## 15. API、RBAC 与审计

正式 API 前缀均为 `/api/v1`，列表分页，Body 经 Zod 校验，Controller 不访问 Prisma。

主要接口族：

- `/backoffice/users`；
- `/backoffice/user-groups`；
- `/backoffice/user-global-settings`；
- `/backoffice/ndp-experience-campaigns`；
- `/backoffice/membership-tiers`；
- `/backoffice/membership-benefits`；
- `/backoffice/users/:id/experience-entries`；
- `/im/conversations/:conversationId/contact-cards`。

权限拆分为用户查看/编辑、分组查看/编辑、全局设置查看/发布、会员等级查看/发布、权益查看/编辑、经验流水查看和联系人名片发送。

以下操作必须记录审计：

- 会员资格赋予、续期、升级、降级和到期处理；
- 会员等级版本发布；
- 全局策略和 NDP 活动发布；
- 自定义分组创建、编辑、归档和成员变更；
- 权益全局启停；
- 用户账号状态变化。

审计 metadata 不记录完整手机、邮箱、eKYC 原文或消息正文。

发布使用乐观版本控制。版本已被其他运营修改时返回 409；活动时间重叠、主题不可读、未知会员值和非法权益配置均拒绝发布，不进行部分写入。

## 16. UI 错误与降级

- 用户列表、分组成员和经验流水均具备加载、空数据、错误与重试状态；
- 主题保存失败保留本地草稿并指出具体字段；
- 未接通权益明确显示“能力未接通”，不能显示已自动发放；
- 联系人名片目标不是自己或有效好友时服务端拒绝；
- 会员到期与发送名片并发时，以创建消息事务解析到的有效会员版本为准；
- 权益关闭或会员到期只影响之后的新事件，历史经验和历史卡片快照保留。

## 17. 微步骤实施顺序

为遵守一次一个正式微步骤的仓库规范，实施拆分为：

1. 平台会员配置地基：四档会员、版本、权益目录、主题、价格、会员资格、RBAC、审计和 OpenAPI；
2. 用户分组与全局策略：系统/自定义分组、绑定/eKYC 开关、NDP 常规规则和临时活动；
3. 用户经验账户与基础事件：Lv 账户、不可变流水、签到、服务完成和有效点赞；
4. NDP 经验事件：钱包结算、会员倍率、活动、额外赠送、续期和退款冲正；
5. 运营后台五个入口：正式列表、详情、分组、策略、等级和权益 UI；
6. 规则执行：绑定要求、上门/到店 eKYC、Request 优先和会员到期降级；
7. 聊天联系人名片：正式候选、服务端快照、主题、eKYC、Lv、简介和点击导航；
8. 未接通权益入口：只增加明确不可用的专属客服入口，其余发放能力留待依赖具备。

每个微步骤独立 migration、提交、测试和回滚，不把整组能力做成一个巨大提交。
