# 商户后台超时与本地 worktree 隔离设计

## 背景

商户后台的门店总览与员工列表在本地开发环境同时出现数据加载失败。员工列表暴露 `error.network.timeout`，并在错误提示下方继续显示“没有符合条件的正式技师”。

现场证据表明，正式 backend、MySQL、Redis 与 Vite API 代理恢复后均健康；相同 LifeDance 商户身份下，门店总览和员工列表接口都能在几十毫秒内返回真实数据。超时发生前，项目根目录下另一个隔离 worktree 创建 HTML 与 `tsconfig.json`，当前 Vite 开发服务器将这些文件误判为主项目变化，连续触发整页重载、缓存清除与重新编译。前端请求超过固定 10 秒后被中止，页面随后保留错误状态。

## 目标

1. 隔离本地 Git worktree 文件变化，避免其他开发任务干扰当前 Vite 服务。
2. 为商户后台关键只读数据增加一次有限的瞬时故障重试。
3. 让错误状态、加载状态、成功空状态互斥，避免把请求失败误报为“没有数据”。
4. 保持正式 API、RBAC、真实数据库和现有页面结构不变。

## 非目标

- 不提高 10 秒请求超时上限。
- 不给写入、删除、审核、财务操作增加自动重试。
- 不扩展到用户端、技师端、运营后台或全站请求。
- 不新增 mock、离线假数据或本地兜底业务数据。
- 不改变商户身份、权限或 API 契约。

## 方案

### 1. Vite 开发监听隔离

在 `vite.config.ts` 的 `server.watch.ignored` 中排除：

- `**/.worktrees/**`
- `**/worktrees/**`

现有 `test.exclude` 继续负责 Vitest 文件发现；开发 watcher 规则独立配置，因为测试排除规则不会影响 Vite dev server。

配置测试必须读取实际 `serve` 配置并断言这两个规则存在，防止以后只保留测试排除而再次遗漏开发 watcher。

### 2. 商户只读请求有限重试

复用现有 `loadCoreReadWithTransientRetry`：

- Dashboard 的共享请求资源通过该工具加载。
- 员工列表与客户列表的正式分页读取通过该工具加载。
- `408`、`429`、`5xx`、浏览器网络异常只重试一次，默认等待 300ms。
- `401`、`403`、参数错误和其他确定性业务错误直接返回。
- 共享 Dashboard 缓存继续合并相同商户范围内的并发请求；一次重试序列仍只对应一个共享 Promise。

这不是慢接口掩盖机制。请求仍在 10 秒时中止，第二次失败后立即进入明确错误状态。

### 3. 商户读取错误呈现

建立一个小型、可测试的商户读取错误描述函数，把正式 API 错误转换为当前语言的用户可读文案：

- `401`：登录状态失效。
- `403`：当前身份无权限。
- `408`：网络响应超时。
- `5xx`：本店经营数据服务暂时不可用。
- 其他网络异常：检查网络后重试。

门店总览与人员列表复用该描述函数。人员列表只有在请求成功且 `total === 0` 时显示空状态；存在错误时只显示错误提示和显式重试按钮。

## 数据流

```text
商户页面
  -> 共享 Dashboard 资源 / 人员分页读取
  -> 正式 /api/v1/merchant-admin/*
  -> 瞬时错误？
       是 -> 等待 300ms -> 仅重试一次
       否 -> 直接返回错误
  -> 成功：渲染真实数据或真实空状态
  -> 最终失败：渲染本地化错误与手动重试
```

## 测试与验收

测试先行并观察失败：

1. Vite `serve` 配置必须忽略两个 worktree 目录模式。
2. Dashboard 第一次超时、第二次成功时恢复，并且共享缓存行为不变。
3. Dashboard 的非瞬时错误不重试。
4. 人员正式分页读取使用有限重试。
5. 人员页面错误时不渲染成功空状态。
6. 原始错误键不直接展示给用户，超时文案走现有 i18n。

实现后运行：

- 相关前端测试。
- 完整 `npm test`。
- `npm run lint`。
- `npm run build -- --mode formal`。
- 本地正式服务健康检查。
- 使用真实 LifeDance 商户身份验收门店总览、员工列表、显式刷新与真实返回数量。

## 上线边界

生产构建不运行 Vite dev watcher，因此 worktree 监听问题只属于本地开发链路。商户只读请求的有限重试、明确错误文案和错误/空态互斥会进入正式构建，用于抵御生产网络中的短暂抖动。任何持续超时仍会暴露为可观察、可重试的错误，不会伪装成空数据。
