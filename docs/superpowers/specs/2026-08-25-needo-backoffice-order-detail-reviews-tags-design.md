# NeeDo 后台订单详情、双向评价与后台标签设计

日期：2026-08-25  
状态：已完成交互设计确认，等待书面规格复核  
适用阶段：Step 10 订单事实链路的定向补强，以及 Step 12 后台真实数据详情纵向切片

## 1. 目标

修复新预约已写入正式数据库、但在后台订单数据第一页不可见的问题；在运营后台订单列表中明确区分下单时间和预约时间；把订单详情升级为由正式接口驱动的集中详情抽屉，并用与用户端一致的预约状态节点展示时间线。

同一纵向切片还要补齐订单关联客人和技师的正式资料、逐单双向评价、评价标签，以及仅平台后台可见的系统/人工行为标签。通讯录中用户自己在本地标记的个人标签不属于本次范围。

## 2. 已确认的产品决策

1. 后台订单默认按 `BookingOrder.createdAt DESC, id DESC` 排序，不再按预约开始时间排序。
2. 列表同时显示“下单时间”和“预约时间”，避免两种时间口径混淆。
3. 后台详情通过独立详情接口加载，不能用列表行数据冒充完整详情。
4. 用户可以对已完成订单的技师提交评价；技师可以对已完成订单的用户提交评价。
5. 技师评价标签由用户评价产生，可在用户端、技师端、关联店铺和平台后台按权限展示。
6. 用户评价标签由技师评价产生，可在与该用户有预约关系的技师端、关联店铺和平台后台展示；不进入普通用户公开主页。
7. 系统/人工后台行为标签仅平台后台可见，不向用户、技师或店铺接口返回。
8. 后台行为标签支持系统自动分配和有权限的运营人员人工添加、撤销。
9. 正向后台标签使用绿色，负向后台标签使用红色。
10. `态度差` 等主观负向标签只能人工添加，必须填写原因并写审计日志。
11. 通讯录本地个人标签不读取、不迁移、不同步，也不出现在订单详情查询中。
12. 不引入新的前端 mock、fake API 或仅浏览器存在的正式数据。

## 3. 当前问题与根因

正式预约创建页已经调用 `POST /api/v1/bookings`，订单会写入 `booking_orders` 并创建首条 `order_status_histories` 记录。后台数据中心和订单中心也已经调用正式 `GET /api/v1/backoffice/orders`。

当前后台仓储查询按 `startsAt DESC` 排序。三个月仿真订单可能具有晚于新下单订单的预约时间，因此新的 `ND...` 订单即使已经写库，也可能被排到第一页之后。数据中心订单表没有显示 `createdAt`，通用详情抽屉只转储列表字段，没有订单状态历史、参与者资料、评价或后台标签。

## 4. 范围

### 4.1 本次包含

- 后台订单排序和下单时间列。
- 正式后台订单详情接口。
- 用户端与后台端共用的状态时间线组装语义。
- 后台订单时间线持久化留言。
- 逐单用户评价技师、技师评价用户。
- 逐条评价标签及评价汇总更新。
- 系统自动和人工维护的后台行为标签。
- 本地/测试仿真账号的后台标签 seed/backfill。
- RBAC、Zod、OpenAPI、审计日志、i18n、测试和可视化验收。

### 4.2 本次不包含

- 通讯录本地个人标签。
- IM、Social 或通讯录同步。
- 普通用户公开主页重做。
- 评价申诉、审核或内容风控工作流。
- Request 大厅、NDP 账本规则或支付渠道扩张。
- 后台整体视觉重构。

## 5. 术语与可见性

为避免三种标签混用，接口和代码使用不同字段名：

| 类型 | 字段 | 来源 | 可见范围 |
|---|---|---|---|
| 评价标签 | `reviewTags` | 完成订单后的用户或技师评价 | 按评价目标和业务关系授权 |
| 后台行为标签 | `backofficeTags` | 系统规则、人工操作或非生产仿真 seed | 仅平台后台 |
| 通讯录个人标签 | 不进入本次契约 | 用户本地通讯录操作 | 保持原本地范围 |

后台标签的 `sentiment` 只允许 `positive` 或 `negative`。前端分别使用现有绿色和红色 Badge 语义，不在接口中传 CSS 类名。

## 6. 数据模型

### 6.1 `OrderReview`

逐单评价事实表：

- `id`
- `bookingOrderId`
- `reviewerUserId`
- `targetType`: `customer` 或 `technician`
- `customerProfileId`: 评价用户时填写
- `technicianProfileId`: 评价技师时填写
- `rating`: 1 到 5 的整数
- `comment`: 可空，最多 2000 字符
- `createdAt`
- `updatedAt`
- `deletedAt`

索引覆盖订单、评价人、客户目标、技师目标和软删除字段。服务层保证目标字段恰好有一个，并保证评价人、评价目标与订单真实参与者一致。同一订单、评价人和目标类型只能有一条未删除评价。

### 6.2 `OrderReviewTag`

逐条评价标签：

- `id`
- `orderReviewId`
- `label`: 1 到 40 字符
- `createdAt`
- `updatedAt`
- `deletedAt`

服务层对同一评价的标签去空格、去重并限制最多 8 个。标签必须来自后端允许的目标标签目录；本次不接受客户端任意伪造系统标签。

### 6.3 `BackofficeProfileTag`

仅平台后台可见的用户/技师行为标签：

- `id`
- `targetType`: `customer` 或 `technician`
- `customerProfileId`
- `technicianProfileId`
- `code`: 稳定代码
- `label`: 展示文字快照
- `sentiment`: `positive` 或 `negative`
- `source`: `system`、`manual` 或 `simulation_seed`
- `ruleVersion`: 系统规则版本；人工标签为空
- `evidenceJson`: 系统计算依据；人工标签为空
- `assignedByUserId`: 人工操作人；系统/仿真为空
- `reason`: 人工负向标签必填，其他人工标签可填
- `assignedAt`
- `expiresAt`: 可空
- `isActive`
- `createdAt`
- `updatedAt`
- `deletedAt`

索引覆盖目标、代码、来源、有效状态和软删除字段。系统标签只由规则服务激活或失效，后台 UI 不能直接删除系统标签。人工标签可由有权限的运营人员添加或撤销，所有变更写 `AuditLog`。

### 6.4 `OrderTimelineComment`

后台订单时间线留言：

- `id`
- `bookingOrderId`
- `actorUserId`
- `body`: 1 到 2000 字符
- `visibility`: 本次固定为 `backoffice`
- `createdAt`
- `updatedAt`
- `deletedAt`

留言不是订单状态，不写入或伪装成 `OrderStatusHistory`。详情服务把状态历史与留言按时间合并成展示事件。

### 6.5 现有 `ReviewSummary`

`ReviewSummary` 继续作为读取优化的累计摘要。创建 `OrderReview` 时，在同一事务中根据未删除评价重算目标的平均分、评价数、最近评价时间和高频评价标签。逐单评价表始终是事实来源。

## 7. 后台行为标签规则

规则常量集中在版本化的领域配置中，初始版本为 `backoffice-profile-tags-v1`。规则只使用正式数据库事实，不在读取接口中产生随机值。

### 7.1 用户自动标签

- `high_spend` / 高消费 / 正向：近 90 天已完成且已确认付款金额合计不低于 100,000 JPY。
- `high_frequency` / 利用频度高 / 正向：近 90 天完成订单不少于 6 单。
- `active_reviewer` / 积极评价 / 正向：近 90 天完成订单不少于 3 单，且用户对技师的评价覆盖率不低于 70%。
- `high_cancel_rate` / 取消率高 / 负向：近 90 天已完成或已取消订单不少于 5 单，取消率不低于 30%。
- `slow_payment` / 付费慢 / 负向：近 90 天至少 3 笔确认付款，付款确认时间减去下单时间的平均值大于 48 小时。

### 7.2 技师自动标签

- `high_rating` / 高评价 / 正向：累计有效评价不少于 10 条且平均分不低于 4.8。
- `high_completion` / 完单稳定 / 正向：近 90 天已完成或已取消的指派订单不少于 10 单，完成率不低于 90%。
- `high_self_cancel_rate` / 主动取消率高 / 负向：近 90 天由该技师执行取消的指派订单样本不少于 5 单，取消率不低于 20%。取消执行人根据状态历史的真实 actor 判断。

### 7.3 仅人工标签

- `proactive_communication` / 积极沟通 / 正向。
- `poor_attitude` / 态度差 / 负向。

本次不读取 IM/Social 内容自动判断沟通或态度。任何人工负向标签都必须填写原因。

### 7.4 计算时机

在下列正式事件成功提交后，调用标签规则服务重算受影响的用户或技师：

- 订单完成。
- 订单取消。
- 付款确认或退款完成。
- 用户或技师提交评价。

标签计算失败不能回滚已经成功的订单状态、付款或评价事务；失败必须记录结构化错误和目标 ID，并支持受权限保护的重新计算命令。现有数据通过一次幂等 backfill 计算。

## 8. API 契约

### 8.1 后台订单列表

`GET /api/v1/backoffice/orders`

- 复用正式分页结构。
- 默认排序为 `createdAt DESC, id DESC`。
- 每行同时返回 `createdAt`、`startsAt` 和 `endsAt`。
- 列表保持轻量，不内嵌逐条评价、时间线留言或完整参与者资料。

### 8.2 后台订单详情

`GET /api/v1/backoffice/orders/:id`

返回：

- 完整订单和付款字段。
- `timeline`: 已按时间升序组装的状态节点和后台留言。
- `customer`: 头像、显示名、账号、联系方式、会员等级、累计预约、评价摘要、技师给出的评价和 `reviewTags`、`backofficeTags`。
- `technician`: 头像、显示名、所属店铺、服务区域、经验、评价摘要、用户给出的评价和 `reviewTags`、`backofficeTags`；未指派时为 `null`。

仓储层使用固定 include/select 和批量关系读取，不能在映射循环中逐条查询。

### 8.3 提交订单评价

`POST /api/v1/orders/:id/reviews`

请求体：

```json
{
  "rating": 5,
  "comment": "服务过程很顺畅。",
  "tags": ["准时", "沟通清楚"]
}
```

鉴权身份决定评价方向：

- 订单客户评价订单技师。
- 订单指派技师评价订单客户。

只有 `completed` 订单允许评价。订单没有技师时，客户不能提交技师评价。重复评价、错误方向或非完单评价返回稳定的 `409` 错误键。

### 8.4 后台时间线留言

`POST /api/v1/backoffice/orders/:id/comments`

请求体只包含 `body`。成功后返回持久化留言事件。留言写审计日志，并且默认只出现在平台后台详情。

### 8.5 人工后台标签

- `POST /api/v1/backoffice/customers/:id/tags`
- `DELETE /api/v1/backoffice/customers/:id/tags/:tagId`
- `POST /api/v1/backoffice/technicians/:id/tags`
- `DELETE /api/v1/backoffice/technicians/:id/tags/:tagId`

新增请求包含 `label`、`sentiment` 和 `reason`。负向标签的 `reason` 必填。删除仅允许撤销 `manual` 来源标签，使用软删除并写审计日志。

### 8.6 权限

新增或明确以下权限：

- `backoffice:orders:read`
- `backoffice:orders:comment`
- `backoffice:profile-tags:write`
- `order:review`

平台角色按职责获得后台权限；客户和技师角色只获得 `order:review`。越权读取继续按现有订单安全规则隐藏为 `404`，明确缺少后台功能权限时返回稳定 `403`。

## 9. 统一时间线语义

后端提供一个共享的订单时间线组装器。用户端订单详情和后台订单详情对相同状态历史使用相同角色和结果文案：

| 状态历史 | 角色 | 结果文案 | 色调 |
|---|---|---|---|
| `null -> pending` | 预约创建 | 客户通过 App 创建预约，展示金额和付款方式 | 绿色 |
| `pending -> confirmed` | 服务方接单 | 店铺或技师已确认接单 | 绿色 |
| `confirmed -> inService` | 服务开始 | 技师已开始服务 | 绿色 |
| `inService -> completed` | 服务完成 | 服务已完成 | 绿色 |
| `pending/confirmed -> cancelled` | 预约取消 | 展示真实取消原因 | 红色 |

事件展示真实 `actor` 的名称、角色和头像；系统事件使用共享系统图标。不得生成数据库中不存在的检查或确认节点。后台留言以“后台评论”事件合并显示，但不会泄露到用户端。

前端统一使用 `ContactEventTimelinePanel`：左侧时间、中间连续节点线、右侧头像和消息气泡；只有取消和异常事件使用红色。底部评论框调用正式留言接口，提交成功后刷新或追加服务器返回记录。

## 10. 后台界面

### 10.1 列表

数据中心“订单数据”和订单中心都显示：

- 订单编号。
- 客户。
- 服务 / 店铺。
- 金额。
- 下单时间。
- 预约时间。
- 状态。
- 详情操作。

两处复用同一时间格式化规则和同一个正式详情抽屉组件，避免数据中心继续使用通用对象转储。

### 10.2 详情抽屉

顺序固定为：

1. 订单概要：状态、编号、下单时间、预约起止、时长、服务方式、金额、支付、门店、服务项目、地址和备注。
2. 节点时间线。
3. 预约客人资料卡。
4. 预约技师资料卡；未指派时显示明确空状态。
5. 现有订单状态和人工收款/退款操作区。

客人与技师资料卡显示评价摘要、逐条评价标签和“仅后台可见”的后台标签。后台标签使用绿色或红色 Badge，并显示来源；系统标签可展开查看计算依据，人工标签显示操作原因。

桌面宽抽屉中双方资料卡可并排，窄屏约 390px 时上下排列。不得产生横向滚动。可操作控件必须有 loading、错误和禁用状态。

## 11. 仿真和 seed

本地/测试三个月仿真 seed 为全部仿真客户和技师确定性写入 2 到 4 个 `simulation_seed` 后台标签，覆盖正向和负向展示场景。相同 seed 重跑不能生成重复活动标签。

正式订单事实能够满足规则时优先通过规则服务生成 `system` 标签。只为补足无足够行为样本的本地 UI 验收对象写 `simulation_seed` 标签。生产 seed 不生成任何模拟后台标签，脚本继续拒绝生产数据库。

## 12. 错误处理与安全

- 所有 params、query 和 body 使用 Zod。
- 评价、标签和留言长度在后端校验，前端校验只用于体验。
- API DTO 明确 select 字段，不返回密码哈希、OTP、Token、认证内部字段或不在权限范围内的标签。
- 详情加载失败展示可重试错误，不能退回列表行数据伪装成功。
- 重复评价、非法状态和并发写入使用稳定冲突错误。
- 人工标签和后台留言写审计日志。
- 所有列表和逐条评价读取过滤 `deletedAt IS NULL`。
- 自动标签规则使用 UTC 事实时间计算 90 天窗口，API 输出 ISO 8601，前端按当前时区显示。

## 13. 测试与验收

### 13.1 后端

- 仓储测试证明订单按 `createdAt`、`id` 倒序。
- API 测试证明新订单会出现在后台第一页并返回下单时间。
- 详情测试覆盖时间线顺序、真实 actor、客户/技师资料和未指派技师。
- 权限测试证明后台标签不会出现在用户、技师或商户 DTO。
- 评价服务测试覆盖双向身份、完单限制、重复提交、标签去重和摘要重算。
- 自动标签规则测试覆盖阈值边界、90 天窗口、激活和失效。
- 人工负向标签测试要求原因并验证审计日志。
- 留言测试验证持久化、权限、时间线合并和软删除过滤。

### 13.2 前端

- 数据中心和订单中心显示下单时间与预约时间。
- 打开详情时请求正式详情接口，并覆盖 loading、失败和重试状态。
- 时间线使用共享组件，事件语义和用户端一致。
- 双方资料卡显示正确评价方向、评价标签和后台标签隐私标识。
- 后台标签绿色/红色语义正确，系统和人工来源可辨认。
- 留言提交调用正式接口，失败时不追加本地假记录。
- 390px 视口下无横向溢出。

### 13.3 命令与可视化验收

- 前端 `npm run lint`、`npm test`、`npm run build`。
- 后端 `npm run lint`、`npm test`、`npm run build`。
- Prisma migration/seed 使用本地非生产数据库验证。
- 在真实后台数据中心和订单中心检查桌面默认视口及约 390px 窄屏。

## 14. 实施边界

本设计应拆成可运行、可测试、可回滚的微步骤，先保护订单可见性和详情读取契约，再引入评价事实表，最后接入后台标签计算和人工管理。每个微步骤必须先写失败测试，再完成最小实现，并独立通过相关 lint、test 和 build；不得把 IM/Social、通讯录或其他后台模块带入本次改动。
