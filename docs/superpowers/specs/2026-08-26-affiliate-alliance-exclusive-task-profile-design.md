# NeeDo 联盟、专属任务与联盟营销个人中心设计

## 1. 目标与边界

本设计把现有 Afirieito / 联盟营销浏览器本地演示中的层级、权限和分成概念，收敛为正式数据库、API、RBAC、NDP 账本与审计能力，并补齐以下已确认业务：

- 联盟是跨任务长期复用的账号级关系，不随单个任务重复创建。
- 每个账号最多拥有或加入一个有效联盟。
- 联盟仅有 1 级和 2 级；负责人、合伙人是 1 级，下级是 2 级。
- 联盟成员只能从邀请人的 NeeDo 双向好友通讯录中选择，接受邀请后才生效。
- 负责人可以设置成员权限、联盟默认介绍者比例和成员个人覆盖比例。
- 无联盟用户也可以领取公开任务。
- 任务发布者可以发布公开任务或仅指定一个联盟可见、可领取的专属任务。
- 服务完成后，总返点在同一事务内分配至平台钱包、联盟钱包和实际介绍者钱包。
- 联盟营销个人中心新增独立的联盟营销简介与渠道资源卡。
- 页面必须继承当前入口的主题 token，不固定使用现有绿色视觉。

本设计不允许继续扩张 `src/features/business-cps` 的浏览器 `localStorage` 运行态。正式能力必须使用 `/api/v1/`、JWT、RBAC、Zod、OpenAPI、Prisma/MySQL、Ledger 和 AuditLog。

任务到期自动结束和释放剩余冻结预算仍按 `2026-08-26-affiliate-task-expiry-budget-release-design.md` 作为前置独立微步骤完成；不得把联盟全量能力塞进该事务。

## 2. 术语与角色

所有用户可见文案统一使用“联盟”，不再使用“组织”。数据库和 API 领域命名统一使用 `AffiliateAlliance`。

### 2.1 联盟负责人

- 角色代码：`owner`。
- 联盟 1 级，且每个联盟恰好一名。
- 始终拥有联盟全部管理权限，不能被关闭。
- 可以邀请、移除成员，设置成员权限与介绍者比例，管理合伙人绑定，转让负责人，以及操作联盟钱包转账。

### 2.2 合伙人

- 角色代码：`partner`。
- 联盟 1 级，不与负责人或其他合伙人形成父子层级。
- 同一联盟允许多个合伙人；1 级成员之间可以建立多对多合伙人绑定。
- 合伙人能否领取任务、查看联盟数据、管理自己名下 2 级成员，由负责人逐人授权。
- 合伙人作为实际介绍者时获得其领取快照中的介绍者份额；联盟钱包不会因合伙人身份自动向其二次分配。

### 2.3 下级

- 角色代码：`subordinate`。
- 联盟 2 级。
- 必须绑定一名当前有效的 1 级直属上级，该上级可以是负责人或合伙人。
- 每个下级最多一名直属上级，不能继续增加下级。
- 能否领取任务和查看数据，由负责人逐人授权。

### 2.4 无联盟用户

- 不拥有有效联盟成员关系。
- 可以领取公开任务。
- 不能查看或领取指定联盟专属任务。
- 服务完成时，平台取得平台费，剩余返点全部进入其个人钱包。

## 3. 联盟关系约束

每个用户全平台最多只能有一个有效联盟成员关系。联盟负责人也占用这一个名额；已加入其他联盟的用户不能创建联盟、接受另一联盟邀请或成为另一联盟合伙人。

联盟关系上限固定为两级：

```text
1 级：负责人 ── 合伙人 A ── 合伙人 B
        │             │
        ├─ 2 级成员    └─ 2 级成员
        └─ 2 级成员
```

图中的 1 级横向关系是合伙人绑定，不是上下级；2 级节点只能连接一名 1 级直属上级。Service 必须阻止自绑定、重复绑定、跨联盟绑定、2 级互绑、2 级作为上级以及任何超过两级的关系。

建议使用可空唯一 `activeKey` 承载 MySQL 的“每个用户仅一个有效联盟”约束：有效成员写入 `user:<userId>`，退出或移除后置空，同时保留历史行。

## 4. 邀请、加入、退出与解散

### 4.1 邀请来源

点击“增加成员”打开 NeeDo 内部好友通讯录。候选人必须同时满足：

- 邀请人与候选人之间存在两条未软删除的 `Contact` 记录，即已经互为好友。
- 候选用户有效且未软删除。
- 候选用户当前没有有效联盟成员关系。
- 候选用户没有该联盟的重复待处理邀请。

前端候选列表仅用于体验过滤；发送邀请和接受邀请时，后端必须重新验证全部条件。

### 4.2 邀请内容

邀请时选择 `partner` 或 `subordinate`。邀请下级时必须同时指定一名有效 1 级直属上级；邀请合伙人时不得设置直属上级。

邀请状态为 `pending / accepted / rejected / cancelled / expired`。对方接受后才创建有效成员关系。若用户同时收到多个联盟邀请，第一个成功接受的邀请占用唯一有效成员资格，其余邀请在后续接受时返回明确冲突，不能覆盖既有联盟。

好友关系只作为发出和接受邀请时的准入条件；加入联盟后解除好友关系不会自动退出联盟。

### 4.3 退出与移除

- 普通成员可以主动退出。
- 负责人可以移除合伙人或下级。
- 获授权的合伙人只能邀请、移除直属于自己的 2 级成员。
- 退出或移除立即撤销新领取、新推广和联盟数据权限。
- 退出前已经领取的任务仍按领取时快照完成结算，不追溯修改受益人或比例。
- 历史成员、邀请、权限、关系、任务快照和账本不得物理删除。

### 4.4 负责人转让和联盟解散

负责人不能直接退出。其可把负责人身份转让给当前有效合伙人；转让在单事务中完成，原负责人默认转为合伙人，双方权限和层级同步重算并写审计。

联盟存在以下任一状态时禁止解散：

- 联盟钱包可用或冻结余额不为零。
- 存在未完成、未结算、待退款或待冲正的联盟任务快照。
- 存在未完成的联盟钱包转账或财务恢复事项。

解散后联盟进入 `closed`，停止新邀请、领取和转账，但所有历史记录继续保留。联盟钱包与财务主体不能因关闭而删除。

## 5. 成员权限

负责人始终拥有全部权限。合伙人和下级按成员记录分别配置：

- `canClaimTasks`：领取公开任务或本联盟专属任务。
- `canViewAllianceOverview`：查看联盟汇总表现。
- `canViewMemberDetails`：查看其他成员的任务与业绩明细。
- `canManageOwnSubordinates`：邀请、移除自己的直属 2 级成员；仅 1 级合伙人可启用。
- `canViewAllianceWallet`：只读查看联盟钱包余额和流水。

联盟钱包转账、负责人转让、联盟解散、全联盟默认分成和成员覆盖分成不提供可委派权限，始终只允许负责人操作。

权限修改只影响后续操作，不改变历史任务快照。每次修改必须记录修改前后值、操作者、目标成员和时间。

## 6. 公开任务与指定联盟专属任务

AffiliateTask 增加任务受众：

- `public`：所有符合条件的用户可以看到；无联盟用户可直接领取，联盟成员还必须拥有 `canClaimTasks`。
- `alliance_exclusive`：绑定且只绑定一个目标联盟；仅目标联盟的当前有效成员可以看到，且领取者必须拥有 `canClaimTasks`。

专属任务不能在普通任务大厅、搜索结果、推荐流或公开详情接口中泄漏给非目标联盟用户。运营后台可以基于独立 backoffice permission 查看全部任务。

发布者在发布前从正式联盟目录搜索并选择一个有效联盟。联盟目录仅向具备任务发布资格的商户或店铺账号开放。任务发布成功后，受众类型和目标联盟进入版本快照；如需修改，必须创建任务新版本并重新走审核与预算冻结，不能原地改变已发布任务的受众。

同一联盟内的多名授权成员可以分别领取同一任务。每个领取账号继续获得自己的 `publicCode`、URL token 和归因链路，不共享优惠码。

## 7. 平台费、联盟比例与领取快照

### 7.1 平台费

平台费由运营后台设置，默认 `10%`，使用基点存储：

```text
10% = 1000 bps
100% = 10000 bps
```

平台费规则必须版本化，包含费率、生效时间、创建人和审计记录。修改不得回写历史领取记录。

### 7.2 联盟分成

负责人设置一个联盟默认“实际介绍者比例”，并可以为单个合伙人或下级设置个人覆盖比例。成员领取任务时优先使用个人覆盖比例，否则使用联盟默认比例。

联盟比例不是独立随意叠加的额外费用，而是守恒后的剩余值：

```text
allianceShareBps = 10000 - platformFeeBps - promoterShareBps
```

必须满足：

```text
0 <= platformFeeBps <= 10000
0 <= promoterShareBps <= 10000
platformFeeBps + promoterShareBps <= 10000
```

平台新费率生效后，如某联盟的默认或个人覆盖比例与其冲突，系统不得静默截断比例；受影响成员的新领取操作被阻止，并明确提示负责人先调整比例。已有领取继续使用旧快照。

### 7.3 无联盟用户

无联盟用户领取公开任务时：

```text
promoterShareBps = 10000 - platformFeeBps
allianceShareBps = 0
```

例如原始返点 `1000 NDP`、平台费 `10%`，平台获得 `100 NDP`，领取者个人钱包获得 `900 NDP`。

### 7.4 快照时点

领取成功时固化：

- 是否为无联盟领取或联盟领取。
- 联盟、成员、角色和直属关系快照。
- 平台费规则版本及 `platformFeeBps`。
- 联盟默认比例、个人覆盖比例来源及最终 `promoterShareBps`。
- 计算后的 `allianceShareBps`。
- 领取时关键权限快照。

用户领取后加入、退出或更换联盟，负责人修改权限或比例，运营后台修改平台费，均不得改变已经存在的领取快照。

## 8. 服务完成后的三方原子结算

采用“服务完成时一次性多钱包分配”方案，不先把全部返点打入某一方再做二次扣款。

以任务原始返点 `1000 NDP` 为例：

```text
平台费率       10%  -> 平台钱包       100 NDP
介绍者比例     80%  -> 实际介绍者钱包 800 NDP
联盟剩余比例   10%  -> 联盟钱包       100 NDP
```

实际介绍者无论是负责人、合伙人还是下级，都获得领取快照中的介绍者份额；联盟钱包始终获得联盟剩余份额。

联盟领取的金额计算规则：

```text
platformNdp = floor(rewardNdp * platformFeeBps / 10000)
promoterNdp = floor(rewardNdp * promoterShareBps / 10000)
allianceNdp = rewardNdp - platformNdp - promoterNdp
```

联盟领取的整数尾差归联盟钱包。无联盟领取使用以下独立计算，保证不存在的联盟钱包不会承接尾差：

```text
platformNdp = floor(rewardNdp * platformFeeBps / 10000)
promoterNdp = rewardNdp - platformNdp
allianceNdp = 0
```

所有金额必须是非负安全整数，且实际入账金额之和严格等于任务原始返点。

一次服务完成事务必须同时：

1. 锁定 Attribution、Reward、预算 Reservation、发布者钱包和全部收款钱包。
2. 从发布者冻结预算捕获完整原始返点。
3. 向平台、联盟和实际介绍者钱包写入对应可用余额。
4. 写一笔 `affiliate_reward_settlement` LedgerTransaction 及完整 WalletLedger entries。
5. 写 Reward allocation 明细、预算聚合、任务聚合、对账记录和审计。

任何一个钱包、快照、预算或账本写入失败，整笔事务回滚。重复完单事件必须命中同一幂等键，不能重复入账。

## 9. 退款、冲正与恢复

服务完成后发生符合政策的退款时，冲正必须读取原 Reward allocation 金额，不能使用当前费率或重新计算比例。平台、联盟和实际介绍者三方按原入账金额原路冲正，发布者预算恢复遵循后续正式退款微步骤。

联盟钱包收入可能已由负责人转给合伙人，因此冲正时如联盟钱包余额不足：

- 不静默透支、不篡改历史转账。
- 记录联盟主体的 `outstandingRecoveryNdp`。
- 冻结联盟新转账，并从后续联盟收入中优先恢复。
- 运营后台显示待恢复金额、来源 Reward 和处理状态。

介绍者个人钱包不足时沿用同类恢复机制。平台、联盟、介绍者各自的恢复金额独立记录，合计必须等于原 Reward 的未恢复金额。

## 10. 联盟钱包手动转账

联盟钱包是独立财务主体，使用 `WalletOwnerType.ALLIANCE`，不能与负责人个人钱包混用。

只有负责人可以发起转账，收款人仅限：

- 负责人本人。
- 当前有效的本联盟合伙人。

联盟钱包不能直接向 2 级成员转账。合伙人的个人介绍者比例只在其本人实际带来完成服务时自动结算；不代表联盟钱包按比例自动分配。

转账必须校验联盟状态、负责人身份、收款成员状态、联盟可用余额、待恢复金额和正整数 NDP。成功后在一个事务内借记联盟钱包、贷记个人钱包，写 `affiliate_alliance_transfer` LedgerTransaction、转账领域记录、对账和审计。接口必须接受客户端幂等键。

## 11. 联盟营销个人中心

### 11.1 导航

联盟营销首页继续使用共享头部。点击头像进入：

```text
/afirieito/me?tab=profile
```

个人区域顶部切换由当前两个标签扩展为：

```text
个人中心 | 收益 | 资金结算
```

- `个人中心`：基础账号展示和联盟营销信息卡。
- `收益`：仅显示收益汇总、明细、状态和筛选。
- `资金结算`：仅显示可结算余额、结算记录和状态。

“语言切换”和“UI 切换”不在上述三个内容页显示，只保留在头部齿轮进入的系统设置中。

### 11.2 资料边界

头像、昵称等基础账号资料继续读取 NeeDo 统一账号资料。联盟营销简介独立保存，不覆盖用户端普通个人简介。

联盟营销信息卡支持：

- 独立联盟营销简介。
- 优势资源说明。
- X、Instagram、YouTube、TikTok 预设渠道。
- 自定义其他渠道。
- 每个渠道的频道 URL、粉丝数和更新时间。

URL 必须使用 `https`，预设渠道校验允许的域名；粉丝数必须是非负整数。用户填写的数据明确显示“用户自行填写”和最后更新时间，不伪装成平台认证数据。后续如增加认证，必须使用独立验证状态和证据，不覆盖自报值。

联盟营销信息卡只对以下主体可见：

- 本人。
- 本联盟负责人。
- 具备任务发布资格的商户或店铺账号。
- 具备相应 permission 的运营后台人员。

普通用户、非发布者和未登录访问者不能读取这些资料。

### 11.3 视觉与布局

不得把当前绿色样式固化为联盟品牌色。页面复用现有 `--client-*` 主题变量、共享头部、间距、圆角和焦点规范；切换主题后卡片、文字、边框、按钮和图标一起变化。

“联盟营销信息卡”是本页唯一强调结构：渠道按真实平台逐行展示图标、URL 域名、粉丝数和更新时间；编辑态在原卡片内展开，不跳转到另一套表单页面。其余区域保持克制，避免复制通用仪表盘的大号渐变指标卡。

移动端概念结构：

```text
┌─ 共享头部：头像 / 位置 / 设置 ─────────┐
│ 个人中心 │ 收益 │ 资金结算             │
├───────────────────────────────────────┤
│ 基础账号：头像、昵称、联盟身份          │
│ 联盟营销简介                     编辑  │
├─ 联盟营销信息 ─────────────────────────┤
│ X          x.com/...          12.8万   │
│ Instagram  instagram.com/...   4.2万   │
│ YouTube    youtube.com/...      8.6万   │
│ + 添加渠道                              │
└───────────────────────────────────────┘
```

## 12. 正式数据模型

建议新增：

- `AffiliateAlliance`：联盟主体、负责人、名称、状态、默认比例、版本和时间字段。
- `AffiliateAllianceMember`：联盟成员、角色、直属上级、个人比例覆盖、activeKey、加入/退出信息。
- `AffiliateAlliancePermission`：逐成员权限。
- `AffiliateAlliancePartnerBinding`：同联盟 1 级成员的多对多合伙人绑定。
- `AffiliateAllianceInvitation`：邀请角色、预定直属上级、状态和响应时间。
- `AffiliatePlatformFeeRule`：平台费率版本、生效时间和操作者。
- `AffiliateProfile`：用户独立的联盟营销简介和优势资源。
- `AffiliateProfileChannel`：平台、URL、粉丝数、自报更新时间。
- `AffiliateRewardAllocation`：每笔 Reward 的平台、联盟、介绍者金额与钱包快照。
- `AffiliateAllianceTransfer`：联盟钱包向负责人或合伙人的手动转账记录。

现有模型扩展：

- `WalletOwnerType` 增加 `ALLIANCE`。
- `LedgerTransactionType` 增加 `AFFILIATE_ALLIANCE_TRANSFER`。
- `AffiliateTask` 增加受众类型和可空目标联盟。
- `AffiliateClaim` 增加联盟/成员/权限/费率/比例快照字段。
- `AffiliateReward` 保留总原始返点，并关联 allocation 明细。

所有新表包含 `id / createdAt / updatedAt / deletedAt`，关联字段建索引，读取默认过滤软删除。Schema 变更必须生成新 migration，不修改已经应用的 migration。

## 13. API 与权限边界

建议正式接口：

- `GET/PATCH /api/v1/affiliate/profile`
- `POST/PATCH/DELETE /api/v1/affiliate/profile/channels`
- `GET/POST /api/v1/affiliate/alliances`
- `GET /api/v1/affiliate/alliances/me`
- `GET /api/v1/affiliate/alliances/me/eligible-contacts`
- `POST /api/v1/affiliate/alliances/me/invitations`
- `POST /api/v1/affiliate/alliance-invitations/:id/accept`
- `POST /api/v1/affiliate/alliance-invitations/:id/reject`
- `PATCH/DELETE /api/v1/affiliate/alliances/me/members/:id`
- `POST/DELETE /api/v1/affiliate/alliances/me/partner-bindings`
- `GET/POST /api/v1/affiliate/alliances/me/wallet/transfers`
- `GET /api/v1/affiliate/publisher/alliances`
- 现有 task publish、marketplace、claim 和 reward API 按本设计扩展契约。

运营后台增加平台费率、联盟列表/详情、成员关系、任务快照、三方结算、联盟转账、恢复和审计读取接口。

每个接口必须使用 Zod、分页、OpenAPI、JWT 与明确 permission。Controller 只处理 req/res，Service 负责事务与状态，Repository 负责 Prisma。前端隐藏按钮不能代替后端权限检查。

## 14. 运营后台 Afirieito

运营后台必须能够在一个联盟详情抽屉或工作区内查看：

- 联盟基本资料、状态、负责人和联盟钱包余额。
- 1 级/2 级关系、合伙人绑定、成员权限和比例。
- 邀请、加入、退出、移除、负责人转让和解散历史。
- 公开/专属任务、领取者和领取快照。
- 平台、联盟、介绍者三方 allocation。
- 联盟钱包手动转账和待恢复金额。
- 全部关联审计日志。

平台费率设置必须展示当前值、未来生效值、受影响联盟数量和版本历史。运营冻结联盟或成员只阻止新操作，不能直接改写历史账本或删除既有快照。

## 15. 测试与验收

自动测试至少覆盖：

- 只有双向好友可以被邀请，且接受后才成为成员。
- 一个账号不能同时拥有或加入两个联盟。
- 负责人/合伙人是 1 级，下级是 2 级，不能形成第 3 级或环。
- 合伙人多对多绑定不改变层级。
- 成员权限由后端执行，不能通过直接调用 API 绕过。
- 无联盟用户领取公开任务得到平台/个人快照。
- 无联盟用户和非目标联盟不能看到专属任务。
- 目标联盟授权成员可以分别领取并获得独立链接和优惠码。
- 领取后修改费率、比例、权限或成员关系不改变历史快照。
- 服务完成三方金额守恒、整数尾差正确、重复事件幂等。
- 联盟成员退出后历史任务继续结算，新领取被拒绝。
- 联盟钱包只能由负责人转给本人或有效合伙人。
- 余额不足、待恢复、非负责人、2 级收款人和重复幂等键均被正确拒绝。
- 退款按原 allocation 冲正，余额不足形成独立待恢复金额。
- 联盟营销简介独立于普通用户简介，渠道 URL、粉丝数和可见范围正确。
- 收益页和资金结算页不出现语言/UI 切换入口。
- 所有新增文案完成中、日、英三语言 i18n。

每个财务微步骤必须有本地真实 MySQL 验收脚本，拒绝 production/staging、远程数据库和生产样式数据库名；脚本只创建唯一 marker 数据并精确清理。完成声明必须同时提供相关单测、API 集成测试、lint、TypeScript、Vite build、MySQL 流程验收和真实页面检查。

## 16. 微步骤实施顺序

严格按以下顺序推进，每次只实现一个可运行、可测试、可回滚的微步骤：

1. 完成已经批准的任务到期自动结束及剩余冻结预算释放。
2. 建立联盟、成员、邀请、层级、合伙人绑定和权限数据模型与基础 API。
3. 接入 NeeDo 好友通讯录候选、邀请接受/拒绝、退出、移除与负责人转让。
4. 建立联盟营销个人资料与渠道资源正式 API。
5. 扩展任务发布为公开/指定联盟专属，并完成受众可见性与领取权限。
6. 给 AffiliateClaim 增加平台费、联盟、成员、权限和比例快照。
7. 把服务完成返点升级为平台、联盟、实际介绍者三方原子结算。
8. 完成 allocation 原路冲正、待恢复和联盟钱包手动转账。
9. 接入联盟营销前端的联盟、个人中心、收益和资金结算真实数据。
10. 接入商户/店铺任务发布选择器和运营后台 Afirieito 全量查看与配置能力。

在前一微步骤未通过验收前，不进入下一步；不得用浏览器本地演示状态或静态指标替代正式接口数据。
