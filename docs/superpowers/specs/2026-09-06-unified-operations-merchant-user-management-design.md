# 运营后台与商户后台统一用户管理设计

> 日期：2026-09-06
>
> 状态：用户已确认
>
> 所属阶段：Step 12 — 运营后台与商户后台真实数据
> 前置设计：`2026-09-01-platform-user-management-membership-experience-contact-card-design.md`

## 1. 目标

统一运营后台和商户后台的用户列表、用户详情结构与交互语言，同时保持两端既有 RBAC 和数据范围边界。

本设计以：

- 运营后台当前用户列表作为两端唯一列表规范；
- 商户后台现有正式用户详情卡作为两端唯一详情视觉规范；
- 正式 API、数据库、RBAC、审计记录作为唯一数据来源。

本次不是新建第二套页面，也不允许复制组件后分别维护。

## 2. 已确认的产品决策

1. 会员类型和个人会员倍率可以由有权限的运营人员修改，必须填写调整理由。
2. 个人会员倍率只影响调整后新产生的经验；不重算历史经验。
3. 当前等级只能由累计经验和已发布等级规则推导，不允许直接修改等级。
4. 退款和差评的修正采用追加修订版本；原始记录、时间线和留言不可覆盖或删除。
5. 运营后台与商户后台统一展示结构，但不统一扩大权限。
6. 运营后台用户列表作为统一列表基准，商户后台详情卡作为统一详情基准。
7. 用户详情增加“评价”页签，展示服务完成后用户收到的评价与标签。
8. 会员名称和评价标签必须按当前 UI 语言显示，禁止直接显示数据库字段代码。

## 3. 统一架构

### 3.1 单一共享列表

建立共享的用户目录页面组件，通过 `portalScope` 区分数据范围：

- `operations`：读取运营权限范围内的正式用户；
- `merchant`：只读取与当前商户存在正式业务关系的用户。

两端复用：

- 查询栏；
- 表头筛选器；
- 列定义；
- 空状态、错误状态与分页；
- 行详情入口。

服务端必须决定数据范围。商户端不能通过隐藏行、前端过滤或省略按钮来代替正式权限控制。

### 3.2 单一共享详情

以现有 `FormalCustomerDetailPanel` 的身份卡、页签导航和内容卡片为基础，收敛当前运营用户管理的独立详情抽屉。

共享详情组件接收：

- 正式用户详情数据；
- 当前 portal scope；
- 当前操作者权限；
- 当前 UI 语言；
- 允许显示的运营动作。

运营专属动作只在权限满足时出现。商户端保持相同信息结构，但不能获得会员调整、全局合作平台标记或跨商户评价修改权限。

## 4. 用户列表

### 4.1 统一列

列表按以下顺序显示：

1. 用户：头像、显示名称、NeeDo ID；
2. 邮箱：直接显示实际邮箱地址，未设置时显示本地化“未设置”；
3. 城市；
4. 身份；
5. 会员等级；
6. 预约数；
7. 隐私模式；
8. eKYC；
9. NDP；
10. 账号状态；
11. 注册时间；
12. 操作。

不得继续显示绿色“邮箱已绑定”代替邮箱地址。手机号绑定状态如仍需展示，必须是独立字段，不得与邮箱混在同一列中。

### 4.2 会员本地化

后端继续返回稳定代码，例如：

- `free`
- `silver`
- `gold`
- `black_diamond`

前端通过共享 i18n 映射显示当前语言名称。切换语言后列表和详情同步更新，不重新写入数据库。

禁止直接显示 `free`、`gold`、`black_diamond` 等内部字段。

### 4.3 隐私模式

列表主文案显示：

- 已开启；
- 未开启。

判断规则由正式用户隐私可见范围推导。详情页同时显示具体范围，例如完全私密、限定公开、关系网络可见等，避免只保留布尔值而丢失正式设置。

### 4.4 预约数口径

- 运营后台：用户的正式预约总数；
- 商户后台：用户与当前商户之间的正式预约总数。

两端必须使用同一列名称，但 API 返回的统计范围受 portal scope 约束。

## 5. 查询与表头筛选

### 5.1 顶部查询栏

两端统一保留运营后台样式的顶部查询区域。

全局关键词支持：

- NeeDo ID；
- 显示名称；
- 手机号；
- 邮箱；
- 城市。

查询、重置、分页和浏览器返回必须保持一致。查询条件写入 URL，重新加载页面后可恢复。

### 5.2 表头筛选按钮

除“操作”列外，可筛选或排序的表头显示统一筛选按钮：

| 列 | 能力 |
| --- | --- |
| 用户 | 名称 / NeeDo ID 排序 |
| 邮箱 | 已设置 / 未设置筛选，邮箱排序 |
| 城市 | 可搜索多选 |
| 身份 | 多选 |
| 会员等级 | 多选，按正式等级顺序排序 |
| 预约数 | 数值范围筛选 |
| 隐私模式 | 已开启 / 未开启及具体范围筛选 |
| eKYC | 已验证 / 未验证 |
| NDP | 数值范围筛选 |
| 账号状态 | 正常 / 停用 |
| 注册时间 | 日期范围、升序、降序 |

筛选条件必须提交给正式分页 API。现有 `DataTable` 的客户端筛选只能处理已加载数据，不能作为该列表的正式筛选实现。

任何筛选条件变化后：

1. 页码回到第 1 页；
2. 请求服务端新数据；
3. URL 同步更新；
4. 总数和总页数使用服务端结果。

## 6. 用户详情

### 6.1 顶部身份卡

两端统一使用商户后台现有正式详情卡结构，展示：

- 头像；
- 账号状态；
- 当前语言会员名称；
- 隐私状态；
- 显示名称；
- 城市；
- NeeDo ID；
- 身份标签。

头像或字段缺失时只显示明确的缺失状态；不得用虚构头像或模拟资料补位。

### 6.2 核心指标

身份卡下方显示与个人中心相同来源、相同口径的：

- 积分 / NDP；
- 利用次数；
- 信用值；
- 隐私模式。

运营与商户范围不同的统计值必须由服务端返回带范围的聚合结果，不允许前端从当前页列表自行计算。

### 6.3 页签

统一页签顺序：

1. 基础资料；
2. 会员等级；
3. 预约与消费；
4. 评价；
5. 权限与账号；
6. 用户动态。

页签名称、空状态和字段标签全部走现有三语言 i18n。

## 7. 会员等级与经验

会员区位于核心指标下方，视觉结构与用户信息卡一致。

展示：

- 会员类型；
- 个人经验倍率；
- 当前等级；
- 累计经验；
- 下一等级进度；
- 经验流水。

有权限的运营人员可分别修改会员类型和个人倍率。每次修改必须：

1. 填写调整理由；
2. 通过 Zod 校验；
3. 写入不可变调整记录；
4. 写入审计日志；
5. 返回新版本号或冲突错误。

会员类型和个人倍率的“修改”按钮分别放在对应字段右侧；没有权限时不显示按钮，但仍显示只读值。

等级始终由累计经验和已发布等级规则计算。会员调整接口不得接受 `level` 字段。

## 8. 评价页签

### 8.1 数据范围

评价页签展示用户作为被评价对象，在正式服务完成后收到的评价。

- 运营端：按运营权限读取；
- 商户端：仅显示当前商户订单产生的评价；
- 只关联正式订单、正式评价和正式标签记录；
- 不从列表、模拟数组或本地缓存回退。

### 8.2 列表内容

每页固定 10 条，支持翻页。每条评价显示：

- 订单编号及详情入口；
- 服务名称；
- 服务完成时间；
- 评价方姓名、头像和身份；
- 评分；
- 评价正文；
- 用户收到的评价标签；
- 创建时间；
- 是否存在修订及最新修订状态。

评价标签按当前 UI 语言显示，API 使用稳定代码。

### 8.3 评价修订

退款或差评需要修正时：

- 只有具备正式权限的运营人员可操作；
- 必须填写修订理由；
- 新建修订版本，不覆盖原评价；
- 原评分、正文、标签、作者和时间戳永久保留；
- 每次修订写入审计记录；
- 商户可以查看自身范围内的修订历史，但不能获得运营修改权限。

评价及其修订不可删除。

## 9. 利用明细与履约时间线

在审计记录上方增加利用明细列表，每页固定 10 条，支持：

- 近 7 天；
- 本周；
- 近 30 天；
- 本月；
- 今年；
- 自定义日期；
- 关键词搜索；
- 翻页。

每条记录可打开正式履约详情时间线。时间线读取订单状态历史和既有履约事件，不重新构造第二套状态机。

时间线支持追加评论：

- 评论只能新增；
- 不允许编辑或删除；
- 记录作者、时间和 portal scope；
- 商户只能访问本店订单；
- 运营按权限访问。

## 10. 合作平台标记

代理商、加盟商、供货商等合作标记分别维护独立有效期：

- 开始时间必填；
- 结束时间可填写具体日期；
- 可选择永久；
- 标记理由必填；
- 修改采用新版本，不覆盖历史范围；
- 同一用户、同一标记类型的有效时间段不得重叠；
- 所有操作写入审计。

“永久”在数据层使用明确的无结束时间语义，不使用虚构的超远未来日期。

## 11. 权限与字段显示

- 角色和权限使用标签展示；
- 权限字段默认收起；
- 展开后显示权限代码及作用域；
- 默认页面不得一次性渲染超长权限文本；
- 角色、权限和账号信息仍来自正式 RBAC 合同。

商户端不得显示运营全局权限或其他商户的作用域。

## 12. API 与数据合同

### 12.1 用户列表

统一列表 API 需要提供或补齐：

- 实际邮箱；
- 城市；
- 预约数；
- 隐私模式与具体范围；
- 会员代码；
- 经验等级和累计经验；
- 现有身份、eKYC、NDP、状态与注册时间。

列表参数需要覆盖顶部查询和表头筛选，并继续返回统一分页结构。

### 12.2 用户详情

详情聚合合同提供：

- 身份卡；
- 核心指标；
- 会员与经验；
- 预约与消费；
- 评价摘要；
- 权限与账号；
- 用户动态；
- 操作者可执行动作。

前端依据 `capabilities` 或权限结果显示动作，不自行推断管理员身份。

### 12.3 评价列表

新增或扩展正式后台评价查询，必须支持：

- `userId`；
- `page`；
- `page_size=10`；
- portal scope；
- 订单与评价标签聚合；
- 稳定排序；
- OpenAPI、Zod、RBAC 和集成测试。

## 13. 错误与并发

- 用户详情、评价、利用明细各自具有加载、空状态和错误重试；
- 失败时不得回退到列表行或模拟数据；
- 调整会员、评价和合作标记使用事务；
- 并发修改必须通过版本号或等价机制拒绝静默覆盖；
- 权限不足返回正式错误，不只隐藏按钮；
- 日期统一使用 UTC ISO 8601，界面按当前时区和语言显示。

## 14. 测试与验收

### 14.1 后端

- 列表字段、搜索、筛选、排序和分页集成测试；
- 商户数据范围隔离测试；
- 评价目标用户与商户范围测试；
- 会员修改理由、版本和审计测试；
- 合作标记时间段重叠与永久期限测试；
- 评价修订不可覆盖、不可删除测试；
- 时间线评论只追加测试；
- OpenAPI 契约测试。

### 14.2 前端

- 两端共享列表列顺序与视觉测试；
- 实际邮箱、城市、预约数和隐私状态展示测试；
- 表头筛选、URL 恢复和服务端分页测试；
- 中文、日文、英文会员名称和评价标签测试；
- 两端共享详情页签测试；
- 运营动作显示与商户动作隐藏测试；
- 评价每页 10 条和翻页测试；
- 权限默认收起测试。

### 14.3 浏览器验收

分别在运营后台和商户后台验证：

1. 顶部搜索；
2. 每个表头筛选；
3. 翻页后筛选结果不丢失；
4. 同一用户详情视觉一致；
5. 商户看不到其他商户的预约和评价；
6. UI 切换语言后会员和评价标签立即本地化；
7. 会员调整、评价修订和合作标记均强制填写理由；
8. 时间线和留言没有删除入口；
9. 控制台无错误，桌面宽度无异常横向溢出。

## 15. 交付边界

本次实现只处理运营后台与商户后台用户管理统一，以及本设计明确依赖的正式 API、数据库、RBAC、审计和测试。

不包含：

- 重构其他人员管理模块；
- 扩大商户数据权限；
- 修改会员全局等级规则内容；
- 重算历史经验；
- 删除历史评价、时间线或评论；
- 推送远端、部署或运行生产迁移。

完成后在独立分支验证并合并到本地 `main`。远端推送、部署和正式环境迁移分别报告，不因本地合并自动执行。
