# 运营数据大屏与地区下钻设计

日期：2026-09-06  
状态：已完成产品设计确认，待实施计划  
阶段：Step 12 运营后台正式数据的后续微步骤

## 1. 目标

在运营后台现有“数据大盘”标题右侧增加“数据大屏”入口。入口必须在新标签页打开独立的大屏页面，不能替换或覆盖原数据大盘。大屏使用正式数据库数据，支持浏览器全屏、低负担实时更新、自动滚动，以及日本行政区地图逐级下钻。

首期仅支持日本。国家、行政层级、API 查询和地图资源注册均使用可扩展结构，但不得展示尚无正式数据合同的其他国家。

## 2. 已确认的产品决策

- 新页面地址为 `/pf-admin.html#/admin/live-screen`。
- 数据大盘入口使用新标签页打开，并设置 `noopener`/`noreferrer`；原页面保持原状态。
- 大屏不渲染 `AdminLayout` 侧栏和顶部导航，使用完整视口布局。
- 大屏默认国家为日本，国家代码为 `JP`。
- 地图层级为“日本 → 都道府县 → 市区町村/特别区”。
- 点击都道府县会放大到该都道府县并把数据范围切换到该都道府县；继续点击区、市、町或村时再收窄数据范围。
- 例如点击东京都后显示东京的市区町村和 23 个特别区；点击新宿区后，全部指标、列表、趋势和排行榜都使用新宿区范围。
- 地区归属按服务实际发生地点计算：到店服务使用服务发生店铺地点，上门服务使用订单的实际服务地址。
- 刷新采用“缓存快照 + SSE 增量事件”的混合方案，不周期性重跑全部数据库聚合。
- 地图要精细、清晰、可辨识，但整体视觉必须继承运营后台，不制作独立赛博科技皮肤。

## 3. 范围与分步

本功能拆成两个可运行、可测试、可回滚的微步骤，按顺序实施。

### 微步骤 A：正式服务地点与地区化读模型

- 建立正式行政区参考数据和层级关系。
- 为店铺建立经过核验的标准行政区归属。
- 为 Booking 建立不可变服务发生地点快照。
- 扩展正式 Booking 创建合同，使上门服务提交结构化行政区代码。
- 对存量到店订单执行可校验回填；无法可靠识别的存量上门订单保持未归属。
- 建立地区化大屏快照 API、SSE 事件合同、Redis 缓存和权限。
- 本微步骤不创建大屏页面。

### 微步骤 B：独立数据大屏页面

- 增加新标签页入口和受保护路由。
- 实现全屏布局、精细行政地图、地图下钻和面包屑。
- 接入正式快照与 SSE。
- 实现实时订单、经营动态和排行榜的前端自动滚动。
- 完成主题一致性、响应式、可访问性和浏览器验收。

两个微步骤不得合并为一次爆发式修改。微步骤 A 验收通过后才开始微步骤 B。

## 4. 行政区与地图数据

### 4.1 行政区参考数据

行政区边界使用日本国土交通省“国土数值情報 行政区域数据 N03”2026 年版。该数据提供 GeoJSON、都道府县代码和市区町村代码。源数据地址：

`https://nlftp.mlit.go.jp/ksj/gml/datalist/KsjTmplt-N03-2026.html`

服务端保存用于关联和校验的轻量行政区目录，不把完整边界写入 MySQL。数据职责如下：

- `AdministrativeRegion`：国家代码、官方行政代码、层级、父级、中心点、数据来源和来源版本。
- `AdministrativeRegionLocale`：行政区五语言显示名称。
- 唯一键为国家代码与官方行政代码；父子关系必须属于同一国家。
- 首期目录只发布 `JP`，以后新增国家时通过独立版本化导入扩展。

所有目录表遵守仓库的 `id`、`createdAt`、`updatedAt`、`deletedAt`、索引和 migration 规则。

### 4.2 精细地图资源

原始 N03 数据只在构建工具中使用，生成可版本化的本地 TopoJSON/GeoJSON 派生资源。浏览器运行时不请求国土交通省或第三方地图服务。

生成两层资源：

- 全国层：保留 47 个都道府县、主要离岛和连续海岸线，用于日本全国视图。
- 都道府县层：按需加载当前都道府县的市区町村/特别区边界；东京层必须清晰显示 23 个特别区以及其余市町村。

地图处理必须保持共享边界拓扑，避免行政区之间出现缝隙或重叠；保留 MultiPolygon、离岛和合法的未定边界表达。构建产物记录原始文件名、来源版本、校验和、简化参数和生成时间。全国地图的 gzip 目标不超过 600 KiB，单个都道府县资源的 gzip 目标不超过 500 KiB；超过预算时应调整分层和按需加载，不能通过删除关键行政区来达标。

地图精细度验收包括：北海道、本州、四国、九州、冲绳轮廓可辨识；东京湾与岛屿不被粗糙矩形替代；东京都下钻后特别区边界无明显断裂；缩放和窗口变化后边界保持清晰。

## 5. 服务发生地点快照

### 5.1 当前缺口

当前 `Shop` 只有自由文本 `city`/`address` 和可空坐标；`BookingOrder` 只有 `fulfillmentMode`，上门地址目前被拼入 `note`。该结构不能可靠支持行政区统计，也不能把店铺地址冒充为上门服务地点。

### 5.2 正式快照

新增一对一的 Booking 服务地点快照，保存：

- `bookingOrderId`
- `countryCode`
- `admin1RegionCode` 与名称快照
- `admin2RegionCode` 与名称快照
- `source`：`SHOP_LOCATION` 或 `CUSTOMER_SERVICE_LOCATION`
- `resolutionStatus`：`VERIFIED` 或 `UNRESOLVED`
- `regionDatasetVersion`
- `resolvedAt`
- 标准时间戳和软删除字段

该快照在订单创建事务内写入，创建后不可被普通资料修改回写。大屏只读取行政代码和地区名称，不返回顾客的详细地址、电话、邮箱或订单备注。

到店订单由服务端从当前店铺的已核验行政区生成快照。上门订单请求必须提交国家、都道府县和市区町村/特别区代码；服务端校验父子层级和首期 `JP` 范围后生成快照。客户端传入的地区名称不作为权威。

### 5.3 历史数据

- 存量到店订单可以从已核验店铺地点回填。
- 存量上门订单仅在现有结构化证据足够时回填。
- 只有自由文本备注且不能可靠识别的上门订单标记为 `UNRESOLVED`，不得猜测所属地区。
- 未归属订单计入日本全国数据，但不计入任何都道府县或市区町村数据。
- 快照响应必须包含地区归属总数、未归属数和完整率，使运营人员知道地区统计覆盖度。

回填脚本必须拒绝生产式错误目标，支持只读预检、显式应用、独立复核和精确恢复策略；不能夹带应用无关 migration。

## 6. 大屏数据合同

### 6.1 统一查询范围

地区查询统一使用：

- `country=JP`，必填且首期只接受 `JP`。
- `admin1`，可空；存在时必须是 `JP` 下的都道府县代码。
- `admin2`，可空；存在时必须属于 `admin1`。
- `period`，默认 `today`，可选 `today | last7days | last30days`。

URL 保存当前地区和期间，刷新或复制同一受保护地址后可恢复相同视图。非法层级组合返回稳定的校验错误，不静默降级为全国。

### 6.2 快照接口

新增只读投影接口：

`GET /api/v1/backoffice/dashboard/live-snapshot`

响应在同一个一致性读取边界内生成，并包含：

- `scope`：国家、当前行政区和面包屑。
- `evaluatedAt`、缓存时间和数据新鲜度。
- 当前地图层的子地区及其真实业务计数。
- 所选期间四项：新增订单、完成订单、新增用户、入驻技师；`today` 时标题显示“今日数据”。
- 所选期间已确认且未退款的服务支付总额。
- 订单总览：订单量、服务 GMV、平台净收入和代理分佣；JPY 与 NDP 分开显示。
- 分页结构的第一页实时订单摘要，固定 `page=1`、`page_size=20` 并返回 `total`。
- 由正式订单状态历史和支付状态组成的地区订单动态摘要。
- 近 7 天订单量与已确认支付趋势。
- 服务项目 TOP10。
- 技师业绩 TOP10。
- 地区归属完整率和未归属数量。

接口复用现有 Dashboard、财务、订单和排行榜的正式定义与 Repository/Service 逻辑。它是同一权威数据的屏幕快照投影，不允许复制一套不同公式或建立平行 Dashboard 数据源。

所有金额口径继续遵守现有正式证据：完成/收款/退款/冲正状态必须完整；JPY、正式 NDP 和 Test NDP 不得混算。

### 6.3 SSE 接口

新增只读事件流：

`GET /api/v1/backoffice/dashboard/live-events`

事件流只发送紧凑、隐私受限的数据变化：

- 新订单或订单状态变化摘要。
- 当前地区核心指标增量或失效通知。
- 排行榜/趋势缓存失效通知。
- 连接心跳和事件序号。

SSE 必须使用 Bearer 授权的 fetch stream，禁止把 access token 放进 URL。连接要求当前活动平台身份和正式 Dashboard 读取权限。事件不包含顾客姓名、详细地址、电话、邮箱、备注或内部数字关系键。

## 7. 低负担刷新与缓存

刷新节奏固定为：

| 数据 | 节奏 |
|---|---|
| 当前时间与列表动画 | 浏览器本地每秒/每帧更新，不请求服务器 |
| 实时订单 | SSE 事件到达即更新 |
| 核心数字 | SSE 增量或缓存失效后合并更新 |
| 排行榜 | 最多每 60 秒更新一次 |
| 趋势 | 最多每 60 秒更新一次 |
| 完整快照校准 | 每 5 分钟一次，进入页面和切换地区时立即读取 |
| SSE 心跳 | 每 30 秒 |

后端按 `country/admin1/admin2/period` 缓存已计算快照。并发缓存未命中使用 single-flight 合并，避免多个大屏同时触发相同聚合。业务事务提交后只发布紧凑失效/增量事件，由共享实时基础设施转发；不能为每个浏览器建立 Redis 订阅或数据库轮询。

页面隐藏或设备锁屏时暂停定时校准和动画；恢复可见时补取一次快照。断线重连使用指数退避、随机抖动和最后事件序号，避免集中重连。慢客户端触发背压保护时允许断开并通过快照恢复，不能无界缓存事件。

## 8. 页面与交互

### 8.1 入口与全屏

现有 `DashboardPage` 标题右侧增加“数据大屏”链接。链接在新标签页打开，并保持“处理订单”“财务对账”等现有入口不变。新标签页通过既有正式 refresh/session 恢复流程建立自己的认证状态；不得把 token 放入 URL、`window.name` 或 opener 消息。

`LiveDashboardPage` 不使用后台侧栏，默认占满可视区域。右上角提供“进入全屏/退出全屏”；使用浏览器 Fullscreen API，按 `Esc` 可退出。浏览器拒绝全屏时保留普通页面并显示清晰提示。

### 8.2 布局

桌面宽屏采用三列结构：

```text
┌──────── 当前时间 ─────── 数据大屏 ─────── 地区/全屏 ────────┐
│ 所选期间数据      │ 期间确认支付总额 + 地图 │ 订单总览        │
│ 4 个正式指标      │ 日本 → 东京 → 新宿区   │ 4 个经营指标    │
├───────────────────┤                         ├─────────────────┤
│ 实时订单滚动      │                         │ 服务项目 TOP10  │
├───────────────────┼─────────────────────────┼─────────────────┤
│ 地区订单动态      │ 近 7 天订单与支付趋势   │ 技师业绩 TOP10  │
└───────────────────┴─────────────────────────┴─────────────────┘
```

小于宽屏最低尺寸时允许页面等比缩放到可读下限并出现明确的“建议横屏/宽屏查看”提示，不把三列强行挤成不可读窄列。该页面不是移动端核心操作页面，但必须避免横向内容越出浏览器画布。

### 8.3 地图交互

- 初始显示日本全国和 47 个都道府县。
- 地图区域支持鼠标、触控和键盘选择。
- 悬停或聚焦显示行政区名称、订单数和确认支付金额。
- 点击行政区后更新 URL、地图层级和所有数据面板。
- 顶部面包屑显示“日本 / 东京都 / 新宿区”，每一级均可返回。
- 切换地区期间保留最后成功快照，并显示目标地区加载状态，不整屏清空。
- 新订单只在对应行政区出现一次轻微扩散提示，随后消失；减少动态效果模式下改为静态高亮。

### 8.4 自动滚动

- 实时订单每 3 秒平滑移动一行。
- 服务和技师排行榜每 4 秒移动一行，服务端数据仍按 60 秒节奏更新。
- 鼠标悬停、键盘焦点或页面隐藏时暂停。
- 数据不足一个视口时不滚动，也不复制记录制造重复内容。
- 新事件从列表顶部插入，使用稳定公开订单号和事件序号去重。
- `prefers-reduced-motion: reduce` 下取消平移、数字跳动和地图脉冲，仅更新内容。

## 9. 视觉规范

大屏是“运营后台的专业全屏版本”，不是独立科技展厅。

- 继承打开入口时的运营后台日间/夜间主题偏好。
- 复用现有后台主题 token、字体、状态色、圆角、边框和层级。
- 不使用星空、光束、扫描线、机械边框、粒子背景或持续霓虹闪烁。
- 背景、卡片和表格使用现有后台的低对比深色/浅色层级。
- 地图使用克制的扁平矢量风格：无数据区为中性底色，有数据区按 NeeDo 蓝色深浅编码，悬停提高亮度，选中区使用清晰描边。
- 数字变化使用短淡入，不使用翻牌器或夸张跳动。
- 图表、按钮、空状态和错误状态沿用后台语义色。
- 精细地图本身是页面的唯一视觉重点，其余装饰保持克制。

## 10. 权限、安全与审计

- 页面路由继续要求 `page:dashboard`。
- 快照与 SSE 继续要求正式平台身份和 `backoffice:dashboard:read`；不得因新页面扩大普通用户、商户或技师权限。
- 前端隐藏入口不能代替后端 RBAC。
- SSE 连接建立和地区切换读取遵循现有只读审计策略；心跳和每个列表动画不写审计，避免无意义负载。
- 响应不返回密码、token、OTP、顾客 PII、完整上门地址或内部关系键。
- 行政区、期间和分页/列表上限必须由 Zod 严格校验并写入 OpenAPI。

## 11. 加载、错误与恢复

- 首次加载失败：显示错误原因、重试入口和返回数据大盘链接。
- 地区切换失败：保留当前成功地区和数据，明确显示目标地区切换失败。
- SSE 断线：显示“实时连接恢复中”和最后成功更新时间，后台自动重连。
- 快照超时：保留最后成功数据，标记“数据可能已过期”。
- 地区无数据：显示真实的 0 和空状态，不使用演示值。
- 地图资源加载失败：数据卡仍可显示，提供地区下拉和面包屑作为可访问的备用选择方式。
- 全屏请求被拒绝：保持普通页面，不阻断数据使用。
- 服务端返回的地区与请求条件不一致：前端拒绝提交该快照，继续显示上一份一致数据。

## 12. 测试与验收

### 12.1 微步骤 A

- migration/schema 测试：行政区目录、地点快照、唯一键、外键、层级和索引。
- Validator 测试：`JP`、都道府县/市区町村父子关系、非法国家和非法层级组合。
- Booking Service/Repository 测试：到店地点、上门地点、事务回滚、不可变快照和隐私投影。
- 回填测试：已核验到店订单、不可识别上门订单、重复执行幂等和精确统计。
- Dashboard Repository/Service 测试：全国、东京都、新宿区范围；所有面板共享相同地区和评价时间。
- 财务口径测试：确认支付、退款、冲正、JPY/NDP/Test NDP 分离。
- 缓存和 SSE 测试：single-flight、失效合并、权限、背压、断线恢复和事件去重。
- API/Supertest/OpenAPI/RBAC/审计测试。
- 回滚安全的本地真实 MySQL checker，完成后验证临时数据和缓存键全部清理。

### 12.2 微步骤 B

- 入口测试：新标签页、正确 URL、`noopener`/`noreferrer`、原页面不导航。
- 路由权限测试：无权限拒绝，平台权限成功。
- 地图测试：默认日本、47 个都道府县、东京下钻、特别区选择、面包屑返回、键盘选择。
- 一致性测试：点击新宿区后全部请求和面板都使用同一个地区条件。
- 全屏测试：进入、退出、拒绝和 `Esc` 状态同步。
- SSE 客户端测试：Bearer fetch stream、增量合并、断线退避、页面隐藏/恢复和重复事件。
- 自动滚动测试：节奏、悬停/焦点暂停、少量数据不复制和减少动态效果。
- 错误恢复测试：保留上次快照、地图备用选择器和筛选错配拒绝。
- 五语言文案检查；行政区名称按可用正式 locale 显示。
- 构建产物检查：地图来源清单、校验和、资源大小和懒加载边界。

### 12.3 浏览器验收

在已证明 PID、cwd、分支、前端代理和正式后端来源的标准本地运行时进行：

- 1920×1080 和 2560×1440 的日间/夜间主题。
- 新标签打开、原数据大盘状态保留。
- 日本 → 东京都 → 新宿区完整下钻与逐级返回。
- 触发一个隔离测试订单事件，验证 SSE、列表、地图提示和指标更新，并清理测试数据。
- 全屏进入/退出、窗口缩放、无横向溢出、控制台无未解释错误。
- 暂停标签页后恢复，确认只补取一次快照且无请求风暴。
- 对照真实 MySQL 查询核验所选地区的订单、支付、排行和未归属数量。

自动化测试和 build 通过不能替代以上浏览器与真实数据流验收。

## 13. 非目标

- 首期不开放日本以外国家。
- 不接在线底图、导航、路线或出行计价服务。
- 不在大屏编辑订单、财务、店铺或行政区数据。
- 不展示顾客精确位置或详细上门地址。
- 不增加 mock、示例数字、前端随机事件或浏览器本地业务数据。
- 不重做现有数据大盘，不删除现有入口、指标卡、筛选或详情页。
- 不在本功能中执行大规模压测；容量阶梯仍属于 Step 14。

## 14. 完成定义

只有在两个微步骤分别完成代码、专项测试、lint、build、OpenAPI、真实 MySQL 检查和浏览器验收后，才能宣称数据大屏完成。必须分别报告本地实现、migration 应用、正式数据验证、浏览器验收、远端推送和部署状态；其中任何一项未执行都要明确标为未完成。
