# eKYC personal information form implementation plan

Goal: Replace the user's static verification cards with a usable NeeDo-themed identity form based on the approved reference. Hide bottom navigation and show the shared close control.

Architecture: Remove static verification claims and the user-requested status card; retain backend verification guards. Isolate the personal information model and input/confirmation views under settings. Reuse application fields, custom dropdowns, floating actions, and red header errors. No mock API, fake success, or stored verification result. Submission processing depends on the user's choice of manual review or a named real eKYC provider.

Approved fields: separate family/given name and full-width katakana; birth year/month/day; sex; postal code, prefecture/city, street, building/room; occupation (with other text). Exclude residence type, contact phone, email, bank/card/PIN, transaction purpose. Continue using the current palette rather than the reference bank's branding.

- [x] Implement the model and input/confirmation views. Preserve entries between these views in component memory; do not write sensitive details into browser storage.
- [x] Reuse shared header close and hide bottom navigation; keep errors floating below the header and actions at the bottom.
- [ ] Complete submission integration after the required verification-processing choice is provided. Never manufacture a verified result.
